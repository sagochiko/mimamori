# 開発のハーネス

このリポジトリでは Claude Code を開発の中心に置いている。ここではそのための仕組み(CLAUDE.md、フック、サブエージェント、skill、MCP、mod)を、何のために置いたかと一緒に並べる。審査の「モデルや機能(Skills、サブエージェント、MCP、フックなど)を目的に応じて選び、使い分けているか」に答えるための文書でもある。

考え方は2つある。1つは破ってはいけない決まりへの違反を、Claude の注意力に頼らずフックで止めること。ハッカソンのルール(期間中に書いたものだけ、権利のない素材を使わない)、精度の測り方の公正さ(最後に測る組を見ない)、本番と秘密の扱いがこれにあたる。もう1つは ISUCON2026 を1人で優勝した Yoshinori Kawasaki さんの[当日編の記事](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)にある、時刻と停滞をフックが見て監査役を呼ぶ仕組みを、締切が決まったハッカソンに合わせて持ち込むこと。

## 毎回渡すもの

`CONDITIONS.md` に、締切、今のマイルストーン、進んでよい範囲、精度の測定の予算を書く。セッションを始めるたびに、フック(`session-context.sh`)がその中身を残り時間と今のマイルストーンの Issue と一緒に Claude に渡す。指示は「CONDITIONS.md を読んでから次の Issue を進めて」の1行で足りるようにしてある。

`CLAUDE.md` はリポジトリから読み取れないことだけを書き、200行未満に収めた。iOS、裏側、試験用の例文、文書の決まりは `.claude/rules/` に分けてあり、それぞれの分野のファイルを触るときだけ読み込まれる。

## git のフック

リポジトリは提出のときに公開するので、コミットにも家族の情報を入れない仕組みを `.githooks/` に置いた。`make setup` で `core.hooksPath` を向ける(`make bootstrap` の中でも流れる)。

- `commit-msg` はコミットメッセージの形を確かめる。メッセージに電話番号の形、メールアドレス、非公開の語、時刻、作者の以前のプロジェクトの名前が入っていたら止める。マージのメッセージも調べる。規則に当たったときは題の行を出し直さない。止めた語や時刻がそこにあるかもしれないため
- `pre-commit` はステージした差分の足した行だけを調べ、同じ規則に当たったら止める。時刻は `.md` の文書の行だけを見る。`origin/main` を取り込むマージの途中では、マージの相手(`MERGE_HEAD`)に既にある行を調べず、このブランチと、衝突を手で解いた行だけを調べる。main の行は main に入ったときに調べてあり、取り込むたびに止まると取り込めないため(2026年11月4日に作者が決めた)

規則は [`scripts/scan-private.sh`](../scripts/scan-private.sh) の1か所にあり、`guard-private.sh` と `/mm-endgame` の公開前の調べもこれを使う。電話番号は携帯、固定、+81 の形を、全角の数字も含めて見る。メールアドレスは `noreply@anthropic.com` と `*@users.noreply.github.com` だけを通す。非公開の語は作者だけが書く `.claude/private-terms.local` に1行に1語で置き、大文字と小文字を区別せずに探す。Claude はこの一覧を読まず、当たったときも語そのものは出さず「`docs/x.md:12: private term`」のように場所と規則だけを出す。

試験用の例文とテスト(`server/test/`、`eval/cases/`、`eval/test/`、`ios/Core/Tests/`、`scripts/test-hooks.sh`)では、電話番号とメールの形を調べない。詐欺の SMS の差出人や「サポートセンター 050-…」がテストの中身そのものだからだ。電話番号の形を判定する規則(`server/src/rules/`)と、レビュー役や監査役の報告の原文(`docs/audits/raw/`)も同じ扱いにした。規則は番号の型そのものを書き、原文は試験の作り物の番号や会社の公式のアドレスを引くため(2026年11月4日に作者が決めた)。公開前の全履歴の調べ(`scripts/scan-private.sh history`)も同じ範囲で見る。各コミットが足した行を見て、マージのコミットは数えないので、main から入った行を二重に数えない。非公開の語はそこでも調べるので、家族の本当の番号やアドレスは一覧のほうに書く。バンドル ID の `com.sagochiko.mimamori` とチームの ID は公開してよいもので、止めない。

時刻も同じ所で止める(#116)。公開される記録(Issue、PR、コメント、コミットのメッセージ、文書)には時刻を書かず、日付だけにする(2026年11月4日と5日に作者が決めた)。この決まりは memory にしか無く、2026年11月5日にこのセッションが思い出さずに、時刻を Issue の本文4件、コメント4件、PR の本文1件、コミットのメッセージ1件に書いた。本文とコメントはあとで直したが、コミットは履歴を書き換えないので残った。必ず守ることなので、文ではなくフックに置いた([best practices](https://code.claude.com/docs/en/best-practices) の「If something has to happen every time, make it a hook, a deny rule, or a managed setting」)。だれの何の時刻かはフックに分からないので、一日のどの時刻の形も止め、止める文で日付だけにするよう伝える。当たったときは、ほかの規則と同じく場所と規則(`time of day`)だけを出す。

止める形は、コロンでつないだ時刻(秒つき、1桁の時も、全角の数字とコロンも)、「時」の前の数(「時台」「時04分」も、全角の数字も)、英語の am と pm だ。「午前」「午後」「夕方」「夜」を前に付けた時刻も、「時」かコロンの形なので止まる。通すのは、長さの「時間」、ISO 8601 の T でつないだ日時(秒、小数、末尾の Z か時差も)、コロンのすぐあとの数(`docs/x.md:13:45` の行と桁)だ。T でつないだ形は、`CONDITIONS.md` の節目や `make usage` が書く記録の時刻のように機械が読む値で、文書の地の文の書き方ではないので通した。T でつないだ日時の末尾の時差もコロンの時刻の形をしているので、日時を丸ごと外してから時刻の形を探す。この規則を説明する文書では、時刻を例に書かず、形を言葉で書く。

かける所の範囲は次のように決めた。コミットのメッセージ(`commit-msg`)と gh で書く題と本文(`guard-private.sh`)は、すべての行を見る。ステージした差分(`pre-commit`)は `.md` の文書の行だけを見る。コードには cron の式やテストの時刻の値があるためだ。`eval/results.jsonl` は機械の記録で、`ts` を1日の回数の数え(`eval/run.ts`)、`pacer.sh`、帯、`/mm-eval` が読むので、時刻ごと残す。人が読む [`eval/RESULTS.md`](../eval/RESULTS.md) の表の行は、日付だけにした。同じ日の回は `results.jsonl` の `ts` と `git_sha` で見分ける。

試験用の例文、テスト、レビュー役と監査役の報告の原文(`docs/audits/raw/`)は、電話番号の形と同じく時刻を調べない。原文はレビュー役の言葉をそのまま残すもので(`/mm-task` の手順6)、ログの UTC の時刻や、アプリが持つ時刻、相談の筋書きの例をそのまま引く。2026年11月5日に保存済みの原文87本(うちレビュー役が82本)を1本ずつ `scripts/scan-private.sh text` に流すと、33本(レビュー役は28本)がこの規則に当たった。電話番号かメールの形を持つものは4本で、そのうち3本は時刻の形も持っていた。止めると、時刻を扱う機能のレビューほど「(伏せた)」だらけになる。PR に原文を貼るときも、本文の最後が保存した原文と1バイトも違わないときだけ、その部分を `raw report` として、コミットのときと同じに扱う。時刻、電話番号の形、メールの形は調べず、非公開の語は調べる。電話番号の形を調べたままだと、「(伏せた)」に替えたところで最後が原文と合わなくなり、本文全体が調べられて原文の時刻まで止まるためだ(PR #119 のレビュー)。非公開の語で止まったときは、保存した原文のほうを「(伏せた)」に替えて貼り直す(`/mm-task` の手順6)。原文のファイルの名を書くだけでは外れず、上の見出しの行はほかの本文と同じに調べる。

アプリが持つ時刻を書く文書も調べない。`docs/design.md`、`docs/plan.md`、根の `README.md` と `README.ja.md` は、毎日の声かけの既定の時刻と選べる時刻の範囲のような、だれの操作でもない時刻を書き、日付だけにすると意味が無くなる。ほかの `.md`(開発の記録、`CONDITIONS.md`、`eval/README.md` のような下の階層の README、監査のまとめ、skill など)は調べる。`CONDITIONS.md` は行事の節目の時刻も書くが、作者の決定の記録も同じファイルにあり、ファイルごと外すとそこに時刻を書いても通ってしまう(PR #119 の2回目のレビュー)。節目の時刻は frontmatter に T でつないだ形で置き、地の文は `feature_freeze`、`code_freeze`、`submit_window` の鍵の名で指す。メッセージや Issue、PR でアプリの時刻を書くときは、「既定の時刻」のように時刻の形を避ける。

規則を入れる前からある文書の時刻は、次のように扱った。`pre-commit` は足した行だけを見るので、残した行も、そこを書き換えるときに止まる。書き換えることの多い `CONDITIONS.md` の地の文は、締切と節目を frontmatter の鍵の名で指す書き方にした。`CLAUDE.md` のハッカソンの決まりの行は開発期間の始まりと書き、`/mm-endgame` の skill の description は締切を `deadline` の鍵で、`/mm-deploy` の skill の1行は毎日の掃除を `src/cron.ts` の `dailyAtJst` で指す書き方にした。`eval/README.md` の2行は `make eval` の回を時刻で指していたので、日付とコミットで指す書き方に直した。開発の記録(`docs/dev-log.md`)の前からある見出しと本文、日付のついた監査のまとめ(`docs/audits/` の下)、`make eval` が足すだけの `eval/RESULTS.md` の前の行は、あとから書き換えないので、そのまま残した(git の履歴も書き換えていない)。`docs/claude-usage.md` の時刻は、次に `make usage` で書き直すときに日付だけになる。

公開前の全履歴の調べ(`scripts/scan-private.sh history`)には、この規則をかけない。コミットは書き換えず、すでに入ったものはそのまま残すと作者が決めているので、当たっても直す先が無いためだ。`/mm-endgame` の手順9が見るのは今までどおり電話番号、メール、非公開の語になる。

自己テスト(`scripts/test-hooks.sh`)は、本物の一覧を読まないよう、テストのときだけ差し替えの変数でダミーの一覧を渡す。worktree から本体のツリーの一覧を見つけられるかも、使い捨てのリポジトリで確かめる。`.worktreeinclude` には2つの一覧を書き、Claude Code が作る worktree にも写させる。

## サブエージェント

実装とレビューを分け、レビュー、検証、監査、採点の役には編集のツールを渡していない(Bash は git や gh で読むために持つ)。過去の受賞作で公開リポジトリを確認できた8件のうち、サブエージェントの定義を置いていたものは無かった。数を増やすより、役割と使うモデルの理由が言えるものだけを置いた。

| `mm-verifier` | Opus | medium | ビルド、テスト、シミュレータの画面を確かめ、数字と画像だけを返す | 手順は決まっているが、撮った画面が設計どおりかの判断と、落ちたテストの原因の行の読み分けが要る |

主のセッションは、作者と話す対話の主も、作者がいないあいだの `/mm-autopilot` の主も Opus にした。2026年11月4日の夜に作者が、autopilot の主は聞ける人がいないので何をマージし、何を「作者: 」の Issue に積むかを1人で決めるとして Fable を選んだ(#85)。2026年11月6日に作者が Opus に戻した。前の夜の引き継ぎで autopilot の新しい窓が `claude --model fable` で起動され、作者は既定の Opus から変わっていたことに驚いて、手で Opus に戻したからだ。同じ日に作者が「AdvisorのみFable」と言い、レビュー役、監査役、採点役も Opus にした(上の表)。Fable が残るのは advisor(`advisorModel`)だけだ。effort は、同じ日に作者が「コストは別に考えなくてもいい」と言ったので、はじめは `max` を除いた一番上(xhigh、確かめ役と例文集めは high)にした。2026年11月5日に作者が、主もサブエージェントもすべて medium にすると決めた。新しい主は `/mm-handoff` がどちらの場合も `claude --model opus` で起動する。Opus は既定のモデルだが、[model-config](https://code.claude.com/docs/en/model-config) に「`/model` saves your choice as the default for new sessions by writing the `model` field in your user settings」とあり、作者が前に `/model` で選んだモデルが新しい窓に持ち越されうるので、起動の行に書いておく。起動できたかはプロセスではなく、[`scripts/handoff-started.sh`](../scripts/handoff-started.sh) が新しい transcript に道具を呼んだ Claude の答えと、その道具の結果(同じ `tool_use_id` の `tool_result`)の両方が出たかで見る。許可の確認で止まった窓や、API のエラーで落ちた窓を「起動できた」と取り違えて、作者がいないあいだに古い主まで止まらないようにするためだ(PR #90 のレビューの指摘)。道具の呼び出しは許可の確認に答えが来る前に transcript に書かれ、brief は作業フォルダの外にあって最初の読み取りで確認が出うる([permission-modes](https://code.claude.com/docs/en/permission-modes) の「The first read outside the working directories」)ので、結果の行も要る(PR #90 の3回目のレビュー、原文 [`docs/audits/raw/20261105-0146-mm-reviewer-a25a8f44.md`](audits/raw/20261105-0146-mm-reviewer-a25a8f44.md))。この Mac の引き継ぎで起動された6本の transcript は、どれもこの判定で「始まった」になる(2026年11月5日に流して確かめた)。check が exit 2(起動の前の一覧が無い)を返したときは、先に stamp の打ち間違いかを見て、窓を開き直すのは1回までにする。打ち間違いで2つ目の autopilot が同じ木に開かないようにするためだ。[cli-reference](https://code.claude.com/docs/en/cli-reference) の `--model` は「Sets the model for the current session with a model alias such as `sonnet`, `opus`, `haiku`, or `fable`」で、起動したセッションにだけ当たる。skill の frontmatter の `model` は「The override applies for the rest of the current turn and isn't saved to settings」([skills](https://code.claude.com/docs/en/skills))なので、何ターンも続く autopilot には使えない。

主の設定は [`.claude/settings.json`](../.claude/settings.json) の2つのキーで入れた。`"language": "japanese"` は [settings-reference](https://code.claude.com/docs/en/settings-reference) で Scope が「Any file」のキーで、サブエージェントの報告が英語だと主の応答も英語に引かれていたので足した。effort は `modelSettings` の `claude-opus-5-5` と `claude-fable-5-1` に、どちらも `medium` を置いた(はじめは `xhigh`)。上の階の `effortLevel` にしなかったのは、文書に「In project, local, and managed settings, and with `--settings`, this key applies to every model.」とあり、どのモデルにどの値を当てたかが設定から読めなくなるからだ。Fable 5.1 もモデルの名前で置いたのは、ユーザー設定の古い形の上の階の `effortLevel` が「it keeps applying where it applied before, on Opus 5, Fable 5.1, and earlier models」とされ、プロジェクトに Fable の値が無いと、作者の端末の古い値が Fable で動く主の effort を決めてしまうからだ(PR #90 のレビューの指摘)。はじめは autopilot の主のための値だった。2026年11月6日に autopilot の主もサブエージェントも Opus になり、Fable で動くのは advisor だけになった。それでも、作者がセッションの中で `/model fable` に切り替えたときのために残した。レビュー役などのサブエージェントは frontmatter の `effort` で決まり、model-config には「On another model, that level doesn't apply. To pick a subagent's level, set `effort` in its definition.」とあるので、この値は当たらない。advisor の effort は、model-config の全文を2026年11月6日に読んだ範囲では書かれていない。作者のユーザー設定にも Opus 5.5 の xhigh が保存されているが、それは作者の端末の中だけなので、このリポジトリを開く人と worktree のセッションに同じ値を渡すためにプロジェクトに置いた。ファイルをまたぐと「the highest-precedence settings file that sets either an `effortLevel` for that model or a top-level `effortLevel` that applies to that model decides」なので、プロジェクトの値がユーザーの値より強い。セッションの中の `/effort` と起動の `--effort` はそれより先に当たる([model-config](https://code.claude.com/docs/en/model-config) の「Adjust effort level」)。

サブエージェントの model と effort は frontmatter で決める。[sub-agents](https://code.claude.com/docs/en/sub-agents) の `model` は「`sonnet`, `opus`, `haiku`, `fable`, a full model ID such as `claude-opus-5-5`, or `inherit`」を取り、`effort` は「Overrides the session effort level」で「Options: `low`, `medium`, `high`, `xhigh`, `max`; available levels depend on the model」とある。[model-config](https://code.claude.com/docs/en/model-config) の表では Fable 5.1 と Opus 5.5 のどちらも `medium` を使える。呼ぶ側については、Agent ツールに渡す model が解決の順番の1番目(「The per-invocation `model` parameter」)で、frontmatter より優先される。作者のグローバルの決まりは「単純な作業は Sonnet を指定する」なので、そのまま当てると検証役とレビュー役が Opus から黙って外れる。`/mm-task` と `/mm-endgame` には、`mm-*` を呼ぶときは model を省くか定義と同じにすると書いた。2026年11月6日に作者が、軽めのレビューや作業は Sonnet に振ると決めたので、PR の差分が日付つきの記録(ビルド番号のコミット、`docs/audits/raw/`、`docs/dev-log.md`、`docs/claude-usage.md`)だけのときに限り、`mm-reviewer` と `mm-verifier` に `sonnet` を渡す例外を `CLAUDE.md` の「モデルの使い分け」に置いた(PR #148)。行数ではなく変える中身で分けたのは、`docs/plan.md` の通知先の約束を3行だけ変える PR まで Sonnet で読まれないようにするためだ。同じ日に作者が「かるい作業はSonnetでもいいんだけど今ってそうはなってないのかな」と聞き、主が範囲を AskUserQuestion で聞いた。作者は「画面の無い確かめも Sonnet」を選んだ。検証役がシミュレータの画面を撮らず見ないとき(`make verify`、試験、`make eval-rules`、grep での照合)は、PR の中身にかかわらず `mm-verifier` に `sonnet` を渡してよい。コマンドを流して数字を読むだけなので、モデルの差が出にくいからだ。画面を撮る確かめと、画面が設計どおりかを判断する確かめは Opus のままにし、実装役とレビュー役はこの例外に入れない。effort は frontmatter の `medium` のまま当たる。続きを頼むと同じモデルで動くので、重い変更が乗ったときや、Sonnet の検証役に画面の確かめが要るようになったときは新しく起動する。

報告の形は、役ごとの1行目の値を `CLAUDE.md` の「作業の流れ」の表の1か所に置き、各定義の「Write the report in Japanese, in this shape」がそれを指す。確かめる `report-form.sh` は2つの時点で動く。報告を渡す道具の `SubagentHandback` は「Provided only in auto mode」([tools-reference](https://code.claude.com/docs/en/tools-reference))なので、auto mode では PreToolUse(matcher `SubagentHandback`)で `tool_input.message` を見て、外れたら exit 2 で呼び出しを止める。PreToolUse の exit 2 は「Blocks the tool call」で、stderr がサブエージェントに渡る([hooks](https://code.claude.com/docs/en/hooks))。サブエージェントの呼んだ道具にも settings のフックが当たり、入力に `agent_type` が入る([sub-agents](https://code.claude.com/docs/en/sub-agents) の「a `PreToolUse` hook in `settings.json` also runs before every tool a subagent uses」)。auto mode でないときは報告が最後の返事になるので、SubagentStop(matcher `^mm-`)で `last_assistant_message` を見る。hooks の文書に「Returning `decision: "block"` with a `reason` keeps the subagent running and delivers `reason` to the subagent as its next instruction. A hook that blocks by exiting 2 delivers its stderr message the same way.」とあるので、止めるとサブエージェントは理由を読んで書き直す。SubagentStop の matcher は agent type に当たり、`^` を含む文字列は「JavaScript regular expression, unanchored」として照らされるので `^mm-` にした。SubagentHandback で渡したあとの `last_assistant_message` は「the subagent's closing text, if any, which is not the delivered report」なので、サブエージェントの transcript(`agent_transcript_path`)に SubagentHandback の呼び出しがあれば、SubagentStop では見ない(この Mac の transcript で、その呼び出しが `tool_use` の行として残ることを確かめた)。繰り返しは、SubagentStop では `stop_hook_active`(「`true` when Claude Code is already continuing as a result of a stop hook」)が true なら通し、hooks-guide の「parse the `stop_hook_active` field from the JSON input and exit early if it's `true`」に合わせた。PreToolUse には同じ印が無いので、`agent_id` ごとに止めた数を `.claude/state/report-form/` に数え、2回までにした。片方だけにしなかったのは、PreToolUse だけでは auto mode でない場面を、SubagentStop だけでは auto mode で渡された報告(SubagentStop には届かない)を見逃すからだ。

日本語の割合の閾値は、2026年11月5日に保存済みの報告で測って決めた。[`docs/audits/raw/`](audits/raw/) の70本の原文(レビュー、監査、採点、調べもの)は、コード、道筋、URL を除くと日本語の字が51%以上だった。英語の文書(hooks-guide、best-practices)は0%、以前の英語の形の検証役の報告は6〜15%だった。10%未満を返すので、英語の道筋やコマンドの引用が多い日本語の報告は止まらず、地の文が英語の報告だけを返す。数え方は UTF-8 の仮名と漢字の先頭のバイト(U+3000〜U+9FFF)と、A〜Z、a〜z の字数で、macOS と Linux の両方にある `tr` と `awk` で数える。

フックを試すときは、試す形を自分の Bash の行に書かない。このセッションのフックは、サブエージェントの道具の呼び出しにも当たり([sub-agents](https://code.claude.com/docs/en/sub-agents) の「a `PreToolUse` hook in `settings.json` also runs before every tool a subagent uses」)、行の文字を読むので、`echo` や heredoc、`python3` の引数の中に `wrangler d1 execute --remote` と書き込みの語を並べただけでも本物の操作と読んで作者に確認を出す。2026年11月6日、PR #172 の試験を足した主の行(2回)と、すり抜けを探したレビュー役の行(1回)で、作者に確認が3回出た(`.claude/logs/usage.jsonl` の `guard-prod` の記録で見た。呼び出し元は記録に残らないので、主とレビュー役の分け方は動いていた時の重なりから読んだ)。作者は「本当に確認ばっかで進められない」と言った。役ごとの手段は次のとおり。主と実装役は、試す形を Edit で `scripts/test-hooks.sh` に書き、`bash scripts/test-hooks.sh` で流す。検証役は `bash scripts/test-hooks.sh` を流すだけにする。レビュー役と監査役は書くツールを持たないので、フックのコードを読み、試したい形を報告に並べ、足すのは実装役に任せる。`scripts/test-hooks.sh` は外のファイルを読まないので、スクラッチパッドのファイルから渡す道は無い。電話番号の形は、`guard-private.sh` が見るコミットと gh の書き込みの行でだけ止まり、`echo` の中では止まらない。`mm-implementer`、`mm-reviewer`、`mm-verifier`、`mm-auditor` の定義と `CLAUDE.md` の「検証」にもそう書いた。

effort の `max` は使わない。model-config に「`max` may show diminishing returns and is prone to overthinking, so test before adopting it broadly」とあり、設定のキーでも「`max` isn't accepted as a level in either key」だからだ。[`scripts/test-hooks.sh`](../scripts/test-hooks.sh) は、各サブエージェントの frontmatter が opus、effort が medium であることと、advisor が Fable のままであることと、この表と `CLAUDE.md` の表の行が frontmatter と同じことを確かめる。理由を読む人が、実際に動くものを読めるようにするためだ。

The first match in that order determines the outcome, and rule specificity doesn't change the order.」とあるので、allow の `gh api *` があっても ask の `gh api *-X DELETE*` が先に当たる。規則が狙いどおりに当たるかは、`scripts/test-hooks.sh` の `rule` が文書の照らし方(`*` は任意の文字、末尾の ` *` は引数なしにも当たる)をまねて確かめる。この段落と次の段落の deny と ask は、2026年11月6日に作者が消した(「設定の範囲」の節)。

同じ日の1回目のレビューで、allow の `git push*` と `gh api *` の下では、deny の文字列から漏れた形が黙って通ると分かった(原文は [`docs/audits/raw/20261104-1515-mm-reviewer-a669a95d.md`](audits/raw/20261104-1515-mm-reviewer-a669a95d.md))。`git push -fu`、`--mirror`、`--delete main`、`HEAD:main`、`gh api -X PATCH repos/o/r -f visibility=public`、`gh api -X PUT .../merge`、graphql の mutation がその例だ。文字列の規則ではフラグの束や refspec の意味を読めないので、判定は `guard-prod.sh` に置き、deny は文字列で拾える形の予備として残した。deny の `-f` と `+` は、`fix-f` や `c++fix` のようなブランチ名に当たらないよう、前に空白を置いた形(`git push* -f`、`git push* -f *`、`git push* +*`)にした。allow にしていた `git -c credential.helper= * push*` は消した。真ん中の `*` に `branch -D main` や `-c core.sshCommand=...` が入り、push 以外の git や任意のプログラムまで黙って通すうえ、リポジトリの手順でこの形を使う所は無かった。

本番の D1 のマイグレーションは、`migrations apply --remote`(と `--preview`)のとき、cwd、`cd` と `pushd` の先、作業の木の `server/` にある `migrations/*.sql` を全部読み、注(`--` から行末まで、`/* */`。`'--'` のような文字列の中の記号は注と見なさない)を外してから DROP、DELETE、TRUNCATE の語を探し、当たれば聞く。どのファイルがまだ流れていないかは遠隔にしか分からないので、全部を読む。SQLite で表を作り直すマイグレーション(新しい表を作る、写す、`DROP TABLE` する)は、「マイグレーションは確認なし」と「本番の D1 で DROP を含む SQL は聞く」のどちらにも読めたので、2026年11月4日に聞くほうに決めた。2026年11月4日の時点の `server/migrations/` の3つのファイルは注の中にしか当たる語が無く、聞かれない(`scripts/test-hooks.sh` で確かめている)。`server/package.json` に本番のマイグレーションを流す npm のスクリプトは無いので、`npm run` の中身は見ていない。足すときは同じ判定を掛ける。

### permissions の deny と ask を消した

2026年11月6日に作者が、`.claude/settings.json` の `permissions.deny`(38件)と `permissions.ask`(10件)を消すと決めた。作者の言葉は「拒否ルール＋確認ルールはけしましょう。開発なので全部許可する。なのでふつうに消す。これまでの経験上本当にヤバいのは Automode がいい感じに拒否してくれたから」。フックをどうするかを聞くと、作者は「フックは残す」を選んだ。失格を防ぐ関門(`guard-prior-work.sh`)、公開の前の個人の情報の関門(`guard-private.sh`)、マージの関門、`guard-prod.sh` が聞く本番の削除は今までどおり動く。`allow` はそのまま残した。

フックで止まるものは、規則を消しても同じに止まる。permissions の文書に「A hook that exits with code 2 stops the tool call before permission rules are evaluated, so the block applies even when an allow rule would otherwise let the call proceed.」とあり、force push が allow の `git push*` に当たっても `guard-prod.sh` が先に止める。消した規則のうち、フックが同じものを止めるのは次のとおりで、`scripts/test-hooks.sh` で1つずつ確かめている。

- force push(`--force`、`-f`、`+` の refspec、`git -c ... push` の形)と `git push --mirror` は `guard-prod.sh` が止める
- wrangler の削除系(`delete`、`d1 delete`、`queues delete`、`r2 bucket delete`)と D1 の time-travel の restore は `guard-prod.sh` が止める
- `wrangler secret delete`、`wrangler versions secret delete`、`gh api` の DELETE は `guard-prod.sh` が作者に聞く
- `.dev.vars`(`.dev.vars.example` のほか)、`.p8`、`.p12`、`AuthKey_`、`client_secret*.json`、gh の設定の置き場、`gh auth token`、`security find-*`、環境変数を出すコマンドは `guard-secrets.sh` が止める
- holdout の読み取りは `guard-holdout.sh` が止める

フックが見ないものは、今から auto mode の判定だけに任せる。`git reset --hard`、`gh repo delete`、`gh secret`、`gh repo edit --visibility`、Gmail の送信(`send_message`、`reply`、`forward`)、Gmail のごみ箱と削除と迷惑メールの道具、カレンダーの `delete_event`、Claude Docs の `delete` がそれにあたる。wrangler の認証の置き場は、deny では `~/Library/Preferences/.wrangler/**` 全体だったが、`guard-secrets.sh` は `.wrangler/config` の下しか見ないので、残りは判定に任せる。

allow の規則に当たるものは、判定も通らずにそのまま走る。permission-modes の文書に「Actions matching your allow, ask, or deny rules resolve immediately」とあるためだ。deny を消した直後は、`gh issue delete` が allow の `gh issue *` に、`gh pr merge --admin` が allow の `gh pr *` に当たり、取り消せない Issue の削除が確認も判定も無しに走る形になっていた。同じ2026年11月6日に作者がそれを聞かれ、「許可の一覧から外す」を選んだ。deny と ask は足さず、allow の2つをサブコマンドごとの規則に分けた。`gh issue` は `create`、`view`、`list`、`comment`、`edit`、`close`、`reopen`、`develop`、`status`、`gh pr` は `create`、`view`、`list`、`comment`、`edit`、`checks`、`ready`、`diff`、`status`、`close`、`reopen` で、作業の流れで使う書き込みは今までどおり確認なしに走る。`--admin` だけを外す書き方は無い。permissions の文書の「The `*` stands in for whatever text is in its place.」のとおり `*` は `--admin` を含むどんな文字にも当たり、allow の規則に打ち消しの形も無いので、`gh pr merge` は allow から丸ごと外した。マージは今、マージの関門(`guard-merge.sh`)を通ったあとに auto mode の判定を通る。`gh issue delete`、`transfer`、`gh pr checkout` のような一覧の外のサブコマンドも判定に回る。`scripts/test-hooks.sh` の `rule allow` と `rule none` が、ふだんの書き込みが allow に当たり、削除とマージが当たらないことを固定している。

PR #157 の1回目のレビューで、同じ種類の穴があと2つ見つかった。allow の `gh pr close *` は `--delete-branch` で遠隔のブランチを消し、`gh project *` は `gh project delete`、`item-delete`、`field-delete` で板や項目を消す。主が `guard-prod.sh` に流すと、どちらも exit 0 で通った。取り消せない削除が判定なしに走るという、作者が `gh issue delete` を外した理由と同じで、外すのは許可を狭める側なので、作者に聞き直さずに主が外すと決めた(2026年11月6日)。`gh pr close` は allow から外した。skill とエージェントの手順では使っていない。`gh project` は、[`scripts/board.sh`](../scripts/board.sh) が使う `list`、`view`、`field-list`、`item-list`、`item-add`、`item-edit` の6つだけを残した。`scripts/board.sh` の中で走る gh は permissions の規則に照らされない。規則が見るのは Claude が流すコマンドだけなので、この6つの規則が効くのは、Claude が `gh project` を直に流すときになる。

文書の勧めとは外れる。permissions の文書は秘密のファイルについて「To block Claude's file tools from reading a file or directory, add a `Read` deny rule for its path」と書き、settings-reference も `permissions.deny` を「Block listed tool uses, including reads of files that hold secrets」と説明する。ここでは作者の決めたとおり deny を置かず、`guard-secrets.sh` に任せた。このフックは Read、Grep、Glob、Bash、Monitor、Edit、Write、NotebookEdit、WebFetch の実行の前に動き、終了コード2で止めるので、deny と同じく allow より先に効く。文書が「To run all Bash commands without prompts except for a few you want blocked, add `"Bash"` to your allow list and register a PreToolUse hook that rejects those specific commands.」と書く形に近い。

コミットには `Co-Authored-By: Claude` が付く(`attribution` の設定)。放置したときの要約(`idleCompaction`)は切り、窓の上端近くの自動の要約(1M のモデルで約967K トークン)は安全網として残した。要約の前に `/mm-handoff` で移るのが本筋だからだ。

## 残っている穴

フックはツールの呼び出しの文字列を見て止めるので、Bash から Python や Node のスクリプトがファイルを開く読み方までは止めきれない。OS のレベルで確実に止めるのは Claude Code のサンドボックスだが、`xcodebuild` やシミュレータとの相性を確かめていないので、ハッカソン中は入れていない。秘密は Workers の秘密の置き場を正にし、手元の `.dev.vars` には開発用の値だけを置く。

試験用の例文の置き場と holdout の守りにも、文字列の判定では止めきれない書き方が残っている。`cd eval/cases && cat */a.jsonl` のように移ってからのワイルドカードと、`{dev,x}` のようなブレース展開だ。2026年11月3日のレビューで見つかった。大文字のパス、`eval/cases` の直下のワイルドカード、例文集めの役が置き場と holdout を1行に並べる形は止めている(`scripts/test-hooks.sh`)。わざと崩した書き方をしないと通らないので、サブエージェントには止められた操作を別の書き方で通さないよう指示して補う。

個人の情報の調べは文字だけを見る。画像、PDF、スクリーンショットの中の文字は調べないので、`docs/screenshots/` に置く画面は、本番の家族に入っていない端末で、`-mimamori-stub` の作り物のデータを出して撮る(体験用の家族はまだ無い。「設定の範囲」と `/mm-ios-verify`)。確かめのために撮る画面は scratchpad に置き、`docs/screenshots/` には入れない。`gh api` で書く Issue やコメントも `guard-private.sh` を通らない。Issue、PR、コメントの本文は `gh issue` と `gh pr` で書き、`gh api` では書かない(CLAUDE.md の「データと安全」)。マージの関門も `gh pr merge` しか見ない。`gh api` の書き込み(PUT でのマージも含む)と main への push は、`guard-prod.sh` が読める形なら作者に聞く。読み切れない形は聞く側に倒すが、次の段落の穴が残る。Claude Code は permissions の規則を照らす前に `timeout`、`time`、`nice`、`nohup`、`stdbuf`、`command`、`builtin`、`noglob`、フラグの無い `xargs` を外す([permissions](https://code.claude.com/docs/en/permissions) の「Wrappers」)。外さないと `timeout 60 git push -fu origin main` が allow の `git push*` に当たり、フックも見ないまま通っていた(2026年11月4日の2回目のレビューで分かった)。今は `lib.sh` の `command_starts` が同じものを読み飛ばすので、`guard-prod.sh`、`guard-merge.sh`、`guard-private.sh` の3つともラッパーの奥の git と gh を見る。`command -v` と `command -V` は引くだけなので外さない。`env git`、`env gh`、フラグの付いた `xargs`(`xargs -n1 gh ...`)は、文書のとおり規則の側でも外れず `env` や `xargs` のコマンドとして照らされる。このリポジトリの allow には当たらないので、手動のモードなら確認が出る(auto mode では分類器が見る)。関門はこの形の奥を見ない。フラグの無い `xargs` は規則の側で外れるので、その奥の git push と `gh api` は、標準入力から何が足されるか読めないとして `guard-prod.sh` が聞く。その奥の Issue と PR の書き込みは `guard-private.sh` が、マージは `guard-merge.sh` が止める。refspec を省くか `HEAD` の push で、前に `(`、`)`、`cd -`、`cd --`、`popd`、変数を含む `cd` があるときは、最後の `cd` の先を追わず、セッションの cwd と全部の `cd` と `pushd` の先のどれかが main なら聞く。

それでも残る穴がある。`git --git-dir=<main の checkout>/.git push origin HEAD` と `GIT_DIR=<main の checkout>/.git git push origin HEAD` は、作業の木から流すと main を push するのに、フックは作業の木のブランチを見て黙って通す(2026年11月4日に `guard-prod.sh` に流して確かめた)。`git config alias.p push` のような git の別名と、`bash -c "git push ..."` の中の push も見分けない。これらは作業の流れの決まりと auto mode の判定だけが止めている。2026年11月5日までは deny の文字列(`--force`、` -f`、` +`)がこの形の一部を拾っていたが、2026年11月6日に deny を消した。GitHub の側の守りも今は無い。非公開のリポジトリでは、ブランチの保護(`gh api repos/sagochiko/mimamori/branches/main/protection`)もルールセット(`gh api repos/sagochiko/mimamori/rulesets`)も「Upgrade to GitHub Pro or make this repository public to enable this feature.」の 403 が返り、使えない(2026年11月4日に API で確かめた)。提出のためにリポジトリを公開したら、main に force push の禁止、ブランチの削除の禁止、PR を必須にするルールセットを入れる。`bash -c` と heredoc の中の gh は、文字の判定で見つけて止めるが、`bash -c "$X"` のように変数で渡す形は見えない。語に分ける処理は `eval`、エイリアス、`$` の付かない `((...))` の中の `<<` を扱わない(`$((1<<2))` は扱う)。
