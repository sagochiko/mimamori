ステータス: 直すべき指摘あり

公開前に直すべきものは1件だけ。Claude の費用に上限が無い件で、コードを変えずに Anthropic Console の利用上限で塞げる。履歴の秘密、ios の鍵、wrangler の設定、ログには、公開を止める問題は見つからなかった。

## 指摘

### 1. 誰でも家族を作って母の役になれ、Claude を回数の上限なく呼べる(公開前に直す)

場所は [`server/src/families.ts`](server/src/families.ts) の `createFamily`(45行目から)、[`server/src/consult.ts`](server/src/consult.ts) の `consultRoute`(474行目から)と `consult`(284〜330行目)、[`server/src/page.ts`](server/src/page.ts) の `pageRoute`(112行目から)、[`server/src/agents.ts`](server/src/agents.ts) の `RESEARCH_BUDGET_CENTS`(75行目、304行目)。

起きること:
- `POST /families` は認証も回数の制限も無く、端末の鍵を返す。続けて `POST /invites` を呼び、別の鍵で `POST /invites/<code>/join` すれば母の役(`protected`)の鍵が手に入る。join の制限は1つのアドレスにつき1分5回(`join-limit.ts`)で、繰り返す妨げにはならない。
- 母の役の鍵があれば、`POST /consult` に台本から外れた文を送るたびに Sonnet が1回呼ばれる。ウェブ検索が1回足されることもあり、画像を付ければさらに高くつく。
- `ExternalBudget`([`server/src/budget.ts`](server/src/budget.ts))は1回の処理の中で外へ出る呼び出しの数を数えるだけだ。メンバーごと、家族ごと、1日ごとの上限はどこにも無い。`daily`、`per day`、`quota` を grep して確かめた。上限があるのは join の書き込み(1日2000)だけだった。
- `POST /page` に怪しい文とそのたび違うドメインを送れば、キューで Haiku の判定が走り、知らせが出ればそのあと Managed Agents の調べも始まる。調べ1回の上限は0.5ドル(`RESEARCH_BUDGET_CENTS`)だが、回数の上限は無い。1時間に1回のまとめは送り元とドメインごとなので、ドメインを変えれば効かない。
- 公開すると、手順がソースから読め、ホストも [`ios/Config/Shared.xcconfig`](ios/Config/Shared.xcconfig) に書いてあるので、この穴を使うのが簡単になる。穴そのものは TestFlight の外部配布の時点からある。
- 副作用として、`POST /families` を大量に叩くと D1 の無料の1日の書き込み上限と、Workers の1日10万リクエストを使い切れる。そうなると母の端末の判定まで止まる。

公開前にやること: 作者が Anthropic Console で、本番の `ANTHROPIC_API_KEY` が属するワークスペースに月の利用上限を入れる。コードを変えずに済む一番速い手で、作者の操作が要る。時間があれば、メンバーごとに1日の `/consult` と `/page` の Claude 呼び出しの回数の上限を D1 で数える(`join_daily` と同じ形)。あわせて `POST /families` にアドレスごとの制限をかける。確かさは高い。コードで経路を追って確かめた。実際の呼び出しはしていない。

### 2. ファイル名と git の時刻に、平日の勤務時間らしい時刻が残る(公開後でよい、作者が判断する)

場所は `docs/audits/` と `docs/audits/raw/` のファイル名で、`20261104-1015-...` のような形。2026年11月2日から6日の平日の、9時半から18時(昼休みを除く)にあたるものが162件中50件ある。`scripts/scan-private.sh history` はファイル名を見ず、history のときは時刻の規則も飛ばす。

ただ、origin/main のコミットの日時にも、平日10時から18時のものが300件ある。git の日時そのものが同じことを明かしているので、ファイル名だけ直しても変わらない。メモリの「作者の操作の時刻をぼかす」に照らして、受け入れるかを作者が決めることになる。履歴の書き換えはしない決まりなので、直すなら今後のファイル名だけになる。確かさは高い(数えた)。

### 3. GitHub 側で公開の直後に入れるもの(公開後すぐ)

`gh api` の読み取りで今の設定を見た。

- `security_and_analysis` は `null` で、private の無料プランなので Secret scanning と push protection はまだ使えていない。公開したら Settings の Code security で、Secret scanning と Push protection が有効かを確かめる。
- main のブランチ保護とルールセットは、今は「Upgrade to GitHub Pro or make this repository public」の403で設定されていない。公開したらすぐ、force push の禁止、削除の禁止、PR を必須にするルールセットを入れる。マージの手順は `gh pr merge --merge` だけなので、必須の承認数は0でもよい。
- Dependabot alerts は無効(`vulnerability-alerts` が404)。`server/package-lock.json` があるので有効にしておくとよい。
- Actions は `enabled: true`、`allowed_actions: all` で、既定の権限は `read`、PR の承認は不可。`.github/workflows` は無い。今は害が無いが、使わないなら Actions を無効にするか、外部からの PR のワークフローに承認を必須にする設定を確かめておく。
- Actions の secrets は0件、environments は0件、webhooks は0件、deploy keys は0件で、残っているものは無い。

- コミットの作者とコミッターのメールは `users.noreply.github.com` と `noreply@github.com` だけだった。
- `.mcp.json` の履歴は公開の URL と `npx` だけだった。

### `scripts/scan-private.sh` が見るもの
[`scripts/scan-private.sh`](scripts/scan-private.sh) は電話番号、メールアドレス、非公開の語の一覧、時刻の4つを見る。秘密の形(API キー、PEM など)は見ない。上の grep がその代わりになる。

`history` のときに見るのは次の4つ。
- 全ブランチの各コミットの追加行と、`--remerge-diff` で取ったマージ自身の行
- コミットメッセージ
- Issue と PR の題、本文、コメント、レビュー
- 行への PR のレビューコメント(`gh api` の読み取り)

見ないのは次の6つ。
- 時刻(history のときは飛ばす)
- ファイル名
- 画像などのバイナリ
- コミットの作者のメール
- 秘密の形
- テストのデータの場所(`server/test/`、`eval/cases/`、`ios/Core/Tests/`、`docs/audits/raw/` など)にある電話番号とメール。非公開の語はここでも見る

非公開の語の一覧が無いときは、電話とメールだけを見たと標準エラーに出し、それでも0で終わる。流すときはその1行が出ていないかを見る。試験の場所の携帯番号は18種類あり、中ほどの4桁はすべて `0000`、`1111`、`1234`、`3333` で、作った番号だった。
