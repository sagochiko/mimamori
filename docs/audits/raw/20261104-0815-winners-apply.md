### mimamori との差

mimamori の [`docs/dev-log.md`](~/develop/mimamori/docs/dev-log.md) は、どの記録にも日付、時刻、Issue 番号が付く(見出しは `## 2026年11月3日 22:00 外向きの通信の差し替えが素通りする (#4)` の形)。2026年11月4日の時点で、main に4件、まだマージしていない4本のブランチに5件、計9件ある。細かさは CrossBeam と同じ時刻の単位で、受賞作のどれよりも粗いということはない。提出フォームの「一番詰まった場面」の設問の順に揃えた5段落の型、Claude の提案を採らなかった場面、最後の「使ったのは…」の1行は、どの受賞作にも無かった。ここは変えない。

差は3つある。

1つ目は、記録から証拠へ辿る道が無いこと。Custom Universe は段ごとにコミット番号を書き、ARIA は決定ごとにきっかけの監査へのリンクを置き、Medkit は git log を読ませてから書かせる。mimamori の9件のうち、コミット番号が入っているのは最初の記録の `d52f630` だけで(issue-3 のブランチにあり、main にはまだ無い)、PR 番号は #6 の記録の PR #40 だけだった。運営は深さと実行力を「リポジトリの中まで見て判断する」と説明している(`docs/judging.md` 21行)。記録から PR のレビューと直しのコミットへ1回で飛べれば、試行錯誤の跡を審査員が自分で確かめられる。

2つ目は、見出しの時刻の意味が決まっていないこと。#4 と #5 の見出しはどちらも 22:00 で、作業のコミット(#4 は `506e81a` の21:58、#5 は `8341349` の22:01)を出した直後に書いた時刻だった。詰まった時刻ではない。CrossBeam も書いた時刻だが、「Day 2 EOD wrap-up」と添えて、まとめを書いた時刻だと分かるようにしている。mimamori の記録は出来事を書く形なので、読む人は出来事の時刻だと受け取るはずだ(推測)。

3つ目は、作者自身の声がほとんど無いこと。CrossBeam は作者の一人称で、迷いや疲れまで書く(「Heading to the gym.」「Went to Bed at 5 AM」)。mimamori の記録は Claude が三人称で書き、作者の言葉はパーソナルボイスの記録(#3)の「家族の声は日本語無理そうならやめますか」の1か所だけだった。事実は後からでも git と PR から集め直せるが、作者がその日に何を感じてどう決めたかは、あとで Claude には作れない。提出フォームには感想と改善点を書く設問もある(`.claude/skills/mm-endgame/SKILL.md` の7項目目。設問の原文の出典はリポジトリに無い)。

受賞と記録の関係も書いておく。Medkit は履歴がコミット1件にまとめられ、Wrench Board の main は大会のあとに作り直されているが、それぞれ 4.7 の1位と2位だった。4.6 と 4.7 の公式の発表ページは審査基準を載せていないので、記録がどれだけ点に入ったかは分からない。今の大会は、期間中に作ったものだと分かるようにすることをルールとして求めている(`CLAUDE.md` の「ハッカソンのルール」)。受賞作が記録なしで勝ったことは、記録を減らす理由にならない。

### 1. dev-log を union で併合する

受賞作から出てきた話ではない。記録の書き方を見ていて見つけた。

いま開いている PR のうち4本が `docs/dev-log.md` に記録を足している。#40、#41、#43 の3本はどれもファイルの末尾(main の53行目)に1件以上、#39 は途中に1件だ。scratchpad に複製を取り、`git merge-tree` で issue-6(PR #40)と issue-7(PR #41)を併合すると、`CONFLICT (content): Merge conflict in docs/dev-log.md` で止まった。衝突したのはこの1ファイルだけだった。M1 の主役の PR を1本入れるたびに、残りのブランチで同じ衝突を手で解くことになる。作者のいない `mm-autopilot` の途中なら、そこで詰まるか、解き方を誤って記録を落とすおそれがある。

git に組み込みの union の併合を使うと、両側の行を足し合わせて衝突しない。複製で3通り試した。

| 置き方 | 結果 |
|---|---|
| 本体の `.git/info/attributes` に `docs/dev-log.md merge=union`、worktree の中で併合 | 衝突せず、#7 と #6 の記録が両方残った |
| `.gitattributes` を今いるブランチにコミットしてから併合 | 衝突しない |
| `.gitattributes` を取り込む側(main に当たる側)にだけ置いて併合 | 衝突する |

なので、すでに開いている4本には、本体のフォルダの `.git/info/attributes` に1行置くのが早い。worktree はこのファイルを本体と共有するので(`git rev-parse --git-path info/attributes` は本体の `.git/info/attributes` を指した)、`.claude/worktrees/` の5本すべてに効く。リポジトリの中身は変わらず、PR も要らない。そのうえで、次のハーネスの PR で `.gitattributes` にも同じ1行を入れ、これから切るブランチとクラウドのセッションにも効かせる。

気をつけることが2つある。union は両側を足すだけなので、同じ既存の記録を2本のブランチで別々に直すと、行が二重に残る。もう1つ、試した結果では前の記録の最後の行と次の見出しのあいだに空行が入らなかった。GitHub の Markdown の API で同じ形を描かせると見出しとして出たので、表示は崩れない。

M1 より先にやる理由は、主役の一続きの PR(#40 の規則、#41 の判定と知らせ、#43 の引き継ぎ)をマージする道そのものにあるからだ。主役の作業を止めずに、メインのセッションがマージの合間に済ませられる。

### 2. 記録の終わりにコミットと PR を書く

Custom Universe の段ごとのコミット番号、ARIA の Trigger のリンク、Medkit の「use `git log` to ground the entry in real commits」を合わせた形にする。`mm-devlog` の手本の最後の段落を「使ったのは mm-implementer、mm-verifier、guard-prod フック。コミット `abc1234`、PR #12。」のように終え、本文に1文足す。案は次のとおり。

```markdown
End the last paragraph with the commits and the PR that carry the change, found with `git log` and `gh pr list`. The time in the heading is when the entry was written; if the problem happened earlier, say when in the first paragraph.
```

`docs/dev-log.md` の冒頭の説明にも「見出しの時刻は記録を書いた時刻」と1文足す。既存の9件には、見出しや本文を書き換えずに、最後にコミットと PR を足すだけにする。Medkit のコマンドが「Do not rewrite past entries」と決めているのと同じで、過去の記録は当時のまま残す。コミットは `git log --all -S'<本文の語>'` で、PR は `gh pr list --state all --search` で引ける。

効果は2つある。審査員が記録から PR のレビューのコメントと直しのコミットへ1回で飛べるので、深さと実行力の「試行錯誤の跡」と、活用の「Claude Code を開発の中心に据え」を自分で確かめられる。採点役が2026年11月3日 23:40 に「来歴の危うさ」として挙げた、期間中に作ったと分かる記録の弱さにも答えられる(`docs/audits/2026-11-03-2340-judge-harness.md`)。

PR #38 が `mm-task` と `docs/harness.md` を大きく変えているので、そのマージのあとに出すと衝突しない。11月5日の朝の最初のハーネスの PR に入れる。

### 3. 作者のその日のひとことを残す

CrossBeam の `progress.md` の強さは、作者がその場で書いた一人称の声にある。mimamori で同じことを作者に毎回やってもらう余裕は無いので、1日の終わりに1〜3文だけ、作者の言葉をそのまま残す形にする。メインのセッションがその日の終わりに AskUserQuestion で聞き、作者の答えをそのまま引き、Claude はその日の事実(マージした PR、dev の精度、詰まった記録の数)を1行添える。見出しは `## 2026年11月4日 23:30 その日のひとこと` のように、5段落の記録と分けて書く。

事実は後から git と PR で集め直せるが、その日の迷いや決めた理由は作者にしか書けず、11月8日には薄れている。`mm-devlog` の説明にも「memory fades by Sunday」とある。仕上げで書く提出フォームの感想は、ここから拾える。

作者の時間を1日2〜3分使うので、要らなければやらなくてよい。家族の名前や相談の中身を書かない決まりは、ほかの記録と同じ。

### 4. README の Claude の節を仕組みと証拠の組で書く

README に Claude の使い方の節を置くことは、`mm-endgame` の5項目目と計画のタスク16にすでにある。受賞作から足すのは3点だ。

1点目は、仕組みの1つずつに、それが失敗を捕まえた跡のリンクを添えること。Tekton の「How We Used Agents」が、仕組みの説明と失敗した報告の置き場を並べて見せているのにならう。mimamori なら、PR #33 でレビューが3回まわって指摘ごとに直しのコミットが付いたこと(採点役の報告による)、フックが止めた回数(`docs/claude-usage.md`)、`eval/RESULTS.md` の精度の推移、dev-log の記録が材料になる。作品の決まりと作る過程の決まりを揃えた話も書ける。作品はメールや SMS の中の「家族に知らせないで」に従わず、作る過程でも Claude は例文の中の指示に従わない(`CLAUDE.md` の「データと安全」)。作品は「安全です」と返さず、作る過程では Stop のフックがテストを流すまで「直りました」と言わせない。

2点目は、日ごとの表を付けること。日付ごとのコミット数、マージした PR、dev の精度を、`git log`、`gh pr list`、`eval/RESULTS.md` から作る。CrossBeam の日ごとの節を、事実の側だけ機械で作る形だ。期間中に作ったことが一目で分かる。

3点目は、動画のリンクを README の冒頭に置くこと。TARA は16行目にサムネイル、Wrench Board は27行目に「Demo video (3 min)」の1行を置いている。運営は動画を作ったものを伝える「唯一と言って過言ではない」手段だと話しているので(`docs/judging.md` 21行)、リポジトリから入った審査員も動画へ1回で行けるようにする。`mm-endgame` の README の項目には動画のリンクが入っていないので、1行足す。

コードは11月7日で止まるが、README は文書なので11月7日の夜に下書きし、動画のリンクだけ11月8日に入れる。

### 5. テストの関門が止めた回数を分けて数える

Tekton は失敗した検証の報告を残し、それを「the system catching itself」の証拠として見せた。mimamori では `stop-gate.sh` がテストの失敗で応答を止めたとき、`log_event gate stop-gate "tests failed"` を記録する。ところが [`scripts/usage-report.sh`](~/develop/mimamori/scripts/usage-report.sh) は名前だけで数えるので、通したときの `passed` と止めたときが同じ `stop-gate` の行にまとまる(PR #38 の版でも同じ)。記録の `.claude/logs/usage.jsonl`(134行、最後は2026年11月3日 15:42 UTC)には、まだ関門の記録が1件も無い。理由は確かめていないが、監査役が挙げ PR #38 で直している「関門が作業中の worktree を見ていない」件が関係していそうだ(推測)。

PR #38 が入ったあと、集計の関門の表を detail で分け、止めた回数を1行で出す。10分で済むが、審査員がここまで読むかは分からないので、5つの中で一番後ろにする。
