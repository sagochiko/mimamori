## 指摘

1. 新しく足した「安全」の網で「〜から」が素通りし、言い換えの形も拾えない。確度は高い(手元で正規表現を実際に流した)。
   場所は `server/src/claude.ts` の78〜79行の `SOUNDS_SAFE`。足した形は `大丈夫です(?!か)`、`詐欺(では|じゃ)(ありません|ない(?!か))`、`危険(は)?(ありません|ない(?!か))`、`心配いらない(?!か)` の4つ。どれも先読みの `(?!か)` で問いの「か」を除いているが、これだと「から」の「か」でも外れる。このブランチの正規表現を node で流すと、次の文はすべて `miss` になった。
   ```text
   miss 大丈夫ですから安心して
   miss 詐欺ではないから払ってよい
   miss 危険はないから開いてよい
   miss 心配いらないから
   miss 大丈夫だと思います
   miss 大丈夫でしょう
   miss 詐欺ではなさそう
   miss 危険性はありません
   ```
   実際にはこう起きる。2段階の SMS に Claude が `reasons: ["本物の銀行の番号なので大丈夫だと思います"]` か `["詐欺ではないから急がなくてよい"]` を返すと、`decide`(`claude.ts` 193行)がその理由を残す。`toMother`(`server/src/judge.ts` 228行)は電話番号も URL も含まない最初の理由を選ぶので、この一文がそのまま母の通知の本文になり、家族のカードにも載る。`message_to_protected` も同じ網(`claude.ts` 135行)しか通らない。「どの経路でも安全と返さない」という約束に反する。
   `server/src/consult-judge.ts` の117行からの `REASSURING` には、語幹で取る `(大丈夫|安心|平気|本物)(?!か)` と `詐欺(では|じゃ)(な|あり)` がすでにある。直すなら判定の側でもこれを使うか、同じ形にするのがよい。問いを除くなら、`(?!か)` を `(?!か(?!ら))` のような形に変える。`問題ない(?!か)` と `心配ない(?!か)` は main からあったので、同じ「から」の抜けを抱えている。
   試験(`server/test/claude.test.ts` の286行あたりと、`server/test/judge.test.ts` の `expectNothingSaysSafe`)は Issue に挙げた5つの語をそのまま並べただけなので、この抜けでは落ちない。「〜ですから」「〜だと思います」「〜ではないから」の例を、落ちる側に足してほしい。

## 確かめて問題なかったこと

- (2) まとめの条件に `protected_notified_at IS NOT NULL` を足した変更(`server/src/judge.ts` 405〜407行)。`tellMother` は送る前に印を立て、届かなかったときだけ戻す(250〜269行)。母の端末が無いときは印を残して true を返す。送っている途中の行は数えられる側に入るので、同じ束の中で二重には送らない。APNs が 410 か `Unregistered` を返すとトークンを消すので(`server/src/push.ts` 139行)、母の通知が永久に届かずまとめが永久に効かなくなるのは、APNs が 410 以外で落ち続けるときに限られる。PR の「受け入れたこと」に書いた代償の範囲に収まっている。試験2件は、届かなかった行を数えないことと、端末の無い母は届いたとみなすことの両方を見ている。
- (3) [`docs/plan.md`](~/develop/mimamori/.claude/worktrees/issue-53-judge-rest/docs/plan.md) のタスク6に足した2行が、`tellMother` と `family_notice_claimed_at` の実際の動きと合っている。
- (6) 枠の試験2件。14件目の試験は、仕事1件につき Claude 1回、母1台、家族1台の3枚で、40枚のうち13件で39枚を使い、残りが1枚になるよう組んである。判定の前の確かめ(`judge.ts` 369行の `1 + members.length`)が Claude の分しか数えていなければ14件目で Claude を呼ぶので、試験は落ちうる。再配送の試験も、家族の2台分の枠が無ければ `openCase` を呼ばないことを見ている。
- (7) `dedupeDigest`(`server/src/secretbox.ts` 41〜74行)は、HKDF の info で用途を分けて HMAC-SHA256 を取る。AES の鍵とは導き方が違うので、どちらかの鍵でもう一方の役は果たせない。`TOKEN_ENC_KEY` は `server/wrangler.jsonc` 47行の `secrets.required` に入っているので、本番で鍵なしに戻ることはない。`sender_key` と `domain_key` を使っているのは `judge.ts` だけで、ほかに同じハッシュを計算している所は無い(grep で確かめた)。鍵が変わった直後の1時間に二重の知らせが出うる件は、PR に書いてある。
- 試験が自分の mock を確かめているだけ、という形は見当たらなかった。鍵つきの試験は、鍵なしの SHA-256 を試験の中で計算して比べ、別の鍵では値が変わることも見ている。
- `npx vitest run test/judge.test.ts test/claude.test.ts` は `223 passed` だった。
- ハッカソンと個人の情報のルール。試験の電話番号は架空の形で、秘密の値も外から写したコードも入っていない。[`docs/dev-log.md`](~/develop/mimamori/.claude/worktrees/issue-53-judge-rest/docs/dev-log.md) に足した節には日付だけがあり、時刻は無い。`ios/Core` には触れていない。
