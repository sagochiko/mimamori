## 指摘

直すべき指摘は無い。`3430c6c` の方針で、ブラウザでは見える本文や URL が text と url の両方から消える形は新しくできていない。

1つだけ控えに残す。これは今回の変更で生まれたものではない(確信は高い)。`<` のあとに英字が来ない形、たとえば `<p>期限 <本日中 https://x.example/pay> です</p>` は、ブラウザだと `<本日中 https://x.example/pay>` がそのまま見える。それでも `/<[^<>]*>/g` が丸ごと消すので、text は `期限 です` になり、url は付かない。`< 1万円 https://... >` も同じだった。main の `/<[^>]*>/g` も2回目と3回目の `dropTags` も、どの `<` もタグの始まりとして読んでいたので、前から同じように消えていた。今回の正規表現が消す範囲は、main より狭くなっている。URL を山かっこで囲む `<https://...>` は、ブラウザでもタグとして扱われて見えない。なので実害が出るのは、英字以外で始まる山かっこの中に URL を書いたメールに限られる。この PR を止めるほどではない。

## 確かめて問題なかったこと

- 差分。`dropTags` を消して `htmlToText` を `.replace(/<[^<>]*>/g, " ")` に戻しただけで、`anchorHrefs` と `mailPayload` の、本文に無いリンクを `links` として text に足す処理と `url` を選ぶ処理は変わっていない([`server/src/gmail.ts`](server/src/gmail.ts) の 510〜531行と 707〜726行)。
- 方針の向き。タグを消す範囲は、ブラウザがタグとみなす範囲より広くならない。どちらも同じ `<` から始まり、こちらは引用符の中でも最初の `>` で閉じるので、ブラウザより先か同じ位置で終わるためだ(上の英字以外の場合を除く)。残る文字が増える向きにしか外れない。
- 本物の `mailPayload` に `tsx` で当てた結果。どの形でも本文と URL が残った。
  - 3回目の指摘の形 `<p =">…</p><p>">` と `<span a=b="></span><div>…</div><span c=">">` は、text が `未納 https://x.example/pay`、url も同じ。
  - 2回目の指摘の形 `<a title="1<2" href=…>` と `<a data-x="<b>" href=…>` は、属性の残りの文字(`<a title="1` など)が text に混ざるが、`お支払い`、`本日中`、URL は残り、url も付く。
  - `<p class=Don't>`、閉じない `<`、`<!-- -->` の中のタグ、`&lt;b&gt;` は、どれも本文と URL が残った(コメントの中の文字は残りすぎる向き)。
  - `<p title="a>b https://y.example/z">` は、属性の中の URL が text に残り、url にもなった。
  - `<style>İİ</style>`(2回目の `dropBlocks` の指摘)は、閉じタグが元のメールの中で見つかり、本文が残った。
- 時間。`<` を200,000個、`<a ` を50,000個、`<p ="> ` を50,000個並べても、それぞれ 21ms、25ms、28ms で終わり、線形のままだった。`<` を並べた例で url が付かないのは、`JUDGE_TEXT_MAX_CHARS` の切り詰めで後ろが落ちるためで、main でも同じ。
- テスト。`vitest run test/gmail.test.ts` は 102件すべて通った。新しい `it.each` の5件は text に本文と URL があることに加え、`payload.url` も確かめている。古い `not.toMatch(/title=|data-x=|href=/)` を外したのは、方針で受け入れた属性の文字の残りに合わせたもので、リンクと本文の確かめは残っている。
- eval。dev の gmail の見逃しは 0/8、誤報は 0/8 のままで、[`eval/RESULTS.md`](eval/RESULTS.md) の行と [`eval/results.jsonl`](eval/results.jsonl) の数が合っている。
