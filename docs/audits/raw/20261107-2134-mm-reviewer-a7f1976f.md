## 指摘

1. 長すぎる理由を網より先に落とすので、画像の相談で網が穴になる(確度は高い。仕組みはコードで確かめた。実際にどれくらい起きるかは中くらい)

   場所は [`server/src/consult-judge.ts`](server/src/consult-judge.ts) の706行の `reasons: (reasons as string[]).filter((r) => chars(r) <= REASON_MAX_CHARS)` と、1388〜1390行の `claudeLines`。

   画像の相談で Claude が kind help と答えたとき、`decidePlan` は `[claude.action, ...claude.reasons, claude.topic]` に案内しない話題の網(`SENSITIVE`)と `CONTACT` を当てる。PR #186 の1回目のレビューで入った網で、詐欺のスクショを Claude がスマホの困りごとと取り違えたときに、案内を読ませず家族に回すためのもの。今回の変更で、40字を超える理由は網に当たる前に `readClaudeConsult` で消えるようになった。

   こういう場面で起きる。母が銀行を名乗る SMS のスクショを言葉なしで送る。Claude は kind help、level 3、handoff false と答え、理由に「画面のメッセージは銀行を名乗り、リンクから暗証番号の入力を求めている内容です」(40字超え)を、action に網に掛からない設定の手順を書く。
   - 前は理由が長すぎて答え全体を捨てていた。`unanswered` になり、2段階の `UNANSWERED_REPLY` で家族に知らせが行った
   - 今は理由だけが消える。`guided` も `aboutContact` も立たず、`claude.action` が母に読まれ、`record: true` のまま家族には知らせが行かない

   `askedEarlier` のときの `guidedLines` と `guidesContact(claudeLines, claudeLines.slice(0, 1 + claude.reasons.length))` も、同じく消えたあとの理由しか見ていない。出力のスキーマ(355行あたり)に `maxLength` が無いので、40字を超える理由は実際に返りうる。eval で答えを捨てたのが17件に増えたのも、そのためだと読める。

   直し方の案は2つある。消す前の理由を網用に別に持ち、`claudeLines` に入れる。または、長すぎる理由を落とすのはカードに出すところ(`cardReasons`)と `decide` に渡すところだけにし、網は元の文に当てる。テストには「画像、help、40字を超える理由に暗証番号やリンク、action は無害」の組を足し、家族に回ることを確かめてほしい。

2. `requestClaudeConsult` と `requestClaudeJudgment` が、説明にある「Never throws」を守らなくなった(確度は高い。本番への影響は無い)

   場所は [`server/src/consult-judge.ts`](server/src/consult-judge.ts) の772〜773行と、[`server/src/claude.ts`](server/src/claude.ts) の435〜436行。
   - `body.stop_reason` と `body.content?.find` を `try` の外に出した。このため、応答の本文が JSON の `null` だったとき、`content` が配列でないときに TypeError がそのまま上がる。前は `try` の中にあり、null を返していた
   - 本番の呼び出し元は2つとも包んでいて、規則だけで答える。[`server/src/consult.ts`](server/src/consult.ts) の311〜315行と、[`server/src/judge.ts`](server/src/judge.ts) の420〜422行の `try/catch` で見た
   - eval の `loadJudge` と `loadConsultJudge` は包んでいない。妙な応答が1つ来ると、測定がまるごと落ちる

   `body` の形を確かめる部分を `try` の中に戻すか、`typeof body !== "object" || body === null` のとき `fail("no_text")` にすればよい。

3. 失敗の名前の取り次ぎを確かめるテストが、自分で呼んだ偽物を見ている(確度は中くらい。軽い)

   [`server/test/eval.test.ts`](server/test/eval.test.ts) の418行と431行の2件は、偽物が自分で `onFailure` を呼び、それが `claude_parse_failure` に載るかを見ている。`judgeCases` と `claudeJudge` の配線は確かめられる。一方、`requestClaudeConsult` と `requestClaudeJudgment` が `http`、`stop_reason`、`no_text`、`json`、`network` を正しく名付けるかを msw で確かめるテストは無い。eval の記録の材料になる部分なので、少なくとも `json` と `http` は1件ずつ欲しい。

## 確かめて問題なかったこと

- kind scam で action が空の答えは、1段階と2段階では決まった文だけになり、Claude の action は読まれない(1531〜1543行の `!unanswered && level <= 2` と、手前の `sensitive || handoff` の枝)
  - 3段階では `lowConcernWords` が空の行を落とし、決まった1行が必ず最後に付く。母に空の文が届く道は無い
  - `pointsAtNothing` と画像だけの枝でも決まった文になる
- `kind === "help"` の `firstAnswer` と `!usable(claude.action)` の枝は、scam が1544行で先に返すので届かない
- 長すぎる basis を空にしても、basis を読むのは `lowConcernWords` だけ。そこには `usable`、`talksJudgment`、`LEADS_TO_ACT`、`CONTACT`、`SENSITIVE` の網がそのまま当たる。「安全です」に近い文や判定の言葉が通る新しい道は無い。`summaryOf` は basis を使わない
- 理由を落として空の配列になっても、家族のカードは空にならない
  - 判定キューは [`server/src/claude.ts`](server/src/claude.ts) 265〜266行の `decide` が、規則の理由か `PLACEHOLDER_REASON` に戻す
  - 相談は `cardReasons` が規則の理由か `PLACEHOLDER_REASON` に戻す
  - 前から `reasons: []` は受け取っていたので、空のカードになる新しい道ではない
- 段階が軽くなる側を見た。前は捨てて家族に回っていた3段階の答え(理由か basis が長すぎるもの)が、今は3段階として受け取られる。ただ、注入された文で同じ答えを短い理由で書かせれば前から通っていたので、注入で新しく得をする道ではない。`injection_suspected` と規則の床(`keepsOut`、`decide` の `injected`)は変わっていない
- 失敗の名前は決まった列挙(`JudgmentParseFailure`、`ParseFailure`)だけで、Claude の文、母の言葉、例文の中身は入らない
  - `eval/out` の `claude_parse_failure` と、`run.ts` の要約の行の数え上げで見た
  - [`eval/results.jsonl`](eval/results.jsonl) に足した行にも名前しか無い。`claude_unanswered` の数だけだった
- 本番の呼び方は変わっていない。新しい引数はどちらも末尾の省略できる引数で、`server/src/consult.ts` 146行と `server/src/judge.ts` 79行は渡していない
- 届いた本文からは、通知先と共有の範囲に触れる道が無い
- 秘密、家族の情報、外から写したものは差分に無い
- `ios/Core` は変わっていない
- `npx vitest run test/claude.test.ts test/consult.test.ts test/eval.test.ts` は `Test Files 3 passed (3)`、`Tests 1007 passed (1007)` だった
- 注意が1つある。[`docs/plan.md`](docs/plan.md) 137行は判定の形を「各40字以内」と書いている。今回は受け取ってから40字を超えるものを落とすので、渡す側の約束としては守られている。ただ「答え全体を捨てる」から「その理由だけ落とす」に変わったことは、plan にも design にも書かれていない
