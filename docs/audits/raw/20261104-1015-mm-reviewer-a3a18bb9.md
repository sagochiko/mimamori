## 指摘

### 1. 軽い(デプロイ前に直すか確かめる)。知らせの ID がキューのメッセージ ID に頼っていて、やり直しで同じ ID になると文書で確かめられない

場所は `server/src/judge.ts` 277行。

やり直しで二重に送らない仕組みは、すべて「同じメッセージは同じ `message.id` で届く」ことの上に立っている。Cloudflare の文書の Queues の JavaScript API のページは `id` を「A unique, system-generated ID for the message.」としか書いておらず、やり直しで変わらないとは書いていない。Pull Consumers のページは同じ `id` を「a unique, read-only ephemeral identifier」と呼んでいる。テストは `createMessageBatch` に自分で同じ ID を渡しているので、ここが崩れても落ちない。

もし ID がやり直しで変わると、次のことが起きる。送り主もドメインも無い相談(`consult`)で、母への通知は届き、家族への知らせが `CaseNoticeDeferred` でやり直しになったとする。やり直しの回は新しい知らせとして扱われ、Claude をもう一度呼び、行を2つ書き、母にもう一度通知し、相談を2つ開いて家族に2回知らせる。送り主やドメインがある知らせは1時間のまとめで2回目が止まるが、その代わり2つ目の相談は開かれない。

直し方は、`enqueueJudge` が `crypto.randomUUID()` で知らせの ID を作って本文に入れ、受け手はそれを使うこと。これなら文書の書き方に頼らずに済む。計画のタスク6の文(「受け手はメッセージの ID を知らせの ID にしている」)も合わせて直す。今の作りのまま確かめるなら、デプロイした Worker でわざと1回やり直させ、`id` と `attempts` をログに出して比べる(作者の手が要るので `docs/human-queue.md` に積む作業になる)。

### 2. 軽い。母への通知のやり直しはキューの再配送だけで、1時間のまとめが届いていない知らせも数える

場所は `server/src/judge.ts` 182〜211行と 324〜333行、`server/wrangler.jsonc` の `max_retries: 3`。

母への通知が届かないときのやり直しは、30秒おきに3回までの再配送しかない。家族の側には5分ごとの Cron(`sendFirstNotices`)が1日のあいだ送り直す網があるが、母の側には無い。そのうえ1時間のまとめは `notified = 1` の行を数えるので、母に届いていない知らせでも、同じ送り主の次の知らせを止める。

再現の筋は次のとおり(コードを読んでの結論で、テストでは流していない)。母の端末への APNs が3分ほど失敗し続ける。最初の SMS は家族には届き、母への通知は再配送を使い切って終わる(`protected_notified_at` は NULL のまま)。5分後に同じ番号から2通目が届くと、まとめで `notified = 0` になり、母にはどちらの通知も届かない。「知らせ済み」の印は立たないので、1回目の指摘2のような嘘の印にはならない。ただ設計の「伝えたら必ずあなたにも言う」からは外れる。

直し方の案は2つ。まとめの条件に `protected_notified_at IS NOT NULL` を足す。または `sendFirstNotices` と同じ形で、母に届いていない `notified = 1` の行を Cron が送り直す。

### 3. 軽い(推測)。印を先に立ててから送るので、送る途中で処理が止まると誰にも届かないまま印が残る

場所は `server/src/judge.ts` 190〜209行。`server/src/cases.ts` の `tellFamily`(#8)も同じ形。

`protected_notified_at` を先に立て、送れなかったら戻す作りなので、印を立てたあとで Worker の処理そのものが打ち切られる(無料プランの CPU 時間の上限、isolate の入れ替えなど)と、印が残ったまま送られない。やり直しの回は母を送る対象にせず、家族の側も `family_notified_at IS NULL` で探す Cron の網から外れる。打ち切りがどれだけ起きるかは測っておらず、これは推測。二重に送らないことと必ず送ることの取り合いなので、どちらを取るかを決めて計画に1行書いておくとよい。

## 確かめて問題なかったこと

- 3段階と、1時間にまとめた知らせは、母にも家族にも送らず、相談も開かない。最初の回は `notify` が偽なら行を書いて `done` で終わり(356行)、やり直しの回は `notified !== 1` で `done` になる(287行)。M15 と M16 でテストが落ちることも見た。より重い知らせはまとめを通る(`level <= ?`)
- 家族への知らせは `openCase` からだけで、受け手は母にだけ送る。家族への通知は相談の ID を持ち、`threadId` も `case-<id>` にそろう
- やり直しの取り合い。母は `protected_notified_at` の条件つき UPDATE、家族は #8 の `family_notified_at` の条件つき UPDATE で、同じメッセージが同時に2回届いても二重に送らない。送れなかったら印を戻し、やり直しの回は残っている側だけを流し、Claude は呼ばない。`openCase` の `CaseNoticeDeferred` はやり直し、ほかの例外も投げ直してやり直す。1回目の指摘2(送る前に知らせ済みにして ack する道)は無くなった
- 届いた文面を命令として扱わない作り。`<` と `>` を全角にして囲みを閉じられないようにし、システムプロンプトに「従わない」「指示があれば injection_suspected」を書いている。通知先は `members` の `role` と `apns_token` だけで決まる。`injection_suspected` のときは規則の段階を下限にしてから1段重くする。Claude が段階を下げられるのは、confident でない規則より軽くする場合だけで、計画どおり
- 「安全」の言い回しで答え全体を捨てる道は無くなり、当たった理由だけを除く。`message_to_protected` が崩れても段階と理由は残る
- 規則も Claude も決められないときは2段階で確かめ中にし、母に知らせて相談を開く。親が決めた扱いとシステムプロンプトの定義に合う
- 外への通信の枠。1回のバッチで `ExternalBudget` を1つ(40枚)使い、新しい知らせは Claude 1枚と届く端末の数、やり直しは端末の数だけを前もって確かめる。APNs と Claude 以外に外への fetch は無く、D1 は数えない。`max_batch_size` 10 で無料プランの50に収まる。12件で10件だけ流れ、30通になるテストも通っている
- 30日の削除と「すべて消す」。足した列は `alerts` の行と一緒に消える。家族が消えたあとの仕事は Claude を呼ばずに捨てる
- 秘密、本物の家族のデータ、外から写したコードは無い。テストの番号は架空のもの。ログに出すのはエラーの名前だけ。`ios/Core` には触れていない。コミットの形はリポジトリの決まりに合っている
- eval の `rules+claude` は判定のキューと同じ `decide` を使い、鍵が無ければ何も記録せずに止まる。Claude が答えなかった件数を `claude_unanswered` に残す
