## 指摘

### 1. 容量の案内で網を緩めた範囲が広すぎて、「次のページに進んで」「メールの添付を開いて」が丸付きで母に読まれる(確度は高い)

場所は `server/src/consult-judge.ts` の298行から303行(`STORAGE_NAMES` と `guidesContact`)。

`STORAGE_GUIDE` は Claude の案内か理由のどれか1行に「容量」「空き」「ストレージ」があれば当たる。当たると `STORAGE_NAMES` に合う部分を文から消してから `CONTACT` をかける。ところが消す部分に `(前|次|元)の(ページ|画面)` と `(メッセージ|メール)(アプリ)?(の|で)?(添付|書類|データ|容量|写真|ビデオ|ファイル)` が入っているので、行動を促す言い回しまで消えてしまう。同じ正規表現を `node -e` で当ててみた結果を載せる。どの文も、直す前は `CONTACT` に当たっていた。

```text
ストレージを空けるため、次のページに進んで、丸のところの「続ける」を押して → 網に当たらない
容量を空けるため、メールの添付を開いて、案内どおりに進めて           → 網に当たらない
容量不足の解消には、メールのファイルを開いて「実行」を押して           → 網に当たらない
空き容量を増やすには、元のページで「許可」を押して                     → 網に当たらない
容量を空けるため、メッセージで写真を丸の宛先に送って                   → 網に当たらない
容量を空けるため、「メッセージ」を開いて、いちばん上の知らせの手順どおりに進めて → 網に当たらない
```

具体的な場面はこうだ。Safari に出る偽の「ストレージがいっぱいです」の警告ページは、容量の話を装う代表的な手口だ。そのスクショを「これ」と添えて見せたとき、画像の中の文に引かれた Claude が `kind: help`、3段階、`injection_suspected: false` で上の1行目のような案内を返すとする。`decidePlan` はこの網のあと `usable(claude.action)` を見るだけなので、案内の文がそのまま母に読まれ、偽の「続ける」ボタンに丸が付く。3段階なので家族には知らせない。この網はもともと「画像の中の文が Claude の案内を通して母をリンクや入力へ誘うのを止める」ためのもの(design.md の同じ段落)で、そこに穴が開いている。

design.md の書き足しとも食い違う。design.md には「容量の案内でも、SMS、電話、リンク、URL、サイト、ログイン、ページを開く、アプリを入れる、の語があれば今までどおり決まった1行にする」とある。しかし「次のページを開いて」は「次のページ」が消えて「を開いて」だけが残り、網に当たらない。

`consult-image.test.ts` に足した「網を抜けない」側の7件はどれも「このメッセージ」「このページ」のように、消される形に合わない書き方をしている。だから上の形は試験で確かめられていない。

直し方の案を挙げておく。消すのは括弧つきのアプリの名前(`「メッセージ」`、`「メール」`)と、それに続く容量の語(`の(添付|書類)?の?(容量|データ)`)ぐらいに絞り、`(前|次|元)の(ページ|画面)` は消す形から外す。名前を消したあとに `開|進|送|許可|実行` のような動詞が名前と同じ文節に残っていたら、決まった1行にする。上の6文を「決まった1行になる」側の `it.each` に足し、直す前に落ちることを見る。

### 2. 無害な設定の画面の案内が今も決まった1行になる件(守る側に倒れるので、承認は妨げない)

Wi-Fi や文字の大きさの案内は、ふつう `CONTACT` の語を含まないので、そのまま読まれる。ただし「「メール」や「メッセージ」の文字も大きくなります」のように名前が出る案内は、容量の語が無いので今も決まった1行になる。守る側に倒れるので、この PR を止める理由にはならない。

## 確かめて問題なかったこと

- 試験の名前に従って `consult-image.test.ts` を流した。`58 passed` だった。
- `guidesContact` に渡す `guide` は案内と理由だけで、題(`topic`)を含まない。題だけが「ストレージの空きの相談」のときは緩まず、それを確かめる試験もある。容量の案内のときは `ログイン|サインイン` も足して見ている。画像だけの聞き返しの分かれ目(1104行)は今までどおり緩めていない `CONTACT` をかけている。
- `VoiceConsult` の `sentPicture` と `.keepPicture` の順は正しい。`.keepPicture` が出るのは、直前の相談が画像つきで、答えが `ShareConsult.askPicture` のときだけ。その文字列は裏側の `ASK_PICTURE_REPLY` と同じ「この画面で何をしたい?」だ。言葉だけの相談では、同じ文が返っても画像は戻らない(`otherAnswersDropPicture`)。×で外すと、Core の `hasPicture` と App の `attachedPicture` と `attachedImage` が消える。そのあとの言葉だけの送信やマイクの開始で Core の `sentPicture` が false になるので、App が `sentPicture` に古い画像を持っていても欄に戻る道は無い。聞き返しのあとに声で答える経路も試験がある。
- `ChatKeeper.prunePictures` は読み込み、保存、`clear` のたびに走り、どの吹き出しも名指していないファイルを消す。50件(`append` で切れる分)、30日(`restored` で落ちる分)、すべて消す(鍵が消えたときの `chat.clear()` と `forgetIfLeft`)、書きかけの残りがその対象になる。ロック中は画像を書かない。`FilePictureStore` は `.completeFileProtection` と `.atomic` で書き、フォルダとファイルに `isExcludedFromBackup` を付けている。名前は `lastPathComponent` だけを使う。画像の名前だけの吹き出しは `turns` で外れるので、裏側の `history` に空の行は出ない。画像のバイト列は送らない。ログに画像を出すところも見当たらない。
- `MessageField` の `canPerformAction` は、画像があって文字が無いときだけ `true` にし、それ以外は `super` に任せる。`paste` も画像を取らないときは一般のクリップボードで `super.paste` を呼ぶので、文字の貼り付けの経路は変わっていない。ペーストのときに知らせが出るかは実機でしか見られず、PR の「作者に回すこと」に入っている。
- 笑顔の列で `familyPhotos` を使うのは母の画面(`compact: true`)だけ。家族の画面(`FamilyHomeView.swift` 56行の `SmileStrip()`)は今までどおり `photos` を使い、試験でも家族の側は全員分が並ぶことを確かめている。
- 書き換えた既存の試験(`attachedAloneSends`、`pictureSends`、`pictureWithText`、`keepsWordsPictureAndAnswer` など)は、Issue #243 の作者の決定1と2に合わせたもので、ほかの主張は弱めていない。外した `!messages[0].isLocalOnly` も、`history` に母の言葉が入ることを見る主張で代わりに確かめられている。
- 設計と計画の書き足しは、1件目の「ページを開く」の食い違いを除いてコードと合っている(1024ピクセル、品質0.6、300KB、50件と30日、鍵が消えたときに消すこと)。
- `ios/Core` は iOS だけの枠組みを読み込んでいない。描くのと JPEG にするのは App の側(`ConsultPicture.kept()`)でしている。秘密や家族の実際のデータも見当たらない。
- `eval/results.jsonl` の `ts` に時刻が入っているが、前からある行と同じ形なので、この PR の問題ではない。
