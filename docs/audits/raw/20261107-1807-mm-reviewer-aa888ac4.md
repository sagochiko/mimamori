## 指摘

### 1. `<a href>` の正規表現が、前の版で拾えていた押せるリンクを落とす(確信度は高い)

場所は `server/src/gmail.ts` の519行目付近の `/<a\s(?:[^>"']|"[^"]*"|'[^']*')*?(?<=\s)href\s*=\s*["']?(https?:\/\/[^"'\s>]+)/gi`。node で同じ正規表現を流して確かめた。

- `<a/href="https://evil.example/x">` は `[]` になる。HTML の字句解析では、タグ名のあとの `/` は区切りとして読み飛ばされ、`href` は属性になるので押せるリンクだ。新しい形は `<a\s` を求めるので落ちる
- `<a title=it's href="https://evil.example/x">` も `[]` になる。引用符の無い値に `'` が1つ入ると、`'[^']*'` の枝が閉じの引用符を探し続けて合わない。`[^>"']` の枝は `'` を通さないので、そこで全体が外れる。ブラウザでは `it's` はふつうの値で、そのあとの `href` は効く
- `<a x=" href="https://evil.example/x">` のように、前の属性で引用符が対になっていない形も `[]` になる

前の版の `href\s*=\s*...` は、この3つをどれも拾っていた。詐欺の送り手は書き方を1文字変えるだけで済む。HTML だけのメールでは `htmlToText` がタグごと URL を消すので、`payload.url` も本文のリンクも残らない。規則の「名乗る会社と違うドメイン」も似せたドメインの印も付かず、Claude にもリンクが渡らないので、見逃しになる。

直し方は、`<a[\s/]` で始め、引用符の枝が合わないときは1文字ずつ進む枝(`[^>]`)へ戻れるようにし、後ろ読みを `(?<=[\s/"'])` にするのがよいと思う。足す試験は、上の3つの形が `https://evil.example/x` を拾うこと。ほかに、`href=" https://..."` の頭の空白と `&#104;ttps://` の文字参照も前から落ちている(前の版でも拾えない)。ついでに塞ぐかは任せる。

### 2. 待つ受け取りで回数を使うので、最後の受け取りで呼び出しの残りが足りないと、行も知らせも残らず消える(確信度は中くらい)

場所は `server/src/judge.ts` の `judgeOne` の始めにある `if (budget.remaining < 1 + members.length) return "retry";` と、`server/wrangler.jsonc` の26行目 `"max_retries": 3`(行き先のキューは無い)。

Cloudflare の Pull consumers の文書は `attempts` について「When this reaches the value of `max_retries`, the message will not be re-delivered and will be deleted from the queue permanently」と書いている。これに従えば受け取りは3回までで、3回目が最後になる。設計の段落は、この少ないほうの読みでも「3回目で知らせられる」としている。ただ、3回目が上の残りの不足で `retry` を返すと、そのメッセージは黙って消える。`alerts` の行は書かれず、母にも家族にも届かない。前の版は1回目で知らせていたので、残りの不足に3回耐えられた。いまは1回目と2回目を待つのに使うので、余りが無い。

同じ理由で、3回目に知らせた母への push が失敗したとき(`finishNotices` が `retry` を返したとき)も送り直されない。家族の側は `cases.ts` の405行目の cron が送り直すので残る。母の側は待つ前より弱くなった。

起きるのは、1つのバッチに外への呼び出しが40回(`EXTERNAL_CALLS_PER_INVOCATION`)を超えるだけのジョブが入るときだ。メールがまとめて届いて待つジョブが重なると、バッチは前より大きくなりやすい。直し方は、`max_retries` を5くらいに上げて最後の受け取りのあとに1、2回の余りを作るのが一番小さいと思う。設計の「少ないほうの読みでも」の一文も、それに合わせて直すことになる。足す試験は、`attempts` が3で残りが足りないときにどうなるかを決めて確かめるもの。いまは `attempts` が4で決まる試験しか無い。

### 3. 注入の印だけのメールは、待つことで Claude に段階を下げられる場面が増える(確信度は高い。ただ前からある道)

規則は注入の印があると1段階を返す(`server/src/rules/index.ts` の252行目)。この印だけでは `confident` にならないので、この PR では待つ側に入る。`decide`(`server/src/claude.ts` の223行目)が規則の段階を下限にするのは、規則が `confident` のときか、Claude が `injection_suspected` を立てたときだけだ。規則の注入の印は下限にならない。

なので、1回目に Claude が答えず、2回目に注入された文に引かれて `level: 3`、`injection_suspected: false` と答えると、3段階で誰にも知らせずに終わる。前の版なら、1回目の失敗で規則の1段階のまま知らせていた。Claude が1回目から答えれば同じことは前から起きるので、新しい道ではない。ただ PR 本文の「段段階は変わらず上限で知らせる」は、Claude がその後も答えないときにしか当たらない。

`judgeOne` の `steered` は、カードの理由に使うだけで段階を変えない。直すなら、規則の理由に `INJECTION.reason` があるときも `decide` の下限に入れる形になる。この PR で直すか別の Issue にするかは任せる。

### 4. 細かいところ(直さなくてよい)

- 新しい正規表現は、閉じの `>` や引用符が無い入力では長さの2乗の時間がかかる。`"<a '".repeat(32000)` で約480ms かかった(前の版は0.1ms 未満)。ただ同じ入力で、前からある `htmlToText` の `/<[^>]*>/g` も約185ms かかる。HTML だけのメールでは前から同じ種類の危うさがあり、新しく増えたのは、文字だけの部分もあるメールで同じ重さが足されることだ。無料プランの CPU は10ms なので、作った HTML で見張りの tick が毎回落ち、`saveProgress` まで届かずに同じメールで止まり続けうる。直すなら、正規表現に渡す HTML の長さに上限を置くことになる。別の Issue でもよい
- `<area href>` を数えないことを試験で決めている。画像マップは押せるリンクだ。Gmail が `usemap` を通すかは確かめていない

## 確かめて問題なかったこと

- 待つ条件は、`gmail` で、Claude が `null` で、規則が `confident` でなく、段階が2以下で、`attempts < 3` のとき。印はあるが段階の無いものは `decide` で2になるので待つ。印の無いものは `decideFor` で3になるので待たずに終わる(#137 のとおり)。確かな1段階は待たずにすぐ知らせる。SMS とページは条件の外で変わらない。試験(`server/test/judge.test.ts` の1169行目から)もこの分かれ方を確かめている
- 待つ判定は `INSERT` の前にあるので、次の受け取りは `stored` の無い初回として始まり、もう一度 Claude に聞く。同じメッセージが重なって届いても `ON CONFLICT (id) DO NOTHING` と `changes === 0` で二重には知らせない。1時間に1回の重なりは、`notified = 1 AND protected_notified_at IS NOT NULL` の行だけを見るので、待っているあいだのメールは数えられず、前の版と同じ形で効く
- `handleJudgeBatch` は `wait` を `message.retry({ delaySeconds: 120 })` にしている。試験は `retry` の引数を spy で見ているので、間隔を壊せば落ちる。待つあいだの「行が無い、push が無い、`openCase` が無い」も試験で見ている。2回目に Claude が答えたときは `claude_level` が入り、母の文は Claude の理由になる
- 見逃しの側の試験もある。会社の名前と `<link>` の書体だけのメールは、本物の規則でも段階が付かず、3回目でも誰にも知らせない。`<a>` の前に `data-href` があるもの、引用符の中に `>` があるもの、大文字と改行の `<A HREF>` は拾う
- 通知先と共有の範囲は、この差分のどこでも Claude の答えやメールの文で変わらない。待つ分かれ道は段階を下げない(下げうるのは指摘3の、前からある `decide` の道だけ)。「安全です」と返す道も足されていない
- 設計と計画の書き足しは、コードと合っている(120秒、3回目、確かでない1段階も待つ、行を書かない、SMS とページは変えない)。`.claude/rules/server.md` の「規則の判定だけで知らせ」との食い違いは、PR 本文の「残ること」に書いてある
- 秘密の値、実際のメールの中身、外から写したものは差分に無い。試験のメールは作った例(`Made up; no real mail.`)だ。`ios/Core` には触れていない
