## 指摘

de3cfc4 で、1回目に挙げた4つはすべて直っていた。残りは、直さなくてもマージを止めないものが2つだけだ。

1. 名前を崩して書くと、フォルダの規則を抜けられる(確度は高い。正規表現を読んで判断し、試していない。重さは低い)
   - 場所は [`.claude/hooks/guard-secrets.sh`](.claude/hooks/guard-secrets.sh) の `pat` に足した `(^|[[:space:]/~=])\.(mimamori|appstoreconnect)([[:space:]/*?{[]|$)`。
   - `.mimamori` の名前を glob で崩した形(`.mim` に `*` を続けるもの)は抜ける。これは [`docs/harness.md`](docs/harness.md) に「Claude が守る」と書いてある。
   - 文書に書かれていない抜け方も同じ種類で2つある。1つは引用符で包む形(`~/` の直後に `".mimamori"`)で、`.` の前が `"` になるので前の文字の集まりに入らない。もう1つは `.mimamori` の直後にバックスラッシュを置く形で、後ろの文字の集まりに入らない。
   - Grep のツールに `path` で家のフォルダ全体(`~`)を渡す呼び出しも、規則に当たらずに `~/.mimamori/asc/` の下まで読む。これは `.dev.vars` にも前からある、名前で見る関門ならではの穴で、この PR が新しく作ったものではない。
   - わざと名前を崩すのは「別の経路で通さない」の決まりで Claude が守る範囲なので、マージは止めない。直すなら、文書の「名前を崩した glob」を「名前を崩した書き方(glob、引用符、バックスラッシュ)」に広げれば足りる。

2. 1つ目の止まる例は、`np` の確かめを消しても落ちない(確度は高い。重さは低い)
   - 場所は `scripts/test-hooks.sh` の `"the export with the fixed key path twice is blocked"`。
   - 決まった道筋は1回しか取り除かれないので、2回目の道筋の `.mimamori` と `AuthKey_` に `pat` が当たり、`np` が無くても止まる。`np` は二重の守りなので、穴ではない。
   - 一方で `ni` の確かめは、`"the export with a second key ID is blocked"` が守っている。`ni` を消すとこの例は終了コード0になって落ちる。
