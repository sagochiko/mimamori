## 指摘

1. 3段階の Claude の言葉を通す網 `LEADS_TO_ACT` に穴が大きい。また、`CONTACT` の網がこの経路にかかっていない(確度高)
   場所は `~/develop/mimamori/server/src/consult-judge.ts` の `LEADS_TO_ACT`(1440行付近)と `lowConcernWords`(1444行付近)。`lowConcernWords` が当てているのは `usable`、`talksJudgment`、`LEADS_TO_ACT` の3つだけで、`CONTACT`(メール、SMS、メッセージ)も `SENSITIVE` も当てていない。手元で `node -e` を使い、同じ正規表現に NFKC と小文字化をかけて当てた。次の文はどれも `false` になり、網を抜けて母に読み上げられる。
   - `このメールには返事をして確かめてね。`
   - `書いてある窓口に問い合わせて確かめてね。`
   - `amaz0n-help.jp で確かめてね。`
   - `0120-111-222 に連絡して確かめてね。`
   - `LINEで友だち追加して確かめてね。`
   - `差出人に住所と名前を送って確かめてね。`
   - `届いたメールの指示どおりにしてね。`

   起きる場面はこうだ。母が届いた SMS かメールを声で読み上げ、その本文が Claude を「書いてある窓口に問い合わせて」へ誘導する。AI に宛てた文の形をとっていなければ `CONSULT_INJECTION` にも `injection_suspected` にも当たらず、段階は3のまま `reply` に `問い合わせて` や偽のドメインが入る。家族には知らせが行かないので、間で止める人がいない(コメントにある「this net and the fixed line after it are what is left between them」の状況そのもの)。design.md は「迷う形は決まった1行に倒す」としているのに、語の一覧は「連絡」「問い合わせ」「返事」「送」「追加」「指示」「メール」「LINE」と、数字の並びやドメインの形を落としている。直し方の案は2つ。`CONTACT` と数字やドメインの形(`[a-z0-9-]+\.[a-z]{2,}` や数字が3桁以上続く形)を網に足す。または語の一覧ではなく、Claude の行に「確かめる方法」を一切含めない形(basis だけを読む)にする。試験も `it.each` で一覧に入れた語だけを確かめており、上の形が抜けることを試すものが無い(下の3点目)。

2. 出典のホスト名は、網を通したあとに付け足していて、何も確かめていない(確度中、害が出るかは中)
   場所は `~/develop/mimamori/server/src/consult-judge.ts` の `searchReply` の最後の行(`HOST.test(host) ? \`${t}(${host} より)\``)。`HOST` が見るのは形だけなので、引用された先が SEO で上位に来た偽のサイト(例 `iphone-support-jp.top`、`0120xxxxxx.jp`)なら、母に「(iphone-support-jp.top より)」と、開くべきサイトの名前を聞かせることになる。本文ではサイト、URL、番号を網で落としているのに、出典だけがこの網の外にある。公式の「citations must be included」は、出典を付けることを求めているだけで、どのホストを出すかは決めていない。案は2つ。ホストにも `LEADS_TO_ACT` の数字やドメインの扱いと同じ考えを当て、許す一覧(`go.jp`、`jma.go.jp`、`lg.jp` など)に入るときだけ名前を出し、ほかは「(ウェブで調べた結果)」のように出す。または `allowed_domains` で検索先そのものを絞る。

3. 試験が、壊れても落ちない形になっている(確度高)
   - `~/develop/mimamori/server/test/consult.test.ts` の「falls back to the fixed line for a line about %s」で使う15の例文は、どれも一覧に入った語(番号、電話、リンクなど)を含む文だけでできている。たとえば「a number」の例文には「問い合わせ」も入っているが、落ちる理由は「番号」だ。1点目の穴を突く例(連絡、問い合わせ、返事、ドメイン、数字だけ)が無いので、網が狭くても通る。
   - `~/develop/mimamori/server/test/consult-search.test.ts` の「joins the text blocks」は、`server_tool_use` より前に置かれる前置きの text のブロックを再現していない。公式の Web search tool の文書にある応答の例では、`"I'll search for ..."` と `"Based on the search results, "` も text のブロックとして返る。`requestSearchAnswer` はすべての text のブロックをつなぐので、本物の応答では「調べますね。」のような前置きが答えに混ざり、200字を超えれば1回目の答えに戻る。安全の問題ではないが、本物の API ではまだ流していないと PR に書いてあり、試験もこの形を見ていない。直し方は、最初の `web_search_tool_result` より後の text だけを使うか、`citations` の付いたブロックを含む後ろの段落だけを使うこと。

4. お店の営業時間の質問では、検索の答えがほぼ毎回捨てられる(確度高、使い勝手の問題)
   `searchReply` は `LEADS_TO_ACT` を当てるが、その中の `開` と `進` は「10時に開店」「開いています」にも当たる(手元で `本日10時に開店します。` が `true` になった)。design.md と SYSTEM_PROMPT は営業時間を検索の対象の例に挙げているのに、実際は1回目の調べずに言った答えに戻る。検索の答えには「開店」「営業」を外すなどの手当てか、設計の例から外すことが要る。

5. `needs_screen` の聞き返しは `CONTACT` を見ていない(確度中、重さは低)
   場所は `~/develop/mimamori/server/src/consult-judge.ts` の1395〜1407行。条件に `plainLevel3` も `!told.some(CONTACT)` も入っていない。たとえば「知らない番号から SMS で、このアプリを入れてと来た。どうやるの」のように、規則が何も見つけず、Claude が `help`、`needs_screen: true` と答えると、今までの `LOW_CONCERN_ACTION`(「お金や暗証番号を聞かれたら止めて、家族に確かめて」)ではなく「その画面を写真で見せてね」だけが返る。家族に知らせが行かないのはどちらでも同じだが、メッセージの話で止める1行が消える。design.md は、この1行にする条件に「メッセージや電話の話でない」を挙げていない。ただ、firstAnswer の条件とは揃っていない。条件に `!told.some((t) => CONTACT.test(t))` を足せば、今までどおり決まった1行に戻る。

6. 1回目の相談で Claude が `kind: scam`、段階3、`handoff: true` と答えたとき、家族に回らなくなった(確度中、起きる頻度は低い)
   `firstAnswer` は `claude.kind` を見ないので、詐欺の相談で段階3なのに Claude が家族の手を求めた場合も `handoff` が false になり、1457行の段階3の詐欺の枝(Claude の言葉と決まった1行)に入る。#251 の前は `HANDOFF_REPLY` と家族への知らせになっていた。作者が決めた「1回目は AI が答える」は困りごとの相談の話で、詐欺の相談の Claude の handoff まで外すとは書かれていない。見逃しは誤報より重いので、`firstAnswer` の条件に `claude.kind === "help"` を足すのが安全側になる。

## 確かめて問題なかったこと

- Web search tool の API の形を、`claude-docs` の MCP で `/docs/en/agents-and-tools/tool-use/web-search-tool` を開いて確かめた。`web_search_20250305` は今も基本の版としてあり、`claude-sonnet-5-5` は対応モデルに入っている。`name: "web_search"`、`max_uses`、`user_location` の `type: "approximate"`、`country` が2文字の ISO の形、`timezone` が IANA の形、という点も文書と合っている。citations は常に有効で、`web_search_result_location` が `url` を持つこと、`pause_turn`、検索の失敗が 200 の中に入って返ること、料金が1,000回で $10 であることも文書どおりだった。組織の管理者が Console で切っていれば 400 になるが、その場合も `requestSearchAnswer` は `!res.ok` で null を返し、1回目の答えに戻る。
- 15秒の締切の配線(`~/develop/mimamori/server/src/consult.ts`)。`startedAt` は1回目の ask の中で切符を取った直後に入る。`searchTimeLeft` は `CLAUDE_TIMEOUT_MS`(15秒)から1回目にかかった時間を引き、6秒を切れば null を返す。残りは `AbortSignal.timeout(left)` で2回目に渡しており、1回目の始まりから2回目の終わりまでが15秒に収まる。2回目は `judged.toFamily` が false で `record` も false の枝に限られ、知らせを送る処理は後ろに無い。投げられた例外は2か所(consult.ts と judgeConsult)で null にしている。
- 「伝えました」と言ってから知らせが届かない道ができていないか。`stuck` は `handoff` の枝に入り、`toFamily: true` で `HANDOFF_REPLY` を返す。ほかの新しい枝(`ASK_SCREEN_REPLY`、firstAnswer の `ASK_AGAIN_REPLY`、段階3の Claude の言葉)はどれも `toFamily: false` で、家族に知らせたとは言わない。検索の答えにも段階3の Claude の言葉にも `usable`(`TOLD_CLAIM`)が当たっている。
- 偽の AI の行の影響。`aiAnswered` は端末から届く行で決まるが、変わるのは `plainLevel3`(規則が null、段階3、案内しない話題でない、連絡の話でない、警察の話でない)の中で、AI が答えるか家族に回すかだけだった。危ない相談と案内しない話題はこれまでどおりすぐ家族に回る。
- 検索の結果に注入された文の扱い。1回目で `injection_suspected` が立てば `decide` が段階を上げるので、`judged.level !== 3` で検索しない。2回目の答えには、`usable`、`talksJudgment`、`CONTACT`、`LEADS_TO_ACT`、`DELETION`、`SENSITIVE`、200字の上限を当てている。2回目が変えるのは母への答えだけで、段階、知らせる先、記録は変えない(judgeConsult の最後のブロック)。知らせる先と共有の範囲を、モデルの出力で変える道は見つからなかった。
- ページの題(`title`)は読み上げず、引用の `url` からホスト名だけを取っている。`new URL` が失敗したときは null になる。
- 家族のカードと知らせに、母の言葉も届いた文の切り抜きも新しく入っていない。新しい枝は既存の `reasons` と `base` をそのまま使っている。
