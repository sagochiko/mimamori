## 指摘

### 1. `docs/harness.md` の「サブエージェント」が今回の例外と食い違ったまま(確度: 高、文書で見た)

`~/develop/mimamori/docs/harness.md` の79行目は今も「作者のグローバルの決まりは「単純な作業は Sonnet を指定する」なので、そのまま当てると検証役が Opus から、レビュー役が Fable から黙って外れる。`/mm-task` と `/mm-endgame` には、`mm-*` を呼ぶときは model を省くか定義と同じにすると書いた」と書いている。今回の変更で `/mm-task` は「軽い作業は `sonnet` を渡す」になったので、この文は事実と合わない。同じファイルの表(67行目 `mm-verifier`、70行目 `mm-reviewer`)も、Opus と Fable にした理由だけで、軽い作業を Sonnet に回す線は書いていない。

`CLAUDE.md` のこの節は「理由は `docs/harness.md` の「サブエージェント」に書いた」と結び、`harness.md` の3行目はこの文書を審査の「モデルや機能を目的に応じて選び、使い分けているか」に答えるものと位置づけている。`usage-log.sh`(`.claude/hooks/usage-log.sh` 22行目)は Agent 呼び出しの `tool_input.model` を記録するので、`make usage` で作る `docs/claude-usage.md` には Sonnet のレビューが出る。審査員が `harness.md` と使用量の記録を並べて読むと、文書が「Sonnet は使わない」と言い、記録が Sonnet を示す形になる。この PR で `harness.md` の79行目と表の2行に、例外と2026年11月6日の作者の決定を足すべき。

### 2. 「文書の数行の直し」の線が、約束を持つ文書まで含んでしまう(確度: 高、文書で見た)

`CLAUDE.md` の新しい1つ目の項目は、軽い作業を「ビルド番号だけの PR、`docs/audits/raw/` の原文や文書の数行の直し」とし、重いほうを「コード、フック、設定、プロンプト、規則を変える PR」としている。`docs/design.md` と `docs/plan.md` は「文書」だが、段階、「安全です」と言わない約束、誰に知らせるか、30日の削除といったつなぎ目の約束を持つ。`CLAUDE.md`、`CONDITIONS.md`、`.claude/agents/*.md`、`.claude/skills/*` も Markdown で、規則とプロンプトそのものだ。

具体的な場面。`docs/plan.md` の通知先の約束を3行だけ変える PR が出る。親は「文書の数行」と読んで `sonnet` を渡し、設計との食い違いを探す役が Fable から外れる。分類するのは実装を見た親自身なので、独立した目で疑うという `mm-reviewer` の趣旨がそこで抜ける。「数行」は量の基準で、変える中身の基準ではない。

直し方の案。軽い文書を種類で書かず、一覧で書く。ビルド番号の commit、`docs/audits/raw/`、`docs/dev-log.md`、`docs/claude-usage.md` のような日付つきの記録だけを軽いとし、`CLAUDE.md`、`CONDITIONS.md`、`.claude/` 配下、`docs/design.md`、`docs/plan.md`、`eval/` は行数にかかわらず表どおりにすると書く。`SKILL.md` 側の `a few lines of docs` も同じに揃える。

### 3. 続きを頼むと Sonnet のまま残る(確度: 高、公式文書で見た)

code.claude.com の sub-agents の「Choose a model」には `A per-invocation model parameter also applies when the subagent is resumed or sent a follow-up message, so the subagent stays on that model.` とある。`/mm-task` はレビューの2回目以降を SendMessage で同じ `mm-reviewer` に頼み(`docs/harness.md` 30行目の `usage-log.sh` の説明、`SKILL.md` 64行目「After each round」)、検証役も `SKILL.md` 49行目で「verify again」と続ける。

具体的な場面。ビルド番号だけの PR を Sonnet でレビューし、そのあと同じブランチにコードの直しが乗る。2回目を SendMessage で頼むと、PR はもう軽くないのに Sonnet のまま読まれる。`SKILL.md` の43行目に、軽いと見て `sonnet` で始めた役は、PR が軽くなくなったら続きを頼まず `model` 無しで新しく起動する、と1文足すべき。

### 4. 「ビルドが通るか」を Sonnet の確かめに入れると、Opus にした理由と矛盾する(確度: 中、文書で見た)

`CLAUDE.md` の2つ目の項目は「ビルドが通るか」を状態を見るだけの確かめに入れている。`docs/harness.md` 67行目は `mm-verifier` を Opus にした理由を「落ちたテストの原因の行の読み分けが要る」としている。ビルドが落ちたときが、まさにその場面になる。コードの PR の `make verify` を「ビルドが通るか」と読んで `sonnet` を渡す余地がある。Sonnet の確かめはファイルや設定の値を読むものに絞るか、「落ちたら Opus の役を新しく起動して原因を読ませる」と書くか、どちらかにする。レビューと同じく「PR 自体が軽いときだけ」と基準を揃えるのが簡単。

### 5. 3つ目の項目は表の役ではない(確度: 高、文書で見た。文言だけ)

導入の文は「表の役に Sonnet を渡すのは次の軽い作業だけにする」なのに、3つ目の項目は `web-fetch`、`Explore`、`general-purpose` で、表の役ではない。これらは作者のグローバルの決まりがもともと Sonnet にしているものなので、項目を別の文(「表の役でないこれらはグローバルの決まりどおり Sonnet」)に分けると読み違えない。
