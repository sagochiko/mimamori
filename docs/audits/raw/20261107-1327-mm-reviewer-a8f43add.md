PR #236 の目的は「審査員が公開のリポジトリで同じ数を出せる」ことです。ところが、表のコマンドは今の時点でもう表と違う数を返します。マージ後も、コミットやレビューが増えるたびにずれていきます。

## 指摘

### 1. 表のコマンドを流しても表の数は出ない(確度 高)

場所は [`docs/claude-usage.md`](docs/claude-usage.md) の14行目と15行目、[`scripts/usage-report.sh`](scripts/usage-report.sh) の追加部分の最後の2行(`git rev-list ... HEAD`)です。

文書は 730 と 693 と書いています。このブランチの HEAD(`a8834ed`)で同じコマンドを流すと、`731` と `694` が出ました。`scripts/usage-report.sh` は、文書を含むコミットを作る前の HEAD で数えます。そのため、出来上がった文書は必ず1つずれます。worktree で出し直して `diff` を取ると、ずれはこの2行だけでした(ほかに `mm-reviewer` の起動が 189 から 190 に増えていますが、こちらは公開されない記録の数です)。

```text
< | マージを除くコミット | 730 | ...
> | マージを除くコミット | 731 | ...
< | そのうち `Co-Authored-By: Claude` の付いたもの | 693 | ...
> | そのうち `Co-Authored-By: Claude` の付いたもの | 694 | ...
```

`docs/audits/raw/` の件数も同じ形でずれます。`save-report.sh` は、レビュー、審査、監査の報告を返すたびに原文を足します。このレビューでも1件増えます。締切までに件数は増え続け、提出時のクローンで数えると、文書と同じ数にはまず戻りません。そうなると、「同じコマンドを流せば数え直せる」という一文はそのまま偽になります。審査員が流して数が合わなければ、ほかの数まで疑われます。

直し方は、数えたコミットを固定することです。`git rev-parse --short HEAD` を節に書き、コマンドもそのコミットを指す形にします。たとえば `git rev-list --no-merges --count <sha>` や、`git ls-tree --name-only <sha> docs/audits/raw/ | grep -c -- '-mm-reviewer-'` です。PR は `--merge` でマージするので、ハッシュは公開のクローンにも残ります。

### 2. 同じ名前を避けて付く `-2.md` の原文で、役の読み取りが壊れる(確度 高。ただし今は該当するファイルが無い)

場所は [`scripts/usage-report.sh`](scripts/usage-report.sh) の追加部分の `sed -E 's#.*-(mm-[a-z-]+)-[0-9a-f]{8}\.md$#\1#'` の行です。

`save-report.sh` は、同じ分に同じ ID の名前があると `...-<id>-2.md` という名前で保存します。`agent_id` が取れないときは `-noid.md` になります。どちらの名前にも、`sed` の正規表現は当たりません。当たらない行は道筋のまま通り、`read -r n role` の `role` にファイルの道筋がそのまま入ります。手元で `sed` だけを当てて、そうなることを確かめました。

```text
docs/audits/raw/20261107-1216-mm-reviewer-aa8ccd8d-2.md
```

その結果、次の3つが起きます。

- 表に、ファイル名(日付と時分を含む)を役の名前にした行が1行増える。
- `mm-reviewer` の行の数が1つ減る。
- 同じ行に添えた `ls docs/audits/raw/*-mm-reviewer-*.md | wc -l` は `-2.md` も数えるので、表の数とコマンドの数が合わなくなる。

`-[0-9a-f]{8}(-[0-9]+)?\.md$` のように後ろの番号も許すか、`ls` と同じ glob で役ごとに数えると、ずれません。

### 3. 新しい節の試験が無い(確度 高)

[`scripts/test-hooks.sh`](scripts/test-hooks.sh) の1300行目から1323行目にある usage の試験は、日付の行、期間の行、worktree での記録の読み先の3つだけを見ています。新しい節の数は、どの試験にも出てきません。worktree の試験は `$T/wt` に `docs/audits/raw` が無いまま走ります。そのため、`find` が空でも黙って通ります。

試験に足すとよい例は次の3つです。

### 4. 原文の件数と起動の回数の違いの説明が無い(確度 中、軽い)

`mm-reviewer` の原文は 215 件、下の表の起動と再開は 189 回と 21 回で、足すと 210 回です。原文は返された報告の数で、再開ごとにも増えます。一方で、2026年11月4日より前のレビューは原文がありません。読む人は 215 をレビューの回数と受け取りやすく、下の表の数と比べて食い違いに見えます。「報告を返した回数で、記録を始めたのは2026年11月4日」と1文添えると誤読を防げます。数そのものは、ファイルの数として正しいです。

## 確かめて問題なかったこと

- 今の原文の件数。`ls docs/audits/raw/*-mm-{reviewer,judge,auditor}-*.md | wc -l` は 215、6、2 で、表と同じでした。役の名前の形に合わないファイルは `winners-*.md` の3件だけで、`-mm-*-*` の glob にも `find` にも入りません。取りこぼしと数え違いは今はありません。
- 原文は公開のリポジトリに入っている。`git ls-files docs/audits/raw | wc -l` は 226 で、ディレクトリにある数と同じでした。`git check-ignore` にも当たりません。
- `Co-Authored-By: Claude` の数え方。`--grep` に `-i` を付けても付けなくても 694 で、大文字と小文字の違いによる取りこぼしはありません。
- 表の中の `\|`。GitHub の GFM では、表のセルのインラインコードの中の `\|` は `|` と表示され、列は切れません。生の Markdown からコピーすると `\|` が残りますが、コマンドを読めなくなるほどではありません。
- 時刻と個人の情報。足した行は日付の行のほかに時刻を出さず、名前、メール、電話番号も入っていません。ただし指摘2の場合だけ、ファイル名の時分が表に出ます。
- 既存の試験。`bash scripts/test-hooks.sh` は終了コード0で、出力は0行でした(落ちたときだけ出す作り)。`docs/audits/raw` が無い worktree でも、`find ... 2>/dev/null` は空のまま通ります。
- 設計、計画、注入の経路。今回の変更は、[`scripts/usage-report.sh`](scripts/usage-report.sh) と [`docs/claude-usage.md`](docs/claude-usage.md) の集計の表示だけです。危なさの段階、通知の相手、30日の削除、注入された文の扱いには触れていません。
