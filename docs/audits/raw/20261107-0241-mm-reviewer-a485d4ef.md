## 指摘

1. 中。IPv6 を /64 でまとめているので、/48 を1つ持つ相手は D1 の書き込みの枠を安く食い尽くせる。招待のコードの総当たりも、この回数制限では止まらない。場所は [`server/src/join-limit.ts`](server/src/join-limit.ts) の `addressGroup`(20〜33行)と `takeJoinAttempt`(41〜60行)。確かさは中から高。
   - 起きること。Hurricane Electric のトンネルのように、/48 を無料で配るところがある。/48 には /64 が65,536個入っている。新しい /64 から1回送るたびに `join_attempts` に新しい行が1つ入り、表の行と、主キーの自動の索引の行で2行の書き込みになる。D1 の文書は「Indexes will add an additional written row when writes include the indexed column」と書いている。Free の書き込みはアカウント全体で1日100,000行までで、2026年9月1日からは超えるとクエリが失敗する(cloudflare-docs の MCP で、D1 の pricing と changelog を読んだ)。なので、別々の /64 から約5万回送れば、UTC の0時(日本時間の9時)まですべての D1 の書き込みが止まる。止まるのは知らせ、相談、笑顔、それに `takeJoinAttempt` 自身で、正しい家族の参加も 500 になる。この PR の前は、形の崩れたコードの試行は D1 に書かなかった。同じ5万回は Workers の1日10万リクエストの半分を使うだけで、母を守る経路は止まらなかった。
   - 総当たりのほうも同じ。/48 からなら1分に 65,536×5 回試せる。制限が上から押さえないので、残る上限は Workers の1日10万リクエストだけになる。コードのコメントの「six digits cannot be walked through」は、この相手には成り立たない。
   - 直し方の案。IPv6 を /48(少なくとも /56)でまとめる。日本の家庭の回線は /48 か /56 を受け取ることが多く、家族は家がそれぞれ別なので、正しい参加が巻き込まれる道はほぼ無い。D1 の枠を守るには、表の行数に全体の上限を足す方法もある。ただし、ここは約束の変更なので、主の会話で決める。どちらにしても [`docs/plan.md`](docs/plan.md) 113行の「先頭の /64」を合わせて直す。実装役も [`docs/dev-log.md`](docs/dev-log.md) で、全体の上限は主に判断を戻したと書いている。

## 確かめて問題なかったこと

- UPSERT。SQLite の `DO UPDATE SET` は、どの右辺も更新前の行の値で計算する。`window_start` の CASE も更新前の `window_start` を見る。逆の順に評価する実装なら、「starts counting again」のテストの `now + JOIN_WINDOW_MS` で count が7になって落ちるので、テストは落ちうる形になっている。60秒の境目は `window_start <= now - 60000` で切り替わる。59.999秒後は拒み、60秒後に通ることをテストが両方とも見ている。数えは1つの文で上がるので、同時の10回でも通るのは5回だけ。固定の窓なので、境目をまたぐと短い間に最大10回通るが、長く見れば1分に5回で、総当たりの速さは変わらない。
- `addressGroup` の展開。省略形(`2001:db8::1`、`::1`、末尾が `::`)、先頭の0の正規化、大文字、`%` のゾーン、IPv4 射影は正しくまとまる。`::` の右側に点区切りの IPv4 が入ると埋める0の数が1つずれるが、`CF-Connecting-IP` は Cloudflare が整えた形で、相手は書き方を選べない。
- [`server/src/families.ts`](server/src/families.ts) の `||` の順番。結び付けが断れば D1 には触れずに 429 を返す。数えるのは本文とコードを読む前なので、429 で招待のコードが使われてしまうことは無い。正しい参加が止まるのは、同じ接続元から60秒に5回試したあとだけ。iOS の `join` は自動で送り直さない(`ios/Core/Sources/MimamoriCore/Session.swift` 65行、`ios/App/Views/JoinView.swift` 36行)。母が最初の1回で入れることと、別の接続元の家族が入れることはテストで見ている。D1 が落ちたときは 500 になり、閉じる側に倒れる。
- アドレスの残り方。D1 に入るのは `keyedDigest` の HMAC だけで、HKDF の info が `dedupeDigest` と分かれていることをテストが確かめている。アドレスはログにも出ない。鍵が無いときの素の SHA-256 は今までの `dedupeDigest` と同じ扱いで、本番では `TOKEN_ENC_KEY` が `secrets.required` に入っている。`dedupeDigest` を書き換えたあとも判定の側のテストは通っている。
- 毎日の削除。窓が切り替わるたびに `window_start` が新しくなるので、使っている行は消えず、1日より古い行だけが 04:00 JST の `retention` で消える。テストは削除の前に古い行があることも確かめるので、DELETE を外せば落ちる。
- 書き込みの枠。1つの接続元からは、事前の SELECT のおかげで1分に新規の2行と更新の4行まで。拒んだ試行は書かない(同時に来たときは例外で書く)。Cron の D1 の呼び出しの数え(`ExternalBudget`)は、batch に1文足しただけなので増えない。
- マイグレーションの番号。0009 を使っているのは、ほかの遠隔のブランチではこのブランチだけ。plan の表、SKILL.md の「0009 を先に当てる」、手順3の「later deploys では先に手順4」は互いに食い違わない。
- 検証。`npx tsc --noEmit` はエラー無し。`npx vitest run` は `Test Files 20 passed (20)`、`Tests 1674 passed (1674)`。
- ハッカソンと個人情報。秘密の値、実在の家族の情報、外から写したコードは無い。`ios/Core` には手を入れていない。メッセージの本文やモデルの出力が回数や知らせの宛先を変える道も無い。
