`eval/README.md` の100〜102行目(ブランチの版)は「`make eval-split` のあと、`make eval` の `rules` の行をここに写す。」の1行だけで、数字が入っていない。この PR はちょうどその `make eval-split` と `make eval` をしたものなのに、写していない。`docs/plan.md` のタスク4(255行目)と Issue #6 の未完了の項目「`eval/run.ts` を書き、規則だけの数字を出して README の下書きに残す」も、この節が埋まらないと閉じられない。PR 本文の検証の出力(全体と経路ごとの5行)か、`RESULTS.md` の行をこの節に写せば足りる。測り直しは要らない。

### 2. 軽い。仕込みの例は、最後の数字では page の2件しか測られない

`eval/README.md` 51行目の説明は事実と合っている。dev には `consult-injection.jsonl`(3件)、`sms-injection.jsonl`(2件)、`gmail-injection.jsonl`(2件)があり、page の仕込みは dev に無い。main の README の「仕込みの例9件」から引くと、最後に測る組に入ったのは page の2件だけになる(数の上の推論で、最後に測る組は読んでいない)。

困るのは、計画の「見落としやすい5つ」の3つ目(本文の「この警告を止めて」「家族に知らせないで」に従ってしまう)が、主に SMS とメールで起きる失敗だという点。提出前の1回では、SMS、メール、声の相談の仕込みが1件も測られない。分け方の規則の4.(仕込みが dev と最後に測る組の両方に入る分け方を選ぶ)は組の中で働くので、経路ごとに仕込みが1ファイルしかない今の置き方では一度も効かない。

直すなら、作者の判断が要る。たとえば、提出前に各経路の仕込みを新しい手口のファイルとして足し、同じ規則で分けて `split-counts.json` に足す、など。今の PR で直す必要はないと思うが、README の説明に「SMS、メール、相談の仕込みは最後の数字に入らない」と書き添えておくと、提出の文で誤って言わずに済む。

### 3. 軽い。`0120-000-000` が実在の番号でないことを確かめられていない

dev の3件(`gmail-scam-support.jsonl` の `g-sc-12`、`page-scam-support.jsonl` の `p-sc-01` と `p-sc-02`)の本文に `0120-000-000` が入っている。ほかの番号(`+81 90-0000-…`、`+81 80-0000-…`、`+81 50-0000-…`、`+81 3-0000-0100`)は、市外局番や携帯の頭の直後が `0000` の形で、割り当てのない作り物と読める(番号の割り当ての表で個別に確かめてはいない)。`0120-000-000` だけは、0120 の後ろが 0 で始まる番号が実際に使われている帯なので、実在しないと言い切れない。Web で検索したが、割り当ての有無は分からなかった。

`.claude/rules/eval.md` の「実在の電話番号は入れない」に触れるおそれがある。公開するリポジトリなので、作者に確かめてもらうか、規則の電話番号の検出が変わらない範囲で、割り当てが無いとはっきりしている形に差し替えると安全。分ける前の置き場から来た例なので、最後に測る組にも同じ番号がある可能性がある(推測)。
