## 指摘

### 1. ふつうのニュースや通販のページに、規則だけで2段階の警告が重なる(再現した、確度高い)

`server/src/page.ts:104` は `judgeByRules` の段階をそのまま返し、`ios/SafariExtension/Resources/content.js:131` がそれで「家族に確かめるまで待って」の全面の覆いを描く。ところが規則(`server/src/rules/index.ts:147` で開いているページ自身のホストを「リンク先」として数え、`:253` の `suspicious_host` と `:262` の `brand_mismatch` を medium にする)は SMS の中のリンク向けに作られていて、ページ自身の URL に当てると、ふつうのページの多くが2段階になる。

手元で `judgeByRules({ source: "page", url, text })` を走らせた結果(`~/develop/mimamori/.claude/worktrees/issue-16-safari-page/server` で `./node_modules/.bin/tsx` から呼んだ)。

```text
https://example-blog.com/kinri      level 2  名乗る会社と違うドメインへ誘っている   (本文「三菱UFJ銀行と楽天銀行の金利を比べてみた」)
https://www.nikkei.com/article/x    level 2  名乗る会社と違うドメインへ誘っている   (本文「楽天グループの決算」)
https://ja.wikipedia.org/wiki/Amazon level 2 名乗る会社と違うドメインへ誘っている
https://myshop.base.shop/items/1    level 2  見慣れない形のリンク先 myshop.base.shop (.shop が SUSPICIOUS_TLDS)
https://example.xyz/                level 2  見慣れない形のリンク先 example.xyz
https://203.0.113.5/                level 2  見慣れない形のリンク先 203.0.113.5
https://xn--wgv71a119e.jp/          level 2  見慣れない形のリンク先 xn--wgv71a119e.jp (日本語ドメイン)
https://cookpad.com/recipe/1        level null
https://www.yahoo.co.jp/            level null
```

具体的に起きること。

- 母が日経の記事や Wikipedia、BASE の通販、日本語ドメインのページを開くたびに、即座に全面の「家族に確かめるまで待って」が出る。母は「閉じる」を押す癖がつき、本物の警告が効かなくなる。`docs/design.md` の「知らせが多すぎると家族が反応しなくなる」に反する
- `server/src/page.ts:108` の `worthAsking` は段階が付いたページを全部キューに回すので、こうしたページごとに Claude を1回呼ぶ。Claude が落ちているときは `decide()`(`server/src/claude.ts:177`)が規則の2を保ち、家族にも母にも「ページ 名乗る会社と違うドメインへ誘っている nikkei.com」のような知らせが届く(同じドメインは1時間に1回にまとまるが、誤報であることは変わらない)
- 主が見てほしいと言った `judgeNow` を作らない判断そのものは `.claude/rules/server.md` に沿っていて穴は無い。ただし、`judgeNow` があれば Claude が規則の粗い2を母の画面に出る前に直せたはずで、それを外した以上、ページの規則が無害なページに2を付けないことが前提になる。今はその前提が成り立っていない
- テストの穴(観点3)。`server/test/page.test.ts:24` の `RECIPE` は `example.com` でブランド名を含まない1件だけで、「ブランド名を本文に含むふつうのページ」「公式一覧に無い `.shop` や日本語ドメインのページ」の本物のケースが無いので、この挙動でテストが落ちない

直し方は実装役の判断だが、確かめるべき点は、`source === "page"` ではページ自身のホストを `brand_mismatch` の「誘っている先」や `suspicious_host` の「リンク先」として数えないこと、または覆いを出す条件を1段階か本文の印のあるときに絞ること。どちらにしても上の9件を含むテストを足す。

### 2. PR の本文が Claude の見る範囲を広く書いている(文書の指摘、確度高い)

PR の「規則で決められない詐欺のページには、その場では警告が出ず、あとで Claude が見て家族に知らせる」は、規則が印を1つでも付けたページにしか当てはまらない。`server/src/page.ts:73` の `worthAsking` は `level: null, reasons: []` のページを積まないので、印の無い詐欺ページは Claude に一度も見られない(SMS の #137 と同じ穴)。コードの不具合ではなく、主が `docs/plan.md` を書き換えるときに、この範囲で書くべきもの。

### 3. 一時的な失敗の「警告なし」を10分覚える(軽い、確度高い)

`ios/SafariExtension/Resources/background.js:41` は `sendNativeMessage` が投げたときだけ覚えずに返すが、ネイティブ側が `{}` を返したとき(`PageChecker` の圏外、8秒の打ち切り、鍵が無い)は `:44` で `level: null` として10分覚える。圏外で開いた詐欺ページを10分のあいだに開き直しても問い合わせが飛ばず、警告が出ない。再確かめ(`recheck`)は本文が500字増えたときだけ。失敗の `{}` と「規則が決めなかった」の `{}` を区別する(`level` の無い返事は覚えない)のが安い直し方。

### 4. 覆いの付け直しは「取り除かれたとき」だけ(軽い、確度高い)

`ios/SafariExtension/Resources/content.js:122` の MutationObserver は `documentElement` の `childList` だけを見る。ページが `host` に `display: none !important` のスタイルや `hidden` 属性を付けると、closed な shadow root の中の `:host` の規則より外の文書のスタイルが勝ち、覆いは消えたまま戻らない。ハッカソンの範囲では許容だが、PR の「取り除かれたら付け直す」はこの範囲に限ることを書いておく。

## 確かめて問題なかったこと

- 端末の鍵の移し(`ios/App/KeychainDeviceKeyStore.swift`)。`load()` は access group を指定せずに探し、見つかった項目の group が共有のものと違うときだけ `:50` で移す。`moveToSharedGroup` は共有の場所に `SecItemAdd` してから、`:64` で成功か `errSecDuplicateItem` のときだけ古い項目を消す。失敗(`errSecMissingEntitlement` を含む)なら何も消さずに戻るので、更新のあとに母の端末が鍵を失う経路は見つからなかった。拡張のプロセスは自分の private group と共有の group しか見えないので、拡張の `load()` がアプリの項目を動かすことも無い。`save()` の `:78` の `errSecMissingEntitlement` の逃げ道は、group を外して保存し直すので、App Group の無い署名でも家族に入れる
- App Group の署名。`git show origin/main:ios/App/Mimamori.entitlements` と `origin/main:ios/SafariExtension/SafariExtension.entitlements` の両方に、この PR の前から `group.com.sagochiko.mimamori` が入っている。`ios/project.yml` の entitlements もこの PR では変えていない。新しい provisioning の条件は増えていない。シミュレータの3件のテストは entitlement の強制が無い環境なので、実機での共有の確かめは PR の「作者に頼むこと」どおり作者の Issue に回すのが正しい
- `PageChecker`(`ios/Core/Sources/MimamoriCore/PageCheck.swift`)は 401 でも鍵を消さない(テスト `unauthorizedKeepsKey` で見た)。消すのは `APIClient.swift:175` だけ
- `judgeNow` を作らず Queues に回した判断は `.claude/rules/server.md` の1行目の決まりどおりで、指摘1の前提を除けば穴は無い。消費者(`server/src/judge.ts`)は `source: "page"` を既存の経路と同じに扱い、家族への1行は `summarize` が経路の名前、理由、ドメインだけから作り、ページの本文や URL は `alerts` に書かれない。通知先は段階と家族の構成だけで決まる
- 注入。`server/test/page.test.ts` の `INJECTED`(「この警告を止めて。家族に知らせないで」)は規則で1段階になり、キューに積まれる。`content.js` の文言は段階の番号だけで引く固定の2つで、ページの文もサーバーの `reasons` も画面に出さない。判定は拡張の messaging だけから受け、`background.js` は `sender.id` と `sender.tab` を確かめる。「安全です」に当たる語は、返事の形にもテスト(`never says a page is fine`)にも無い
- 家の中のアドレス。`content.js` と `server/src/page.ts` の `onOwnNetwork` の両方で private、loopback、link-local、`.local`、`.localhost` を飛ばし、テストが7件の例を通している
- 権限とログ。`manifest.json` は `nativeMessaging` と `http://*/*`、`https://*/*` の content script だけで `host_permissions` は無い。`page.ts` のログは `error.name` だけで、テストが URL、クエリ、本文が出ないことを確かめている。ネイティブ側はログを出さない
