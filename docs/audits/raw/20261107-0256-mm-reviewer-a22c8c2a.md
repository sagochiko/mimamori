## 指摘

1. dev-log の記録が、ほかの記録と `mm-devlog` の決まった形に揃っていない。確度は高い。場所は [`docs/dev-log.md`](docs/dev-log.md) の969〜975行。`.claude/skills/mm-devlog/SKILL.md` は、ラベルなしの5段落をこの順で書くと決めている。何を作っていたか、Claude にどう頼んだか(指示の引用)、何が起きたか、思っていたこととどう違ったか、どう対処したか、の5つだ。直前の #67、#178、#19 の記録もこの形になっている。新しい記録は3段落しかない。

   - 1段落目は流した内容を書いているが、何を作っていたか(#67 の回数制限を本番に出していた)が書かれていない
   - 2段落目の、主の会話への指示の引用が無い
   - 3段落目に「思っていたこととの違い」と「対処」が混ざっている

   提出フォームの「一番詰まった場面」はこのファイルから選ぶので、形が崩れていると拾いにくい。今回は作者からの指示が無く主の会話が自分で動いたので、2段落目にはそう書くのでよい。例えば「PR #201 のマージ後のデプロイは `/mm-deploy` の手順で主の会話が自分で流した」。4段落目の違いには「`apply` が落ちれば止まると思っていた」と書き、5段落目に手順書の変更と「使ったもの」を分けて置けば揃う。時刻と個人の情報は入っていない。「約1分」は長さで、時刻ではない。

2. [`.claude/skills/mm-deploy/SKILL.md`](.claude/skills/mm-deploy/SKILL.md) の58行は、例外を書かずに「Deploy only after `apply`...」と言い切っている。これが手順3の最初のデプロイの順番と食い違う。確度は高いが、影響は小さい。手順3の39行は「On the first deploy the database does not exist yet, so deploy first」と書いている。新しい文には「On later deploys」のような限定が無いので、最初のデプロイの場面で字のとおり読むと、守れない決まりになる。本番はすでに最初のデプロイを終えているので、今の実害は無い。文頭に「On later deploys,」を足せば手順3と揃う。

3. 「パイプでつながない」だけを禁じているので、`apply; deploy` や `apply && deploy` のつなぎ方が残る。確度は中くらい(禁止の範囲の読み方の問題)。場所は同じ58行。wrangler 4.157.0 の `server/node_modules/wrangler/wrangler-dist/cli.js` の241004〜241064行を読んだ。結果の `success` が false で例外が無いときは、表に `❌` を出すだけで `UserError` を投げず、終了の状態は0のままになる。そのため `&&` でつないでも、`❌` のままデプロイに進みうる。同じ文の前半の「`✅` と `No migrations to apply!` を見てから」を守れば防げるが、後半の禁止がパイプに限られているので、`;` や `&&` なら許されると読まれかねない。次のように書くと穴が無くなる。

   ```text
   Run `apply` as its own Bash line and read its output before running `deploy`
   ```

   あわせて、すでにデプロイしてしまったあとで `apply` が通らないとき(今回の場面)にロールバックするかどうかが書かれていない。足すかは主の会話の判断に任せる。
