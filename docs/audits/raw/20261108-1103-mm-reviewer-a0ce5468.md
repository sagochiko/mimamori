## 指摘

マージを止めるほどの欠陥は見つからなかった。気になった点は小さいものが3つで、どれも直さなくてもマージしてよい。

1. VoiceOver で「消す」が2つ並ぶかもしれない(確度は中、シミュレータで確かめていない)
   [`ios/App/Views/FamilyHomeView.swift`](ios/App/Views/FamilyHomeView.swift) の `swipeActions` と、`RemoveAction` が付ける `accessibilityAction(named: "消す")` の重なり。`List` の行の `swipeActions` は VoiceOver の操作として自動で出るので、解決したカードの操作が「消す」「消す」と2つになりうる。`accessibilityAction` は `VStack`(要素にまとめていない入れ物)に付いているので、逆にどの要素にも付かない可能性もある。検証役が Accessibility Inspector か VoiceOver で、操作が1つだけ出るかを見ればよい。出ていれば `RemoveAction` を外すだけで済む。

2. 相談の途中に家族が「解決」と「消す」を押すと、`ai_reply` がまた書き込まれる(確度は高い、起きることはまれ、表には出ない)
   [`server/src/consult.ts`](server/src/consult.ts) の397行目の `recordAiReply` は、`openConsultCase`(230行目、`state != 'resolved'`)で前に読んだ `caseId` に条件なしで書く。母の相談の答えを作っているあいだに、家族が同じ相談を解決してスワイプで消すと、消したばかりの行に AI の答えが戻る。`GET /cases` には出ず、30日の削除でなくなるので、家族にも母にも見えない。「その場で消す」という説明と食い違うだけだ。直すなら `recordAiReply` の UPDATE に `AND hidden_at IS NULL` を足す。

3. `npx vitest run test/cases.test.ts` が1回目だけ2件落ちた(確度は低い)
   作業の木で1回目は81秒かかって `2 failed | 55 passed`、すぐ流し直すと33秒で `57 passed` になった。時間の差からみて、手元の負荷で時間切れになったのだろうと推測している。足したテストに固有の問題なのかは突き止めていない。

## 確かめて問題なかったこと

- 消せるのは自分の家族の解決済みのカードだけになっている。`hideCase` の UPDATE は `id`、`family_id = me.family_id`、`state = 'resolved'`、`hidden_at IS NULL` を同時に条件にしていて、母は403 `family_only`、別の家族は404、`accepted` は409になる。`relays` の DELETE も `family_id` と `hidden_at IS NOT NULL` を条件にしているので、断られた呼び出しは何も変えない。テストは別の家族、母、二重に消す、鍵なし、`accepted` を通している。
- 判定のキューの再試行と #49 の守り。行が残るので、`openCase` の `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM cases WHERE alert_id = ?)` は新しい相談を作らない。`family_notified_at` が空でも、`tellFamily`(280行目、`state != 'resolved'`)が送らない。`openCase` の戻り値は judge.ts の402行目でも consult.ts の267行目でも読まれていないので、null に変わっても挙動は変わらない。テストは `family_notified_at` を空に戻してから `open` を呼び、null が返ること、相談が1件のままのこと、通知が0件のことを見ている。行を消す実装にしたら、このテストは件数が2になって落ちる。
- 母の側の画面と見張り。`watchUnanswered`(531行目と554行目)、最初の知らせの再試行(427行目)、`openConsultCase`、`tellFamilyHeavier` は、どれも `state != 'resolved'` で解決した相談を読まない。消せるのは解決した相談だけなので、どれにも影響しない。母も `GET /cases` を読むが、帯に出すのは `notified` の相談だけだ。
- その場で消す範囲(`ai_reply` と `relays`)は妥当だと思う。`alerts` を残すのは、1時間のまとめ(`sender_key`)、相談の最近の見つけたもの、調べもののためで、plan.md の表とも合っている。30日の削除([`server/src/retention.ts`](server/src/retention.ts) の34行目と36行目)と「すべて消す」([`server/src/families.ts`](server/src/families.ts) の254行目)は `hidden_at` を見ずに行を消すので、印の付いた行も残らない。
- マイグレーションとデプロイの順番。`0012` は `ADD COLUMN` だけで、前の版の Worker のままでも壊れない。[`.claude/skills/mm-deploy/SKILL.md`](.claude/skills/mm-deploy/SKILL.md) の35行目と58行目が、すでに「`migrations list` で未適用があれば `apply` を先に、`apply` と `deploy` を同じ行に書かない」と決めている。`.github/workflows` は無いので、マージしただけで自動でデプロイされることもない。主が `apply` を先に流せば500にはならない。
- 確かめ無しのフルスワイプでよいと思う。消せるのは解決したカードだけで、知らせは誰にも飛ばず、母の画面も変わらない。間違えて消しても、失うのは一覧の表示と AI の答えの1行だけだ。設計の「家族の誰もが同じカードを見る」とも合っている(1人が消すと全員から消える)。
- `List` の行の中のボタン。`CaseCardView` のボタンは `CardButtonStyle`(既定でないスタイル)、`SmileStrip` のボタンは `.plain` なので、行全体が1つのボタンとして一度に押される挙動にはならないはずだ。これはコードを読んだうえでの推測なので、画面では検証役が確かめる。
- iOS の `AppModel.remove`。204か404のときだけ手元の一覧から外し、409やほかの失敗は `run` が `problem` に出してカードを残す。`ios/Core` が増やしたのは `APIClient`、`Session`、`FamilyCard` だけで、iOS だけの framework は import していない。Core のテストは DELETE の方法、道筋、`Authorization`、本文が空なこと、409が呼んだ側に伝わることを見ている。
- plan.md のつなぎ目の約束。D1 の表に `hidden_at` を、API の表に `DELETE /cases/{id}` を足していて、実装の状態コードと誤りの名前(`family_only`、`case_not_resolved`、`case_not_found`、204)が一致している。
- 「安全です」を返す経路は足されていない。段階を下げる経路も、知らせる相手を変える経路も無い。消す口は誰にも知らせない。
