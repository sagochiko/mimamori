## 確かめて問題なかったこと

- 指摘1の形は、どれも送り元が空になる。そのため公式と読まれず、確かさ(`confident`)が付いたままになる。
  ```text
  "Bank <scam@smbc.co.jp?x.evil.example>"  -> null  true
  "Bank <scam@smbc.co.jp/evil.example>"    -> null  true
  "Bank <scam@smbc.co.jp#evil.example>"    -> null  true
  "Bank <scam@evil.example＠smbc.co.jp>"    -> null  true
  "Bank <scam@smbc.co.jp:evil.example>"    -> null  true
  "Bank <x@ｓｍｂｃ.co.jp>"                  -> null  true
  ```
- 本物の公式の From は外れない。次の形はどれも、山括弧の中のアドレスが送り元になり、公式と読まれる。
  - 引用符つきの日本語の表示名
  - 符号化した表示名
  - 素のアドレスと、山括弧だけの形
  - `no-reply_2024.info@mail.smbc.co.jp` のような記号入りのローカル部とサブドメイン
  - 大文字のドメイン

  dev の gmail の From はどれも、この形の中に収まる(1回目に確かめた)。
- 新しく公式と読ませる道も探したが、見つからなかった。
  - ローカル部に記号を入れた形(`smbc.co.jp?@evil.example`)。最後の `@` で分けるので、ドメインは `evil.example` になり、公式にならない。
  - ハイフンで始まるラベル(`-smbc.co.jp`)、似せたドメイン(`evil-smbc.co.jp`)、`smbc.co.jp.evil.example`、`smbc.co.jp-.evil`。どれも公式にならない。[`server/src/rules/domains.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/server/src/rules/domains.ts) 203行の `officialBrandOf` が、ドメインが同じか `.` の境で終わるときだけを公式と数えるためだ。
  - `xn--` のラベル。公式にならず、規則の側で怪しいホストとして扱われる。
  - 点が2つ続く形(`smbc.co.jp..`)と、ローカル部が空の形。どちらも空になる。
  - 公式と読まれるのは、末尾に点が1つ付いた `smbc.co.jp.` と、`evil.example.smbc.co.jp` のような公式のドメインの下だけだった。前者は DNS の上で同じドメインで、後者は組織ドメインが公式のままなので、DMARC の扱いは公式のドメインと同じになる。設計に直した「公式のドメインそのもの(かその下のドメイン)として偽る必要があり」と合う。
- ドメインの正規表現は ASCII の英数字、ハイフン、点だけを通す。この文字の範囲では、`new URL` が読むホストと、生のドメインの文字は同じになる。NFKC で形が変わる文字も入らない。
- 試験は落ちうる形になっている。足した5件の空にする側の例は、1回目の版の正規表現なら送り元が付く形なので、直しを戻すと落ちる。取る側の2件(末尾の点、記号入りのローカル部)は、正規表現を厳しくしすぎたときに落ちる。`npx vitest run test/gmail.test.ts` は63件すべて通った。
- 例のアドレスは `.example` だけだった。足された `docs/audits/raw/` の原文に出てくるのは公開の銀行のドメインだけで、これはもともと `domains.ts` にある。家族の情報と秘密は入っていない。
