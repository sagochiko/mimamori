## 指摘

1. 「母の言葉を渡さない」を確かめる試験が無い(中。確度は高い)
   [`server/test/consult-summary.test.ts`](server/test/consult-summary.test.ts) の `makes its own agent ... and sends no words of hers` は、固定の `INPUT` で `startConsultSummary` を直に呼び、`2段階` と `REASONS` が入っていることしか見ていません。母の言葉が入っていないことは見ていない。`describe("a consultation starts the summary")` のほうは `deps.summarize` を差し替えて `alertId` を記録するだけなので、`consult.ts` の `startSummary` が何を渡したかは誰も見ていません。
   今のコードは D1 の `level, reasons, summary` を読んで渡しており、正しい作りです(`server/src/consult.ts` の `startSummary`)。ただ、誰かが `deps.summarize(env, alertId, { ..., summary: text })` のように書き換えても、14件はすべて通ります。PR の核の約束で、design.md の「データの扱い」も今回書き換えたところなので、壊れたら試験で落ちるようにしておくべきです。
   直し方の案です。`POLICE` の相談で `summarize` が受け取った `input` を記録し、`JSON.stringify(input)` に `POLICE` の特徴的な断片(`LINE のビデオ通話`、`潔白を証明`)が入らないことを確かめる。できれば msw で本物の `startConsultSummary` を通し、`seen.sessions[0]` の本文で同じことを確かめる。

2. `ctx.waitUntil` の30秒で打ち切られると、消されないセッションが残る(中低。確度は中)
   `server/src/consult.ts` は、母に答えを返したあと `startSummary` を `ctx.waitUntil` で走らせます。Cloudflare の文書は「`ctx.waitUntil()` can extend execution for up to 30 seconds after the response is sent ... If any Promises have not settled after 30 seconds, they are canceled」と書いています(developers.cloudflare.com/workers/runtime-apis/context)。
   一方 `startConsultSummary`(`server/src/agents.ts`)は、初回はエージェントの作成(最長10秒)、環境の作成(最長10秒)、`/sessions` の作成(`SESSION_CREATE_TIMEOUT_MS` = 30秒)を順に待ちます。合わせると30秒を超えることがあります。
   困る場面は、Anthropic 側でセッションができたあと、`UPDATE alerts SET investigation_session_id` の前で打ち切られたときです。セッションの ID はどこにも残らないので、5分ごとの見張り、「すべて消す」、30日の削除のどれも、このセッションを消せません。中身はカードの1行と理由で、母の言葉ではありません。それでも、30日で消すという約束がこの経路では守られません。
   裏の調べもの(`startInvestigation`)はキューの consumer で動くので、時間の上限は15分あります。要約だけがこの穴を持ちます。
   直し方は2つ考えられます。1つは、`waitUntil` の中だけセッション作成の時間切れを短くし、作成までの合計が30秒に収まるようにする。もう1つは、調べものと同じくキューに回す。少なくとも PR の本文と design.md に、この残り方があることを書いておくべきです。

3. design.md の「データの扱い」を実装役が書き換えている(低。指摘というより親への申し送り)
   [`docs/design.md`](docs/design.md) の「Managed Agents に渡すのは怪しいメッセージの中身だけ」を、「相談の要約では段階とカードの理由と1行」に広げています。渡すのはカードの1行と理由で、`summaryOf` と `cardReasons` が `quotes()` と `/安全/` を通したあとの文です。`steered` のときは決まった言葉だけになります(`server/src/consult-judge.ts` の `summaryOf` と `cardReasons`)。それでも、Claude が母の相談から作った言い換えが外部のエージェントへ出ていくのは、新しいデータの流れです。#271 の本文は何を渡すかを決めていません。CLAUDE.md は設計の変更を先に作者に聞くことにしているので、作者が認めた形かどうかを PR の「レビュー」の節か #271 に残してください。主の指示より狭い形にした判断そのものは妥当だと考えます。

## 確かめて問題なかったこと

- エージェントの自由な文が外へ出る道は無い。`parseSummary` は `Object.hasOwn` で、こちらが決めた鍵だけを受け取ります。`__proto__`、`toString`、鍵の代わりのラベル、余分な文は `null` になり、試験もあります。D1 に入るのは鍵だけです。`summaryLine` は読むときにもう一度鍵を照らし合わせ、こちらの言葉だけで1行を作ります。ログは `error.name` だけで、`postJson` は道筋と状態だけを出します。
- `collectInvestigation` の分かれ道は `alert.source === "consult"` で決まり、それぞれ自分の道具の名前しか読みません。調べもの(`SOURCES` に `consult` は無い)の結果が要約として、または逆向きに入ることはありません。調べものの知らせでは `finish` が `summary_topic` と `summary_step` に `null` を書くだけです。
- 選択肢の文言(話題6つ、一手2つ)に「安全」「心配ない」と読めるものは無く、`soundsSafe` と正規表現の試験があります。「次に話すときに聞く」を外した理由も design.md の段階の約束と合っています。
- 1段階の固定は、読んだとき(`parseSummary`)と表示するとき(`summaryLine` が今の `level` を見る)の両方で効きます。あとから1段階に重くなった場合も試験があります。エージェントには段階を下げる手段がありません。
- 起動の条件は `caseId && alertId && p.toFamily && p.sign && !p.unguided && p.level <= 2` です。`startSummary` と `startConsultSummary` は D1 側でも `source='consult' AND notified=1 AND level<=2` とセッション無しを確かめます。家族の1日の上限は `takeResearchStart` で調べものと同じ数に数えます。会話の中で `alertId = open.alert_id` を使うので、同じ相談で2回は立ちません。競合して2つできたときは、`UPDATE` の条件で片方のセッションを消します。
- 母の答えは待たせない。`consultRoute` が `defer` に `ctx.waitUntil` を渡し、`index.ts` の経路も `ctx` を渡しています。
- 「すべて消す」(`server/src/families.ts` の `investigation_session_id` の UNION)と30日の削除(`server/src/retention.ts` の30行と85行)は同じ列を見るので、要約のセッションにも効きます。鍵の列は知らせの行と一緒に消えます。
- マイグレーション `0011` は `ALTER TABLE ... ADD COLUMN` の2本だけです。`GET /cases` の SELECT と `finish` の UPDATE が新しい列を使うので、PR 本文の「マイグレーションを先に当て、そのあとデプロイ」は正しい順番です。逆にすると、家族の画面だけでなく裏の調べものの結果の書き込みも落ちます。
- iOS の家族のカードに出るのは裏側の1行だけで、見出しや説明は足していません。「話題と次にすること、」は VoiceOver の読み上げにだけあり、作者の画面の文言の決まりどおりです。`ios/Core` は Foundation だけを使い、`digest` が null、欄が無い、空、文字以外のときも相談は読めます(試験あり)。
- エージェントへの入力は `<data>` で囲み、`neutralize` で `<` と `>` を全角にしています。道具はネットを使わない `custom` の1つだけです。
- 秘密、実在の家族のデータ、外から写したコードは差分にありません。
- 試験は自分では走らせていません(このレビューではファイルを書けず、worktree も作れないため)。2126件と405件が通ったという数は PR 本文の実装役の報告によるもので、親が `make verify` で確かめてください。
