## 指摘

1. やり直すと、見出しの「読んだコミット」が原文を残したコミットに変わる。場所は `~/develop/mimamori/.claude/worktrees/harness-review-record/scripts/review-record.sh` の30行目 `commit=$(git rev-parse --short HEAD)`。確度は高く、再現もした。
   前の手順では `<commit>` を親が渡していた。新しいスクリプトは実行したときの HEAD を使う。1回目の実行は原文をコミットするので、そのあとは HEAD が原文のコミットになる。手順書には「Run again (after a failed post)」と書いてあるので、投稿が `guard-private.sh` に止められたり gh が失敗したりしてやり直すと、見出しが原文のコミットを指す。捨てるリポジトリで試した結果は次のとおり。

   ```text
   1回目、461de67 を読んだもの。...   (レビューしたコミットは 461de67)
   already committed: docs/audits/raw/20261106-0000-mm-reviewer-abcd1234.md
   1回目、664b849 を読んだもの。...   (やり直したあと。664b849 は原文のコミット)
   ```

   2回目のレビューでも同じことが起きる。1回目のやり直しが無くても、原文を残したあとに直しのコミットが無いまま2回目を回すと、見出しのコミットは原文のコミットになる。マージの関門はこの値を見ないので、マージは止まらない。ただ、公開されるレビューの記録に、レビューしていないコミットが書かれる。直し方は2つある。読んだコミットを引数で受け取る(前の手順と同じ)か、HEAD が `$raw` だけを変えた自分のコミットならその親を使う。`scripts/test-hooks.sh` の足した確かめも、見出しのコミットは見ていない。

2. 原文をコミットしてから投稿する順に変わったのに、止められたときの手順書の説明が前の順のまま。場所は SKILL.md の手順6.1の「If it blocks a spot inside the report ... build the comment again with the block above」の段落。確度は中くらいで、影響は小さい。
   前はコメントを投稿してからコミットした。今はスクリプトが先にコミットする。原文の中の非公開の語は、`pre-commit` が `scan-private.sh staged` で同じ規則に当てるので、スクリプトの `git commit` のところで止まる。`set -e` で終わるが、そのときにはコメントのファイルがもう書かれている。手順書はこの止まり方に触れておらず、`guard-private.sh` に止められた場合だけを書いている。伏せてからやり直すと、新しいコミット(伏せた版)ができて正しく動く。なので壊れはしないが、「スクリプトがコミットで止まったら、保存した原文のその場所を伏せてもう一度流す。コメントのファイルは投稿しない」と1文足すと迷わない。`guard-private.sh` と `pre-commit` は `scan-private.sh` を共有しているので、伏せる前の非公開の語だけがブランチに残る道は見つからなかった。

3. 手順書の行を流す確かめが、手元の git の全体設定にあるメールに頼っている。場所は `scripts/test-hooks.sh` の差分の `(cd "$T/wt" && git -c user.name=t -c user.email=t@t config user.name t && bash -c "$tpl")`。確度は高く、影響は小さい。
   `git -c ... config user.name t` で書かれるのは `user.name` だけで、`-c` の `user.email` はこの1回の `git config` にしか効かない。スクリプトの `git commit` は全体設定のメールを使う。全体設定にメールが無い環境では、この確かめが手順書と関係なく落ちる。同じファイルのあとの確かめは `git config user.email t@t` も書いているので、そちらに揃えればよい。

## 確かめて問題なかったこと

- main の木からの移しとやり直しは、前の7行と同じ判定になっている(`-s "$src" && ! "$src" -ef "$raw"` なら `mv`、`-s "$raw"` が無ければ止まる)。足した確かめは、移したこと、main の木に残らないこと、2回目にコミットが増えないこと、無い原文で止まることを見ている。`cp` に替えると落ちることは PR の本文に書かれていて、判定の形からもそうなる。
- コメントの本文は前と同じ順で、見出し `## mm-reviewer の報告(原文)`、回数とコミットと原文の道筋の1行、空行、`cat` した原文になる。`guard-merge.sh` の129行目は1行目が `#+ mm-reviewer の報告` であることを見て、そのあとの `ステータス:` の行を数える。この形は崩れていない。
- `guard-private.sh` の `raw_tail` は、本文の中の `docs/audits/raw/<name>.md` を `cwd`、作業の木、main の木の順に探し、本文の末尾と1バイトずつ比べる。原文は PR の木に移ってコミットされたあとも同じ場所にあるので、PR の木から投稿すれば見つかる。
- 投稿はスクリプトの外の `gh pr comment <pr> --body-file <scratchpad>/review-comment.md` で、道筋は文字のまま書かれている。手順書は「a command of its own」「Do not create the body file in the same command」と書き、変数や `$(...)` の本文に戻る書き方は残っていない。`--body-file` の引用符を外したが、`guard-private.sh` の138行目は語に分けてから読み、153行目の正規表現も引用符が無くても通るので問題ない。
- `.githooks/commit-msg` にスクリプトのメッセージを `Refs` ありと無しの両方で当てたところ、どちらも終了コード0だった。本物の PR #167 で作ったコミット 96c4ea9 も同じ形で、フックを通っている。`git commit -- "$raw"` は道筋を指定するので、ほかに索引に入っている変更は巻き込まれない。
- 「When no file was saved」の節は、原文を PR の木の `docs/audits/raw/<name>` に書いて「Then run the steps above; they find the file in this tree」と続く。スクリプトは `$src` が無くても `$raw` を使うので、新しい形と合っている。
- 回数を `^[1-9]$` に限っているのは、手順書の3回までという決まりの中に収まる。
- 秘密の中身は読んでいない。非公開の語の一覧があるかを `ls` と `grep` で確かめようとしたところ、そのファイルの名前がコマンドに入っていたためフック(`PreToolUse:Bash hook 3`)に止められた。理由は「the author's private lists ... stay out of Claude's context」で、別の方法では試していない。代わりに `scripts/scan-private.sh` を読み、`pre-commit` と `guard-private.sh` が同じ一覧を同じやり方で探すことを確かめた。
