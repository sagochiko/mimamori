## 指摘

1. 「本番の記録で母の受信箱を読み始めたことを確かめた」は、記録から言える範囲を超えている(確度は高い)

   PR 本文は、母の家族の `gmail_auth` の行に `last_history_id` が入っていることを、裏側が母の受信箱を読み始めた根拠にしている。ところが [`server/src/gmail.ts`](server/src/gmail.ts) の183〜195行を読むと、この値は許可の戻り先(`/gmail/callback`)が書いている。`currentHistoryId` が `users/me/profile` の `historyId` を取り、行を作る `INSERT` と同じ文で `last_history_id` に入れる。

   ```ts
   const historyId = await currentHistoryId(tokens.access_token);
   if (historyId === null) return back("failed");
   ...
   INSERT INTO gmail_auth (family_id, refresh_token_enc, granted_at, last_history_id, expired_notified_at)
   ```

   このため、Cron の `readNewMail`(395〜442行の `history.list`)が一度も走っていなくても、許可が通った瞬間に `last_history_id` は埋まる。値が入っていることから分かるのは「許可が成功して見張りの起点が記録された」ところまでだ。受信箱を読んだかどうかは分からない。

   README の次の4か所がこの推論に乗っている。
   - `README.ja.md` 47行の「本番の記録で、許可のあと裏側が母の受信箱を読み始めたことを確かめた」
   - `README.ja.md` 128行の「母の受信箱を読み始めたが」
   - `README.md` 46行の `The production records show the server started reading her inbox after her consent`
   - `README.md` 130行の `The Gmail watch has read her inbox since her consent`

   依頼にある水増しの確かめに当たる。家族に知らせたとまでは書いていないので一番重い形ではないが、記録で確かめた事実として書いてしまっている。直し方は2つある。1つは「許可が本番に記録され、見張りの起点が入った」のように、記録で言えることだけに書き換える。もう1つは、読んだ証拠を別に取ってから書く。たとえば `wrangler tail` で Cron の回に `gmail history failed` などの警告が出ていないことを見る、または許可のときの値から `last_history_id` が進んだことを確かめる(ただし許可のときの値は残っていないので、今の値を控えて、母の受信箱にメールが届いたあとに比べる形になる)。PR 本文の「裏側が母の受信箱を読み始めたことを示す」も同じ理由で直す。

2. 「うち2件は誤報で、#249 で直した」は、aws.training の分では言い過ぎ(確度は中くらい)

   `README.ja.md` 47行と `README.md` 46行の `fixed in #249` が対象。PR #250 の本文の「残ること」には「aws.training の誤報は、規則と Claude の両方が2段階だったので、この PR では消えない」とある。そのあと「足したこと」で DMARC の結果を Claude に渡す指示を足したが、同じ本文に「`make eval`(規則と Claude)は流していない」とある。直ったと言えるのは fonts.googleapis.com の1件(`<a href>` だけを数える変更)だけだ。aws.training の分は、手を入れたが直ったかは測っていない。「1件は #249 で直し、もう1件は Claude に送り元の認証の結果を渡すようにした(効き目は未測定)」のように分けて書くのがよい。
