PR #198 には、直してからマージすべき指摘はない。依頼の4点はコードを読んで確かめ、どれも問題なかった。弱いところが2つあるが、どちらも今の使い方ではまず起きないので、マージは止めない。

## 指摘

1. 失敗が続く最初の知らせが D1 の枠を使い切り、後ろの仕事を止める(中くらいの重さ、起きやすさは低い、仕組みは確か)
   - 場所は [`server/src/cases.ts`](server/src/cases.ts) の `sendFirstNotices`(400〜413行)と、[`server/src/cron.ts`](server/src/cron.ts) の `JOBS` の並び。
   - 起きる場面は、家族の端末への APNs が 410 以外で失敗し続けるとき(`DeviceTokenNotForTopic` や 5xx など)。トークンが消されないので、その相談は毎回 `not_delivered` になる。`no_budget` 以外では loop を抜けないから、こういう相談が24時間のうちに9件以上たまると、毎回の Cron で 1 + 9×4 = 37 回を使い、残りは3になる。
   - そうなると、`watchUnanswered`(5以上が要る)、`notifyMissedSmiles`(5)、`watchGmail`(8)が毎回すぐ戻る。家族に届かないときの母への `NOT_REACHED`(「急ぐなら電話して」)と Gmail の見張りが、最大で24時間止まる。
   - 直す前も外への呼び出しの枠で同じことは起きたが、2台の家族で20件が要った。1台なら起きなかった。この PR で、起きる件数の下限が9件に下がった。
   - 案は次のどちらか。主役(#64 の母への答え)を守るなら前者がよい。
     - `sendFirstNotices` に D1 の上限を持たせ、たとえば半分までにする
     - `watchUnanswered` の分を先に取り置く
   - Issue のとおり今の使い方で9件たまることはまず無いので、マージは止めない。別の Issue にしてよい。

2. Gmail、調べもの、笑顔、掃除に足した判定を、落とせる試験が無い(軽い)
   - 次の4つは、どの試験も通らない。
     - [`server/src/gmail.ts`](server/src/gmail.ts) の 635行と646行
     - [`server/src/agents.ts`](server/src/agents.ts) の 502、512、515、524行
     - [`server/src/smiles.ts`](server/src/smiles.ts) の 234行と255行
     - [`server/src/retention.ts`](server/src/retention.ts) の 43行と70行
   - 試験が見ているのは `cases.ts` の2つの仕事だけで、上の行を消しても全部通る。
   - `watchUnanswered` の試験は母の役の無い家族(`createFamily("作者")` だけ)で組まれていて、`WATCH_D1 = 4` の2回目の `sendPush` も通らない。母のいる家族で1件4回になる形が1つあれば、見積もりが実際より少ないときに落ちる。

## 確かめて問題なかったこと

- 残りを見る位置はどの仕事でも取り置きの前にある。
  - `sendFirstNotices` は `tellFamily` の claim の前(405行)で見る。`watchUnanswered` は `membersOf` と `renotified_at` の UPDATE の前(477行)で見る。
  - `warnBeforeExpiry` の claim の前(646行)、笑顔の `smile_missed_notified_on` の前(255行)も同じ。
  - `countD1` は呼び出しを止めず、数えるだけ(`d1Remaining` は負になれる)。なので、始めた1件が数えた枠のせいで途中で切れる道は無い。
  - 試験の1つ目は、残った相談の `family_notice_claimed_at` が `null` であることを見ている。判定を claim の後ろへ動かすと落ちる。
- 1件あたりの見積もりを、呼び出しを1つずつ数えて照らした。
  - `tellFamily` は claim、`membersOf`、`sendPush` の SELECT、claim を戻す UPDATE の4回。
  - `watchUnanswered` は `membersOf`、claim、`notify` の中の `sendPush` 2回の4回(相手がいないと 0 回になる)。
  - Gmail は前もっての知らせが4回、`endGrant` が3回、`last_history_id` か `saveProgress` が1回で、最大7回。`readNewMail` の中の `judgeMessage` は Queue に送るだけで D1 を呼ばない。
  - `collectInvestigation` は SELECT、`finish`、`dropSession` の3回。
  - 見積もりの外は2つだけ。1つは APNs が断った端末を忘れる UPDATE([`server/src/push.ts`](server/src/push.ts) の141行)で、最後の1件の分しか枠を越えない。もう1つは毎日の `purgeExpired` の2回(SELECT 1回と batch 1回)。どちらも40と50のあいだの10に収まる。
- `countD1` が実際より少なく数えることは無い。
  - tick の道筋で、1回 prepare した文を2回流す箇所は無い。prepare してすぐ `bind` するのがすべてで、使い回しは `families.ts` の36行だけ。これはお知らせの経路の外で、枠は無限なので関係しない。
  - batch の中の文は、どれも包んだ `env.DB.prepare` から作られている。`1 - n` を戻しても、実際より少なくはならない。
  - `withSession` と `exec` は tick の中で使われていない。
- 家族への知らせが母への「届いた」より先に届く約束(#64)は崩れていない。
  - `openCase` は相談の HTTP と Queue の経路から呼ばれ、`new ExternalBudget()` を使う。この道は `d1Remaining` が無限なので、何も変わらない。
  - D1 の枠を持つのは `runScheduled` の1か所(`cron.ts` の67行)だけ。
- 試験は落ちうる形になっている。
  - 1つ目は、D1 の判定が無いと外への枠の40で20件すべてが1回目に届き、`toBeLessThan(20)` で落ちる。呼び出しも81回になり、50を越える。
  - 2つ目は、判定が無いと61回になり、50を越える。
  - 数えるのは試験の側の独立した包みで、実装の `countD1` に頼っていない。
- 試験の結果。`server` で `npx vitest run` を流し、`Test Files 18 passed (18)`、`Tests 1643 passed (1643)` だった。`npx tsc --noEmit` はエラー無しで終わった。
- 秘密の値、家族の実データ、外から写したコードは、差分に無い。`ios/Core` には触れていない。`docs/dev-log.md` の追記は日付だけで、時刻は無い。
- 注入の道は無い。この変更は呼び出しを数えるだけで、知らせる相手、共有の範囲、危なさの段階には触れない。
- `docs/plan.md` と `docs/design.md` には D1 の1回の上限についての約束が無く、食い違いも無い。
- フックに止められた操作は無い。
