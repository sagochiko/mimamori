## 指摘(重い順)

### 1. 端末の無い家族の相談が、5分ごとの送り直しの20件の枠をほかの家族と取り合う(中、コードで見た)
- 場所は `server/src/cases.ts` の 330〜342行(`sendFirstNotices`)と 239行(`reachable === 0` → `"not_delivered"`)
- 以前は端末0台の家族の相談を `family_notified_at` 入りで閉じていたので、送り直しの対象にならなかった。今は `family_notified_at IS NULL` のまま1日残る。`sendFirstNotices` は全部の家族をまとめて `ORDER BY c.notified_at DESC LIMIT 20` で取り、`not_delivered` でも `break` せずに続ける
- 例を挙げる。母だけが入って家族がまだ端末を登録していない家族(作り始めの家族はたいていこの形)に、1日で20件以上の1・2段階の SMS が来たとする。この家族の新しい相談が毎回の20件を埋め、それより古い、別の家族の APNs が失敗した相談はいつまでも送り直されない
- ついでに、この家族の相談は1件ごと、5分ごとに claim の UPDATE と unclaim の UPDATE で D1 に2回書く。最大で20×2×288=11,520回/日になり、無料枠の10万/日には収まる
- 直し方の案は、SELECT で通知を受けられる家族の端末がある家族に絞ること(`AND EXISTS (SELECT 1 FROM members m WHERE m.family_id = c.family_id AND m.role = 'family' AND m.apns_token IS NOT NULL)`)。端末が登録されれば次の tick で拾われるので、「あとで登録すれば届く」は崩れない。テストは「端末0台の家族の相談が20件以上あっても、別の家族の届いていない相談が送り直される」で足りる

### 2. 判定のキューの動きが変わったのに、テストが無い(低、コードで見た)
- 場所は `server/src/judge.ts` の 282〜290行(`finishNotices`)と、`server/wrangler.jsonc` の `max_retries: 3`
- 端末0台の家族では `openCase` が `CaseNoticeDeferred("not_delivered")` を投げるようになった。そのせいで、知らせる SMS やメールの判定はどれも `"retry"` になり、30秒おきに3回まで配達し直す。Claude は呼び直さず(`stored` の道)、外への通信もしないので、費用は Queues の操作と D1 の読み書きだけで済む。動きとしては妥当だ
- ただ `server/test/judge.test.ts` には端末0台の家族の場合が1件も無い(`apns_token = NULL` を grep して0件)。「retry を返すが Claude は呼び直さない。母への通知を2回送らない」を1件足すと、この変化が固定される

### 3. 同じ相談の claim を別の処理が握っている瞬間に、「伝えました」と答えうる(低、コードで見た)
- 場所は `server/src/consult.ts` の 564〜570行(`familyWasTold`)と、`server/src/cases.ts` の `tellFamily`(claim を先に書き、失敗したら消す)
- `familyWasTold` は `family_notified_at` が NULL でないかしか見ないので、ほかの処理の claim と区別できない。例を挙げる。`openCase` の INSERT から claim までの間に5分の tick の `sendFirstNotices` が先に claim したとする。すると相談側の `tellFamily` は `"already"` を返し、`familyWasTold` は true になって、母は「伝えました」と聞く。そのあと tick の APNs が全部失敗して unclaim される。会話の続きの道(`open.family_notified_at === null` → `openFor`)でも同じことが起きる
- 窓は数百ミリ秒で、起きる見込みは低い。直すなら、`openFor` が `openCase` の結果(`"told"` か `"already"` か、投げたか)を返すようにする。`"already"` のときは claim ではなく送り終えた印で判断する必要があるが、今の表にはその列が無い。今回は「既知の残り」として PR に書くだけでもよい

### 4. `notReached` が最初の「家族に伝えました」しか置き換えない(低、コードで見た)
- 場所は `server/src/consult.ts` の 573〜576行。`reply.replace(TOLD_FAMILY, NOT_REACHED)` は文字列を渡しているので、置き換えるのは最初の1つだけだ
- 例を挙げる。ハンドオフの道(492行 `${basis}${SCAM_ACTION}。${TOLD_FAMILY}`)で、Claude の `basis` に「家族に伝えました」が入っていたとする。`usable()` はこの語を弾かない。置き換わるのは basis の側だけで、末尾の固定の「家族に伝えました」が残る。母は「…家族に届いていません。急ぐなら電話して…。家族に伝えました」と、最後に誤ったほうを聞く
- Claude の文に「家族に知らせました」のような言い換えが入っていた場合も同じで、`includes` が外れて末尾に NOT_REACHED が足され、矛盾した2文になる
- 直し方は `replaceAll` にすること。できれば、Claude の basis と action から「家族に(伝え|知らせ)ました」を落とす(または usable で弾く)
- 差分の外の話だが、前からある穴も書いておく。`toFamily: false` の道(3段階の `lowConcernReply`、`help` の `claude.action`)は Claude の action をそのまま読み上げる。Claude が「家族に伝えました」と書けば、相談を開かず誰にも知らせていないのにそう聞こえる。`consult.ts` 194行あたりのプロンプトに、この語を禁じる文は無い

### 5. 重くなった知らせだけが失敗したときも「家族に届いていません」と言う(低、文書で見た)
- 場所は `server/src/cases.ts` の `tellFamilyHeavier`(失敗すると `family_notified_at = NULL` に戻す)と、テスト `server/test/consult.test.ts` の「says 'not reached' when the heavier notice of her open case could not go out」
- 家族は軽いほうの最初の知らせをもう受け取っている。それでも母の答え、母の画面、30分の見張りの通知はどれも「家族に届いていません」になる。`docs/design.md` に足された文は「家族のどの端末にも届かなかった相談では」なので、字面とずれている。母に電話を促す側へずれるので、安全側ではある。dev-log にも意図して入れたことが書いてある
- 直すなら挙動ではなく、design.md のその段落に「重くなった知らせが届かなかったときも同じに扱う」と1文足して、字面と合わせる

### 6. 1日たったあとも VoiceOver が「送り直しています」と読む(低、コードで見た)
- 場所は `ios/App/Views/ProtectedHomeView.swift` の `hint`(notReached の場合)。裏側の送り直しは1日で止まる(`FIRST_NOTICE_RETRY_MS`)が、母の画面には3日出る(`CaseCards.swift` 114行の `openShownFor`)。2日目と3日目は、送り直していないのに「送り直しています」と読む
- 直し方は、hint からその句を落とすこと

## 確かめて問題なかったこと
- 届いたかどうかの判定は、`consult()` の新規の道と会話の続きの道のどちらでも、`openFor` か `tellFamilyHeavier` が済んだあとの `family_notified_at` を読んでいる(`consult.ts` 608〜623行)。端末1台にでも届けば `"told"`(`sendCaseNotice` の `results.some(sent)`)。予算切れ、APNs の全部の失敗、端末0台の3つは、どれも unclaim されて NULL に戻る。テストは3つの原因を `it.each` で回している
- ニセ警察の即答の道は、今も `openFor` を await してから答えを返す。Claude を呼ばない。届いたときは設計どおりの固定文のまま、届かなければ末尾に NOT_REACHED が付く
- 答えの形 `{ reply, speak, handoff }` は変わっていない。`handoff` は届かなかったときも true で、iOS は `loadCases()` を呼び、画面に「家族に届いていません」が出る
- 30分の見張りは、`family_notified_at` が NULL なら母に NOT_REACHED、そうでなければ NO_REPLY_YET を送る(`cases.ts` 418行)。家族への2回目の通知と、状態を変えないことは前のまま
- `loadViews` は `familyNotifiedAt` を ISO の文字列か null で返す。`resolve` の答えにも入る(テストあり)
- 家族のカードに出る「AI の答え」は、母が聞いた文(NOT_REACHED 込み)と同じになる。家族の通知の1行と理由は変わっておらず、母の言葉や届いた文を写す道は増えていない
- 通知先、共有の範囲、段階は、Claude の出力でも母の文でも変わらない。段階を下げる道も無い
- iOS の `Case.init(from:)` は、キーが無ければ `notifiedAt` で埋めて届いた側にし、`null` なら nil にする。テストは3通り(時刻、null、キー無し)ある。`Case` を encode して保存し直す所は App と Core のどこにも無い(`JSONEncoder` を grep して確かめた)。encode すると nil のキーが落ちて「届いた」に化けるが、今は通らない道だ
- `ProtectedNotice` の優先順位は「届いていません」、「返事がまだ」、「伝えました」の順で、設計の段落と合う。解決すれば、届いていない相談も画面から消える
- `ResolveConfirmation` は、`choose` が `defer { asking = nil }` で1回しか case を返さない。そのため「解決にする」の処理のあとに閉じる処理の set(false) から `choose(.cancel)` が呼ばれても、2回は送らない。「やめる」と閉じたときは nil を返す。解決済みには確かめを出さない
- 書き換えた既存のテスト4件は、どれも #60 の決定と逆の期待を直したもので、弱まっていない。端末0台のテストは、投げること、NULL のまま残ること、あとで登録すれば tick で届くこと、まで確かめる形に強くなっている。新しいテストは、どれも実装を戻せば落ちる形だ(期待値が固定の文で、届いた場合と届かない場合の両方がある)
- 母や家族の名前、電話番号、メールは差分に無い。電話番号とメールの形で差分を grep して0件。スタブのドメインは `.example`、名前は「妹」「作者」だけ
- `.claude/rules/server.md` と `ios.md` との食い違いは見つからなかった。「安全」と返す道は増えていない。画面の文言は確かめの題が要約の1行、ボタンが1語の動詞で、説明は hint にある
