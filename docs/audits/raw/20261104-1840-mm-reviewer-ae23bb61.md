## 指摘(重い順)

### 1. 標準入力から `xargs` が足す引数を関門が見ない。force push、main への push、ブランチの削除、gh api の PUT が黙って通る(重い。フックの答えは再現済み、permissions の側は文書から判断)
`.claude/hooks/lib.sh` 324-326行は、フラグ無しの `xargs` を読み飛ばして奥のコマンドを読む。しかし `xargs` は標準入力の語をコマンドの後ろに足す。cwd が作業の木のときのフックの答えは次のとおり。
- `echo -f | xargs git push origin x` は quiet(実際に走るのは `git push origin x -f`)
- `echo main | xargs git push origin` は quiet(main への push)
- `echo --delete x | xargs git push origin` は quiet
- `printf '%s\n' -X PUT | xargs gh api repos/o/r/pulls/3/merge` は quiet(PUT でのマージ)
- 比べると、`echo origin | xargs git push --mirror` は BLOCK になる

permissions の文書(Wrappers の節)には「Bare `xargs` is also stripped」とある。外したあとの `git push origin x` は allow の `git push*` に当たり、deny の `git push* -f` には当たらない。`echo` は読み出しだけのコマンドなので確認なしで走る、と見ている。main ではそもそも `git push*` が allow になかったので、この形はこのブランチで初めて黙って通るようになる。
直し方の案は、`command_starts` が `xargs` を越えた先頭を覚えておき、その先頭の git push、gh api、gh issue/pr の書き込みは聞くこと。guard-private でも同じで、`cat /tmp/x | xargs gh issue comment 3 --body` は quiet になり、本文がスキャンされない。こちらは前から残っていた穴。

### 2. 「最後の cd」を追うのに、サブシェル、`cd -`、`popd`、`cd --` を正しく扱わない(中くらい。再現済み。前の版より後退した形がある)
該当は `.claude/hooks/guard-prod.sh` 57-68行。`here` が `(`/`)` の範囲を無視して進み、`cd -` を常にセッションの cwd へ戻すものとして扱い、`popd` を見ない。
- このリポジトリの main のチェックアウト(`~/develop/mimamori`)を cwd にした `(cd .claude/worktrees/harness-auto-allow && make verify) && git push` は quiet。実際には main のチェックアウトから push する。親のセッションが書きそうな、ありがちな形だ
- cwd が作業の木のとき、`cd <main> && (cd <work>) && git push` が quiet になる。前の版では ASK だった
- `cd <main>; cd <work>; cd -; git push` は quiet。前の版は ASK。`cd -` が戻るのは直前の dir(OLDPWD)なので、65行の注の「where the command started from」は事実と違う
- `pushd <main>; pushd <work>; popd; git push` は quiet。前の版は ASK
- `cd -- <main> && git push` は quiet。前の版も quiet だった

直し方の案は、`(` で `here` を積み、`)` で戻す。`cd -` は1つ前の `here` にし、`popd` も積んだものから戻す。扱えない形(`cd --`、変数)は前の版のように全部の基点を見て、聞く側に倒す。

### 3. `docs/harness.md` の「残っている穴」が1と2の形を書かず、「黙っては通らない」と言い切っている(中くらい。文書で確かめた)
`docs/harness.md` の「残っている穴」の段落に、「`gh api` の書き込み(PUT でのマージも含む)と main への push は `guard-prod.sh` が作者に聞くので、黙っては通らない」とある。1と2の形では通るので、直すか、穴として書き足す。前から残っていた `git --git-dir=<main>/.git push origin HEAD` と `GIT_DIR=<main>/.git git push origin HEAD` もここに入る。作業の木を cwd にすると quiet で、前の版も quiet だった。

### 4. guard-private の新しい振る舞いを確かめるテストが無い。足された1行は直す前から通る(軽い。テストで確かめた)
古い版のフック(64f5132)を新しい `scripts/test-hooks.sh` で流した。guard-prod の15件と guard-merge の4件(GH_REPO の確かめを含む)は落ちたが、`priv 2 "timeout 60 git commit --no-verify -m x"` は落ちなかった。テキストの判定(guard-private.sh 63-73行)が拾うからで、実装役の報告どおりだ。
この直しで実際に変わったのは gh のほうだ。`timeout 30 gh issue create --title t --body 090-1234-5678` と `nohup gh pr comment 3 --body 090-1234-5678` は、古い版では quiet、新しい版では BLOCK になる。古い版では、ラッパーを付けた Issue の書き込みはスキャンされずに通っていた。この差を押さえるテストを足すとよい。たとえば `priv 2 "timeout 30 gh issue create --title t --body Tanukiyama"`。

### 5. `command --` と `nohup --` を読み飛ばさない(軽い。Claude Code の側の扱いは文書に書いてないので分からない)
`command -- git push -f origin x` と `nohup -- git push -f origin x` は quiet になる。Claude Code がこの形のラッパーを外したあと、`-- git push ...` として照らすなら allow に当たらず確認が出る。どう扱うかは文書に書いていない。`--` も読み飛ばしておくと安全側になる。
