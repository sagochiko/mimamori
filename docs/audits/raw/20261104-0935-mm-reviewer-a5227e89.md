## 確かめて問題なかったこと

- マージの途中の pre-commit は、MERGE_HEAD と index の差分の足した行を見る。木の外のリポジトリで、本物の衝突(UU)を起こして3通りに解いた。main の行をそのまま残すと通る(pc=0)。手で新しい番号を書くと `f.md:2: phone number` で止まる(pc=1)。手でダミーの語を書くと `f.md:2: private term` で止まる(pc=1)。衝突を手で解いた行は取りこぼさない。
- このブランチが足した行は main に無いので、MERGE_HEAD と比べれば必ず差分に出る。過去にフックを通さずに入った行も、マージのときに改めて調べられる。前より緩くなるのは「main の同じファイルに同じ文字列で既にある行」だけで、これは方針どおりにあたる。
- main で消した行をブランチの側が衝突の解き方で残したときも、MERGE_HEAD に無い行として調べられる。
- MERGE_HEAD が無いふつうのコミットでは `base` が空になる。`${base:+"$base"}` は何も展開しないので、前と同じ `git diff --cached` になる。cherry-pick、revert、rebase はそれぞれ別の印(CHERRY_PICK_HEAD など)を使うので、前のまま HEAD と比べる。worktree の中でも MERGE_HEAD は worktree ごとに解決され、テストの mg の worktree で動いている。`git merge --squash` は MERGE_HEAD を作らないので、main の行も含めて全部調べる(厳しいほうに倒れる)。
- 除外は場所の文字列の行頭に固定している。text の経路では guard-private.sh が「the command (title and body)」「body file <道筋>」という名札を渡すので、除外には当たらない。範囲が広がるのは staged と history だけで、意図どおり。
- テストが本当に落ちるかを、木を git archive で手元の作業用フォルダに写し、scan-private.sh に変異を入れて確かめた(木のファイルは触っていない)。
