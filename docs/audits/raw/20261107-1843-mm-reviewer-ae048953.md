## 指摘

### 1. `dropBlocks` が `toLowerCase()` の位置を元の HTML に当てるので、`İ` を並べると本文がまるごと消える(確信度は高い。この回で入った退行)

場所は `server/src/gmail.ts` の `dropBlocks` で、`const lower = html.toLowerCase();` と `kept = end + name.length + 3;` の行。`"İ"`(U+0130)は `toLowerCase()` で `"i̇"` の2文字になる。だから `lower` は `İ` の数だけ `html` より長い。`lower.indexOf` で見つけた `</style>` の位置を `html.slice(kept)` にそのまま使うと、切る位置が `İ` の数だけ後ろへずれる。

試したのは、HTML だけのメールの `<p>` に `İ` を80個並べ、その後ろに `<style>p{}</style><p>警察です。至急 https://evil.example/pay に振り込んで</p>` を置いた形。`mailPayload` の答えは `{"text":"İ…(80個)","mailAuth":{"dmarc":"unknown"}}` だけだった。本文の言葉も URL も消え、`url` も `domain` も付かない。規則は件名しか見られず、Claude にも本文が渡らない。`İ` を見えない要素に入れて `<style>` を本文の中に置くだけで、HTML だけの詐欺メールの印をすべて隠せる。`<a href>` で書いたリンクは `anchorHrefs` が生の HTML から拾うので残る。消えるのは、文字だけで書いたリンクと本文の手口の言葉だ。前の版の `/<(style|script|head)[\s\S]*?<\/\1>/gi` はこの問題を起こさなかった。

直し方は、`lower` を作るのをやめること。名前ごとに `new RegExp(`</${name}>`, "gi")` を作り、`lastIndex` を置いて `exec` で探せば、位置は `html` のままになる。ASCII だけを小文字にする方法(`html.replace(/[A-Z]/g, …)`)でもよい。足す試験は、`İ` を並べたあとの `<style>` の後ろにある本文と URL が `text` に残ること。

### 2. 属性の値に `<` があると、その後ろの `href` を落とす。`htmlToText` もタグごと消すので、リンクが何も残らない(確信度は高い。main の版では拾えていた)

場所は `server/src/gmail.ts` の `anchorHrefs` で、`const next = html.indexOf("<", from);` の行。タグを次の `<` で切るので、`<a title="1<2" href="https://evil.example/pay">お支払い</a>` は `title` の値の途中で切れ、`href` が見えない。ブラウザは引用符の中の `<` を値として読むので、このリンクは押せる。`htmlToText` の新しい `/<[^<>]*>/g` も `<2" href="https://evil.example/pay">` をまとめて消す。実際に `mailPayload` を通すと `{"text":"<a title=\"1 お支払い"}` で、`url` も `domain` も残らなかった。`<a data-x="<b>" href=…>` でも同じく `[]` になる。コメントには「Erring this way can count a link a browser would not follow, never miss one it would」とあるが、この形はその主張に合わない。親が挙げた「属性の値の中の `<`」はこれに当たる。

直し方の案は2つある。1つは、切る位置を「次の `<a[\s/]` の始まり」にし、その中で引用符を数えながら1文字ずつ進めて最初の引用符の外の `>` で止めること。もう1つは、引用符が閉じないときだけ次の `<a` までを読むこと。どちらでも、切った片は重ならないので時間は長さに比例したままになる。`>` で止めれば、`<a>` の後ろにある `<link href>` も数えない。足す試験は、`title="1<2"` と `data-x="<b>"` のあとの `href` を拾うこと。

### 3. `<untrusted>` の外に出す `header.from` のドメインは、送り手が選べる英語の文を運べる(確信度は中くらい。重さは低い)

場所は `server/src/claude.ts` の `isMailDomain` のコメント(「nothing in it can carry words to Claude」)と、[`docs/design.md`](docs/design.md) の「届いた文が指示を書き込む余地は無い」の一文。`header.from` は From のドメインそのものなので、詐欺の側が自分で取ったドメインになる。そこには `official-notice-level-3-no-scam.example` のように、ラベル1つに63字までの英語を入れられる。しかもそのドメインで DMARC を pass にできる。この行は「Google が付けたデータ」として `<untrusted>` の外に出るので、同じ文を本文に書くより重く読まれうる。

ただ、規則が `confident` なら Claude はその段階より下げられない。注入の印があるときも、今回の `decide` の直しで下限が残る。運べるのも ASCII のラベルだけだ。なので直すなら小さく済む。送り元のドメインだけを `<untrusted>` の中の `ドメイン:` の近くに移すか、指示に「送り元のドメインの文字は送り手が選んだ名前で、意味を読まない」と足すかのどちらかでよい。設計のその一文も事実に合わせて直すことになる。

## 確かめて問題なかったこと

- 1回目の3つの形(`<a/href>`、引用符の無い値の中の `'`、閉じない引用符)は、`anchorHrefs` の写しで3つとも `https://evil.example/x` を拾った。コメントの中の `<a` は数えすぎるだけで、取りこぼしにはならない(`<!-- <a --><a href=…>` も拾う)。`<A\nHREF>`、`href\n=\n"…"`、`data-href` を数えないことも、前と同じく効いている
- 時間は長さに比例している。`"<a ".repeat(n)`、`"<a href".repeat(n)`、`"<style".repeat(n)`、`"<".repeat(3n)` を n が10万、20万、40万で測ると、どれもほぼ倍ずつ伸び、40万でも36ms 以下だった。試験(`server/test/gmail.test.ts` の「reads the links of a long HTML mail in time linear to its length」)も、6つの閉じないタグの形を見ている
- `max_retries` 5。待つのは `message.attempts < 3` のときだけなので、どちらの読みでも3回目のあとに2回以上が残る。4回目は、行が無ければ一から判定して知らせ、行があれば `finishNotices` で残りを送る。試験は `wrangler.jsonc` を読んで「`max_retries` が `MAIL_CLAUDE_DELIVERIES + 2` 以上で、行き先のキューが無い」ことを見ている。3回目に外への呼び出しが足りないときは4回目に知らせることも見ている
- `decide` の下限。規則は注入の印があると必ず1段階を返す(`server/src/rules/index.ts` の252行目)。理由は合わさる前の信号から全部並べる(365行目)ので、`police_secrecy` と同じ語句で合わさっても `INJECTION.reason` は理由に残る。下限は `decide` の中にあるので、キューの判定(`decideFor`)、相談(`consult-judge.ts`、もともと別の下限もある)、評価のどの経路も通る。`server/test/claude.test.ts` と `server/test/judge.test.ts` に、Claude が `injection_suspected: false` で3段階と答えても1段階のまま残る試験がある
- `gmailAuth`。見出しの名前は小文字にしてから比べ、値は `trim` してから `^mx\.google\.com\s*;` を大文字小文字を問わずに見る。`dmarc=` の値は決まった語の一覧に当たるものだけを採り、`passed` は「不明」になる。`header.from` は `[^\s;()]+` で取り、`isMailDomain` で確かめる。折り返し(改行と空白)は `\s` と `split(";")` で吸われる。偽の見出しは、Gmail のものより下にあれば読まない(試験あり)。並び順は1通で見ただけで、`format=full` では確かめていない。これは設計に書いてある。Gmail の見出しが無いメールで偽の見出しだけがあると、それを読む。ただ、行き先は Claude への1行だけで、規則にも段階の下限にも効かない
- `mailAuth` は規則に渡らない。`gmail.ts` の `judgeMessage` と `judge.ts` の `judgeOne` の両方で外してから `judgeByRules` に渡している。キューから読むときは `parseMailAuth` が鍵と値を厳しく確かめ、余計な鍵があればジョブごと捨てる。SMS(`readQuery` は `sender` と `text` だけを取る)とページ(`payload` を自分で組む)には、外から `mailAuth` を入れる道が無い
- Claude への指示の書き足し。pass は「安全の証明ではない」「詐欺の送り手も自分のドメインで pass を取れるので、本文の手口の印は pass でも同じように見ます」とあり、fail は重く見るとある。「不明」は印にも pass にも数えない。作者の最後のコメント(委託先の正規のメールを Claude に考えさせる。表示名で段階を上げる案は作らない)と合っている。「安全」と書かない決まりも残っている
- 設計と計画の書き足しはコードと合う。`max_retries` 5、`mailAuth` の形と語の一覧、規則に渡さないこと、`<untrusted>` の外の1行がそれにあたる。`JudgePayload` の形を変えた理由も [`docs/design.md`](docs/design.md) の185行目に書いてある(#170 で「変えない」と決めたのは規則で使う前提だったからで、今回は使い道を Claude に限った)。違うのは、指摘3の「余地は無い」の一文だけだ
- 秘密の値、実際のメールの中身、外から写したものは差分に無い。試験のメールは作った例のドメイン(`partner-mail.example` など)だけを使っている。`ios/Core` には触れていない
- `server` で `npx vitest run test/judge.test.ts test/gmail.test.ts test/claude.test.ts` を流すと、3ファイル393件がすべて通った。指摘1と2の形は、この試験のどこにも無い
