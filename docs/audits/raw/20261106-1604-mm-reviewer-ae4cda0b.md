## 指摘

### 1. 認証コードだけの SMS で、揺れたリンクや電話番号が付いた口止めが `null` になり、Claude も見ない(確度は高い、再現済み)

場所は [`server/src/rules/index.ts`](server/src/rules/index.ts) の335〜342行目(`genuineShape` と `signals.clear()`)と、[`server/src/inbound.ts`](server/src/inbound.ts) の28行目の `worthAsking`。

`codeOnly` の SMS では、「ほかの印が1つでも残れば元の文面」という条件が効かない場合がある。規則が拾えない書き方は、そもそも印を残さないからだ。印が何も残らなければ、口止めを消した結果は `CODE_ONLY_REASON` だけの `null` になる。`worthAsking` はこれをキューに積まないので、Claude は一度も見ない。main では `INJECTION` が当たり、1段階で家族に届いていた。

main の規則と 4075478 の規則に同じ文を `tsx` で流して比べた結果を貼る(作業の木は変えていない)。

```text
main=1 br=null  認証コード 1234。ご家族には言わないでください。smbc-kakunin[.]com で入力
main=1 br=null  認証コード 1234。ご家族には言わないでください。smbc-kakunin。com で入力
main=1 br=null  認証コード 1234。このコードはご家族にも言わないでください。〇三-一二三四-五六七八 へお知らせください
main=1 br=null  認証コード 1234。このコードはご家族にも言わないでください。電話 3-1234-5678 へ
main=1 br=null  認証コード 1234。このコードはご家族にも言わないでください。LINE ID: abc123 に送って
main=1 br=null  認証コード 1234。このコードはご家族にも言わないでください。kakunin@gmail.com に転送してください
main=1 br=null  認証コード 1234。このコードはご家族にも言わないでください。名義が事件に関わっています
main=1 br=null  確認番号 1234。この番号はご家族にも言わないでください。のちほど係の者が確認に伺います
```

[`docs/plan.md`](docs/plan.md) に足した一文は「後ろに印の無い文が続いても同じ」と受け入れている。ただ、そこで挙がっている例は動かす先の無い文だけだ。上の表のように、コードの送り先(揺れたリンク、漢数字の電話番号、LINE、アドレス)や、受け取りに来る人がいる文までは受け入れの範囲に入っていない。

直し方の案はこうだ。口止めを消したことで `null` になったときは `CODE_ONLY_REASON` を付けず、キューに回す。Claude が答えなければ `decideFor` が3段階にして誰にも知らせないので、本物の認証コードが迷惑フォルダに入ることも、家族に知らせが行くことも無い。費用は Claude を1回呼ぶ分だけで、詐欺なら Claude が拾える。plan の一文も、それに合わせて直すことになる。

### 2. 公式の送り元の見分けは From の表示名で騙せる(確度は高い、影響は中から低)

[`server/src/gmail.ts`](server/src/gmail.ts) の446行目は、`From` の中で最初に出てくる `<...@...>` を送り元にしている。`"<info@smbc.co.jp>" <x@evil.com>` のように表示名にアドレスを書けば、`info@smbc.co.jp` が送り元として渡る。もともと `From` を認証の結果(`Authentication-Results`)と突き合わせてもいない。このため `officialSender` は、送る側がいくらでも名乗れる値になっている。

公式の送り元のメールで口止めを消すと、次の文が `null` になる。

```text
main=1 br=null  gmail info@smbc.co.jp  暗証番号はご家族にも伝えないようにしてください。smbc-kakunin[.]com でご確認を
main=1 br=null  gmail info@smbc.co.jp  暗証番号はご家族にも伝えないようにしてください。担当がご自宅へキャッシュカードを受け取りに伺います
```

メールの `null` はキューに回り、Claude が見る。そこが指摘1より軽い点だ。それでも、Claude が答えなければ3段階になり、誰にも知らせない。main ではどちらも1段階で家族に届いていた。直すなら、送り元は最後の `<...>`(あるいは表示名を除いた addr-spec)から取る。さらに、`officialSender` を SPF か DKIM の通ったメールに限るのが確かだ。限るのが重ければ、指摘1と同じく「消したことで `null` になったら、Claude が答えないときに2段階で知らせる側」に倒す案もある。本文に書いたアドレスでは騙せないことは確かめた(`x@evil.com` から、本文に `info@smbc.co.jp` と書いても1段階のまま)。

### 3. 足した家族の型が、家族どうしの内緒話をさらに拾う(確度は高い、影響は小さい)

[`server/src/rules/phrases.ts`](server/src/rules/phrases.ts) の66行目は、理由を挟む形を10字まで受ける。そのため、main で `null` だった次の文が1段階になった。

```text
main=null br=1  息子は甘いものが好きだから内緒にしておいて、ケーキ買ってきた
```

依頼にあった「息子は忙しいから内緒にしておいてね」と、「娘は心配性だから内緒に」「息子も来るから内緒にしてね」「子供は寝てるから言わないでおくね」は、main でも1段階だった。main の8字の窓ですでに当たっていたもので、この直しで悪くなったわけではない。

家族からの SMS は連絡先にあるので、Message Filter を通らない。どれも確かでない1段階で、迷惑フォルダにも入らない。影響が出るのは、母が声の相談でこう言ったときで、家族に1段階で回る(`consult` でも1段階になることを確かめた)。理由の形を「心配」「動揺」「迷惑」のような、相手を気づかう語に絞れば、甘いもの、忙しい、寝ているといった話は外れる。マージを止めるほどではない。
