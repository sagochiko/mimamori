## 指摘

1. 送り元のドメイン部に `?`、`/`、`#`、全角の `＠` を入れると、規則は公式と読む。重さは中で、確かさは高い(手元で再現した)
   [`server/src/gmail.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/server/src/gmail.ts) 467行の `/^[^<>\s@"]+@[^<>\s@"]+$/` は、`@` のあとに来る文字の形を見ていない。規則の側は [`server/src/rules/index.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/server/src/rules/index.ts) 158〜159行で、送り元を NFKC にしてから最後の `@` で切り、`parseUrl` で `https://` を付けて URL として読む。だから、ドメイン部のうち URL のホストに当たる所だけが公式かどうかの判定に使われる。Issue の例と同じ本文(公式でないリンク付き)を `tsx` で `mailPayload`、`judgeByRules` の順に流した結果は次のとおり。

   ```text
   "scam@free-mail.example"                  -> level 1 confident true
   "Bank <scam@smbc.co.jp?x.evil.example>"   -> level 1 confident false
   "Bank <scam@smbc.co.jp/evil.example>"     -> level 1 confident false
   "Bank <scam@smbc.co.jp#evil.example>"     -> level 1 confident false
   "Bank <scam@evil.example＠smbc.co.jp>"    -> level 1 confident false
   ```

   RFC 5322 の dot-atom では `?`、`/`、`#` も atext に入る。なので `smbc.co.jp?x.evil.example` は、書き方としては正しいドメインになる。DMARC の組織ドメインは公開接尾辞の一覧で決まるので、このドメインの組織ドメインは `evil.example` で、詐欺の側が自分のドメインで DKIM を通せば揃う。全角の `＠` を入れた形では、Gmail から見たドメインは `evil.example＠smbc.co.jp` になり、規則から見ると `smbc.co.jp` になる。つまり、表示名の穴を塞いだあとも、From のアドレスを銀行のドメインとして偽らないまま、見出しの文字で確かさを外せる。この形は main の正規表現にもあったので、今回の変更で入った穴ではない。ただ Issue の目的と同じ穴であり、[`docs/design.md`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/docs/design.md) に足した段落の「#170 のあとに公式を名乗るには From のアドレスそのものを偽る必要があり」はこの形について事実と合わない。
   こうした From が Gmail の受信トレイまで届くかは、私には確かめられない(偽のメールを母の受信箱に送ることになる)。直し方は安い。`senderAddress` で、NFKC の前の生の文字のままドメイン部が `^[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)+\.?$` に合うときだけ送り元にし、合わなければ空にする。試験には上の4つの形を「送り元を空にする」側へ足す。

2. PR の「`make eval-rules` の gmail は main と同じ」は、この変更の確かめになっていない。重さは小で、確かさは高い
   [`eval/lib/score.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/eval/lib/score.ts) 145行は、例文の `sender`(例 `"三井住友銀行 <info@smbc.co.jp>"`)を From のまま規則に渡していて、`mailPayload` も `senderAddress` も通らない。なので、この変更で dev の数字が動くことはありえない。代わりに、dev の gmail の From 14種を `mailPayload` に通して確かめた。14種すべてで、山括弧の中のアドレスがそのまま送り元になった。本物の公式の From(`info@smbc.co.jp` など)が公式から外れることはない。PR の「確かめたこと」は、そう書き直すほうが正確になる。

3. 本物のメールで公式を外す形が少しある。重さは小で、直さなくてもよい
   次の2つの形は送り元が空になり、公式でなくなる。
   - アドレスのあとに注記を付けた `info@bank.example (Bank)`
   - 表示名を引用符で囲まずにカンマを入れた `Bank Support, Tokyo <info@bank.example>`

   今の銀行の知らせではどちらもまれで、設計に書いた「厳しい側に倒す」とも合う。気になるなら、カンマで空にする前に、末尾が `<addr>` で終わる形を先に見る手がある。

## 確かめて問題なかったこと

- 表示名を抜けて通る道を、手元と試験の両方で見た。次の形はどれも、表示名の中のアドレスが送り元にならない。
  - 引用符つきの表示名とエスケープ(`"(?:[^"\\]|\\.)*"`)
  - 全角の山括弧(`＜scam@smbc.co.jp＞`)。送り元にはなるが URL として読めず、公式にならない
  - 折り返し。`=?ISO-2022-JP?B?...?=\r\n <info@bank.example>` は正しくアドレスを取る
  - 大文字(`SMBC.CO.JP`)。公式と読まれるが、ドメインを偽る話で、Gmail の DMARC の側の問題になる
  - 経路つきのアドレス(`<@route:...>`)と、`@` が2つある形
- From の符号化した語を解かなくなったことで、ほかの所が壊れていないか。`from` を使うのは `mailPayload` の中だけだった。送り元は判定の重複を見る鍵([`server/src/judge.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/server/src/judge.ts) 155、386行)と、Claude に渡す `送り主:`([`server/src/claude.ts`](~/develop/mimamori/.claude/worktrees/issue-170-from-display-name/server/src/claude.ts) 288行)に使われ、もともとアドレスだけだった。表示名は家族のカードにも通知にも出ていない。`domain` は `normalizeDomain` で URL から取り、送り元の変な形には引きずられない。iOS の側に From の表示は無い。
- RFC 2047 の決まり(符号化した語は addr-spec の中に書けない)と、設計の段落のこの点の書き方は合う。
- 送り元の上限は gmail の500字と、キューの `FIELD_MAX_CHARS`(500)で揃っていて、キューの側で切られ直すことはない。
- 試験は落ちうる形になっている。PR の記録で、`gmail.ts` を main に戻すと11件が落ちたとある。期待する値は具体のアドレスか `undefined` で、試験の中で作ったもの同士を比べる形ではない。
- 試験と設計の例のアドレスは `.example` だけで、実在しうるアドレス、家族の情報、秘密は入っていない。`ios/Core` には触れていない。
- 段階を下げる道は無い。送り元が空になると公式でなくなり、確かさが付きやすくなる側にしか動かない。通知の宛先と共有の範囲にも触れていない。
