## 指摘

1. 母が参加した直後に、家族へ「通知が切られています」と誤って届く(確度は中から高。コードで見た。実機では見ていない)
   [`ios/App/CheckupNotifier.swift`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/ios/App/CheckupNotifier.swift) の `HeartbeatSender.report()` は、`authorizationStatus` が `.authorized`、`.provisional`、`.ephemeral` のときだけ真にしていて、`.notDetermined` は偽になる。参加の流れを追うとこうなる。`join` の `run(joining: true)` で route が変わる。route の見張り([`ios/App/AppModel.swift`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/ios/App/AppModel.swift) の95行目)が `cameToFront()` から `runCheckups()` を呼ぶ。`sendHeartbeat()` が許可のシートより先か同時に設定を読み、`.notDetermined` のまま `{ notifications: false }` を送る。`requestPushIfJoined()` が呼ばれるのは `run` が戻ったあと(135、140行目)だ。裏側の `reportSetting` は NULL から1への印を取るので、家族を作った人に「(名前)のiPhoneで、みまもりの通知が切られています」が1回届く。そのあと母が許可すると次の知らせで0に戻るが、戻ったことは家族に伝わらない。新しく入る家族ごとに毎回起き、審査員の体験でも最初に出る。`.notDetermined` は切られたとは数えない(真として送るか、決まるまで送らない)ようにし、Core 側で判定してテストを足すのがよい。

2. `watchHeartbeats` が Cron の1回の D1 の枠(`d1Remaining`)を見ていない(確度は高。コードで見た)
   [`server/src/heartbeat.ts`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/server/src/heartbeat.ts) の `watchHeartbeats` は、`d1Remaining` を一度も調べない。ほかの job はすべて、始める前と各項目の前に `d1Remaining` を見て、印を取る前に抜けている(`cases.ts` 400と414行目と485行目、`smiles.ts` 234と255行目、`gmail.ts`、`agents.ts`、`retention.ts`)。[`server/src/budget.ts`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/server/src/budget.ts) の冒頭の約束は「each job looks at d1Remaining before it starts one more item, so an item is never cut off halfway (a claim taken, its notice not sent)」だ。1人あたりの D1 は、印の UPDATE、`familyOf` の SELECT、`sendPush` の SELECT の3回で、印を戻すときは4回になる。`LAPSES_PER_TICK = 20` なので、最初の SELECT を入れて最大81回になる。前の job が枠を使い切った tick で D1 の上限に当たると、印の UPDATE のあとの `familyOf` か `sendPush` が投げる。印は戻らず、その途切れについて家族に二度と知らせない、という「出ないまま印だけ立つ道」ができる。うしろの `retention-sessions` も `d1Remaining < 2` で毎回飛ばされる。直し方は、ほかの job と同じく `HEARTBEAT_D1 = 4` のような見積もりを置き、関数の頭と各メンバーの印の前で `if (budget.d1Remaining < HEARTBEAT_D1) break;` とすること。`no_budget` で印を戻したあとも `break` すれば、同じ tick で無駄な D1 を使わずに済む。[`server/test/heartbeat.test.ts`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/server/test/heartbeat.test.ts) には D1 の枠のテストが無い。`new ExternalBudget(undefined, 3)` のように枠を小さくして、印が立たないまま次の tick に残ることを確かめるテストがほしい。

3. 通知を送る前に投げたとき、`reportSetting` の印が戻らない(確度は中。コードで見た)
   `reportSetting` で印を1にしたあと、`tellFamily` の中(`familyOf` か `sendPush` の SELECT)で D1 が投げると、印は1のまま残る。`POST /heartbeat` は500を返し、次の知らせでも `changes !== 1` で黙る。母が通知を戻して切り直すまで、家族に伝わらない。2の Cron 側も同じ形をしている。`try` で囲み、失敗したら印を NULL に戻すのが安全だ。起きる頻度は低い。

4. 低電力モードでも「アプリのバックグラウンド更新が切られています」と出るおそれがある(推測で、確度は低。確かめていない)
   `UIApplication.shared.backgroundRefreshStatus == .available` だけで判定している。低電力モードのあいだは、この値が `.available` 以外を返すと記憶しているが、一次情報では確かめていない。そうなら、電池が20%になって母が低電力モードを入れるたびに、家族へ「切られています」が届き、切っていない設定を母のせいにする文になる。作者の実機で低電力モードを入れて `backgroundRefreshStatus` を読むか、Apple の `backgroundRefreshStatus` の文書を確かめてほしい。当たっていたら、`ProcessInfo.processInfo.isLowPowerModeEnabled` のときは送らないか、文を分ける。

5. `docs/plan.md` のタスク17の「渡すもの」が古いまま(確度は高。文書で見た)
   [`docs/plan.md`](~/develop/mimamori/.claude/worktrees/issue-19-checkup/docs/plan.md) の541行目は今も「`POST /heartbeat`(端末の鍵で呼ぶ。中身は時刻だけで、空き容量は送らない)」で、158行目の API の表(2つの真偽)と食い違っている。541行目も新しい形に直すべきだ。

## 確かめて問題なかったこと

- 家族への決まった文の呼び方。裏側の文はどれも `display_name` を使っていて(`LAPSE_TEXT(name)`、`NOTIFICATIONS_OFF_TEXT`、`BACKGROUND_OFF_TEXT`)、「母」は固定で書いていない。「母」はテストで付けた名前にしか出てこない。既存の `smiles.ts` の `今朝は${family.name}の笑顔がまだです` や `cases.ts` の `nameOf` と揃っている。見守られる人は招待から入るので `displayName(…, true)` で空にならず、`nameOf` の代わりがなくても名前が抜けた文にはならない。iOS 側の家族向けの文言にも「母」は無かった

- `watchHeartbeats` の二重送信と行き違い。印の UPDATE に `heartbeat_at <= ?` が入っているので、SELECT のあとに知らせが届いたメンバーには送らない。印のあとに知らせが届いて NULL に戻ったときは、戻す UPDATE が `= now` の条件で何もしない。家族の端末に鍵が無いときは `true` が返って印が残るので、同じメンバーが毎回の tick の頭を埋めることもない
- `HEARTBEAT_LAPSE_MS` は48時間で、一度も知らせていない端末(`heartbeat_at IS NULL`)は数えない。plan の表のとおり
