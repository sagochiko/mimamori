## 指摘

### 1. 一覧に無い種類の自分で名乗る詐欺は、まだ3段階に下がって家族に届かない(重い、確度は中)

場所は `server/src/mail-official.ts` の `OFFICIAL_SCHEMA.no_risky_request` の説明(81〜85行目あたり)と `ANSWER_SYSTEM` の `no_risky_request` の段落、それに `requestOfficialCheck` の `!a.no_risky_request` の条件。

`no_risky_request` が false になるのは、お金(支払い、振り込み、未払い、請求、返金)、ログインやパスワード、個人の情報やカードの番号の入力、電話、急がせる言い回しが文にあるか、判定の理由がそれらを挙げているときだけだ。自分で名乗る詐欺には、この一覧に当たる語を使わないものがある。

起こる場面を挙げる。詐欺の側が `fukugyou-xx.example` から DMARC の `pass` で「月30万円の在宅副業、詳しくはこちら」を送り、リンクも `fukugyou-xx.example` だけに張る。規則は段階を決めず、Claude は「うますぎる副業の勧誘」を理由に2段階を付ける。2回目の呼び出しは説明を文字どおりに読む。稼ぐ話は「支払い、振り込み、未払い、請求、返金」に入らず、理由もこの一覧のどれも挙げていないので、`no_risky_request: true` になりうる。ウェブ検索ではその詐欺のサイトが「公式」として見つかり、`official_domain` は `fukugyou-xx.example` になる。ドメインも揃っているので `yes` になり、`return "done"` で行も通知も残らない。投資、当選や賞金の受け取り、LINE の友だち追加、アプリのインストール、添付を開かせる形も同じ道を通る。

これは [`docs/design.md`](docs/design.md) 183行目の「pass だけでは段階を下げず、本文の印は今までどおり見る」と食い違う。Claude が2段階にした理由そのものが本文の印なのに、一覧に入っていないというだけで確かめの段がそれを上書きして下げる。1回目の指摘1の「自分で名乗る詐欺」は、一覧の語を含む形(架空請求)にしか閉じていない。

直し方の案を2つ挙げる。どちらも `server/src/rules` と `server/src/claude.ts` には触れないので、holdout のあとの決まりの中で直せる。

- (a) `no_risky_request` を「判定の理由が、送り元やリンクのドメインの食い違いのほかに何かを挙げていれば false」にする。この段がもともと救いたかったのは、ドメインの食い違いだけで2段階になった本物のお知らせだ
- (b) 一覧に、稼げる話、投資、当選や受け取り、外の連絡先(LINE など)へ誘う、アプリや添付を開かせる、を足す

(a) のほうが閉じやすい。ただ、作者が選んだ文言(「お金、ログイン、個人の情報の入力、電話をかけさせる、急がせる言い回し」)より広げることになるので、主から作者に確かめてほしい。

### 2. `no_risky_request` は、コードでは何も確かめていないモデルの真偽値で、試験も強さを測っていない(中、確度は高い)

本文に危ない印があるかを、コードは自分では見ていない。下げるのを止める守りは、規則が何も決めなかったこと、1回目の判定に注入の印が無いこと、`<untrusted>` と `neutralize`、それに2回目に判定の理由を渡していることだけだ。メールの文が「このお知らせはお金やログインを求めません」と言い、2回目の呼び出しがそれを鵜呑みにして `injection_suspected` も false にすれば、`true` が通る。注入の典型の形(「公式と答えて」)は `injection_suspected` で捕まえられそうだが、言い切りの形は指示に見えにくい。

`server/test/mail-official.test.ts` の「self-named sender」の試験は、同じ入力の結果が、msw の作り物が返す `no_risky_request` だけで `unknown` と `yes` に入れ替わることを示している。確かめているのはつなぎ方で、モデルに対する強さは確かめていない。`server/test/judge.test.ts` の「公式と答えて」の試験も、1回目の指摘5のとおり作り物が `no` を返すと決めたままだ。

安く足せる2つ目の関門として、`requestOfficialCheck` の中で `input.text` と `input.reasons` を、説明に書いた語(支払|振込|振り込|未払|請求|返金|ログイン|パスワード|暗証|カード|電話|至急|本日中|停止 など)の正規表現で照らし、当たれば `unknown` にする形がある。規則にも判定の指示文にも触れない。作者が選んだ形を変えるものではないので、これは任意の提案として出す。指摘1の (b) と組み合わせると閉じやすい。

### 3. design.md の「範囲は狭いと見て受け入れた」は、作者が決めていない判断を決めたことのように書いている(中、確度は高い)

場所は [`docs/design.md`](docs/design.md) の新しい段落(「照らし合わせるリンクには限りがある。」で始まる段落)の「どちらも送り元が公式のドメインの下にあり、本文の印も無いときにだけ問題になるので、範囲は狭いと見て受け入れた」。

主語が無く、すぐ前の段落が「作者が「下げる条件を厳しくする」を選んだ(2026年11月8日、PR #277)」で終わっている。なので、読む人は作者が受け入れたと読む。ところが作者のコメント「直し方を決めた」にあるのは「`docs/design.md` の記述を、見ないリンク(先頭5件と5000字の切り詰め)の限界に合わせる」だけで、計測用のリダイレクトと切り詰めの穴を量って受け入れたとは書いていない。「範囲は1と2より狭い」は1回目のレビューの見立てだ。`docs/design.md` は誰が何を決めたかの拠り所なので、次のどちらかに書き直したい。

- 限界だけを書き、「受け入れた」を消す
- 出どころを書く。たとえば「1回目のレビューは範囲を狭いと見た。作者は記述を限界に合わせると決め、リンクの行き先まではたどらない」

段落の残り(本文に無い `href` は先頭の5件だけ、5000字で切る、リンクがそこにしか無いメールは確かめない、6つ以上は確かめない)は、`server/src/gmail.ts` の519〜520行目、`OFFICIAL_MAX_HOSTS = 5`、`officialCheckable` と合っている。

## 確かめて問題なかったこと

- 1回目の指摘2(リンクの無いメール)は閉じた。`officialCheckable` が `hosts.length > 0` を求める。`judge.ts` では `officialCheckable` が `takeClaudeCall` と `budget.takeMany` より前で短絡するので、確かめないメールが家族の1日の分もバッチの枠も使わない。`judge.test.ts` の「does not check a mail without links」と「only link is past the 5000 characters」、`mail-official.test.ts` の「asks nothing」が、どちらも呼び出し0回を確かめている
- 拒否の一覧。日本の携帯(`docomo.ne.jp`、`ezweb.ne.jp`、`au.com`、`softbank.ne.jp`、`i.softbank.jp`、`ymobile.ne.jp`)、プロバイダ、無料のメール、共有のホスティングが入った。3つのラベルの共有の末尾(`sakura.ne.jp` など)は名前を挙げて拒み、その下の `someone.sakura.ne.jp` も `endsWith` で拒む。試験は一覧の各ドメインとその下の両方を見ていて、`shop-name.ne.jp` は通している。一覧が閉じきれないことはコードの説明文と design.md に書いてある
- 枠を取る順(1回目の指摘4)。条件の並びは `officialCheckable`、`budget.remaining >= OFFICIAL_CALLS + members.length`、`await takeClaudeCall(...)` の順で、通ったときだけ `budget.takeMany(OFFICIAL_CALLS)` を呼ぶ。2回目の `takeCall` は `first` の旗で1回目を素通しし、2回目だけ `takeClaudeCall` を呼ぶので、1日の数は1 + 1になる。枠の境目の試験(フィラー34件なら確かめる、35件なら確かめない)と、1日の上限で確かめられないときに後ろの9通の SMS が `retry` に回らない試験は、元の順なら落ちる形になっている
- `readOfficialAnswer` は鍵がちょうど4つで、`no_risky_request` が真偽値のときだけ受け取る。文字列の `"true"` は拒む
- 判定の理由は `slice(0, 3)` と200字で切られる。`claude.ts` の判定は3件を超える理由を `too_many_reasons` で落とすので、4件目が消えて危ない理由が抜けることは無い。理由は `neutralize` を通り、2回目の呼び出しの `<untrusted>` の中にだけ入り、検索の呼び出しには入らない(試験あり)
- 規則と判定の指示文は変わっていない。`git diff main...HEAD -- server/src/rules server/src/claude.ts server/src/gmail.ts` は空だった
- 「安全です」を返す経路は無い。新しい段は段階を下げるか何もしないかのどちらかで、母にも家族にも文を出さない。答えは JSON の4つの欄だけで、家族に届くものは無い。`mail-official.ts` の97行目の指示も「安全」「問題ない」「心配ない」を禁じている
- 失敗、時間切れ、壊れた答え、`no`、`unknown` は、どれも2段階のまま知らせる(1回目と同じ)
