## 指摘

### 1. 直すべき。最初の知らせが予算切れや上限超えで落ちると、30分後まで家族に届かず、やり直しもされない

[`server/src/cases.ts`](server/src/cases.ts) 197行目、207行目から225行目。

`openCase` は `budget` を省くと毎回 `new ExternalBudget()`(40枚)を作る。計画のつなぎ目は `openCase(env, alertId)` なので、タスク6の Queues の受け手はこのまま呼ぶ見込みが高い。1回の呼び出しで10件のメッセージを処理すると、Claude の呼び出し10件、母への「開かないで」10件、`openCase` ごとの家族への知らせ(家族2人と母1人の家族なら1件あたり2件)で、共有の予算を通らない外への通信が50件に届く。上限を超えた `fetch` は例外になり、`sendPush` はそれを `failed` として返すだけになる。

明示して共有の予算を渡した場合も、足りなければ `sendPush` は全員を `no_budget` で返す。[`server/src/push.ts`](server/src/push.ts) 150行目の説明は「呼び手があとで知らせ全体をやり直せる」と書いているが、`openCase` は `notify` の結果を見ずに捨てる。しかも相談の行は知らせより前に入っているので、キューが同じメッセージをやり直しても `inserted.meta.changes` が 0 になり、2回目は知らせを送らない。

どちらの道でも、ニセ警察の相談の最初の知らせが黙って消え、家族が知るのは30分の見張りが動いたときになる。そのあいだ母の画面は「家族に伝えました」と出し続ける。主役の場面で一番困る遅れ方だ。

直し方の案。`budget` を省けない引数にする。行を入れる前に家族の届く端末の数だけ `takeMany` で枠を取り、取れなければ例外にしてキューにやり直させる。テストは「予算が足りないと相談を開かず例外になり、次の呼び出しで開いて知らせる」を1件足せば落ちるようになる。

確かさは高い。コードの流れはファイルで確かめた。上限超えの `fetch` が例外になることは Cloudflare の Limits の記述に基づく(依頼文で確かめ済みとされた範囲)。

### 2. 軽い。受け持ちが家族を抜けると、その相談は誰も動かせないまま止まる

[`server/src/families.ts`](server/src/families.ts) 177行目、[`server/src/cases.ts`](server/src/cases.ts) の `relay` と `resolveCase`。

妹が引き受けたあとに家族を抜けると、`members` の行だけが消え、`cases.assignee_member_id` は残る。相談は `accepted` のままなので、ほかの家族は `relay` も `resolve` もできず(403)、30分の見張りも `state = 'notified'` しか見ないので動かない。母の画面は最長3日「家族が見ています」と出し、AI の案内も止まったままになる。抜ける操作が期間中に起きることは少ないので軽いとした。直すなら、抜けるときにその人が受け持つ `accepted` の相談を `notified` に戻す(`assignee_member_id` と `accepted_at` を空にする)。確かさは高い(SQL を読んで確かめた)。

### 3. 軽い。返事の文字数の数え方が iOS と裏側で違い、絵文字を含む返事が「つながりません」になる

[`ios/App/Views/CaseCardView.swift`](ios/App/Views/CaseCardView.swift) 179行目と207行目、[`server/src/cases.ts`](server/src/cases.ts) 282行目。

iOS は書記素で数え(`String.count`)、裏側は UTF-16 の単位で数える(`length`)。「👍」を150個と「あ」を50文字の返事は、画面では 200/200 で送れるが、裏側では 350 として 400 を返す。`Problem` は 400 を `unreachable` に落とすので、家族には「つながりません」と出て理由が分からない。直すなら、裏側を `[...text].length` で数えるか、iOS を `utf16.count` で数える。確かさは高い(上の実測)。

### 4. 軽い。読み上げのあと音声セッションを閉じないので、ほかのアプリの音が小さいまま残る

[`ios/App/ReplySpeaker.swift`](ios/App/ReplySpeaker.swift) 15行目から17行目。

`.duckOthers` でセッションを有効にし、読み終えても `setActive(false)` を呼ばない。ほかのアプリの音を下げる効果はセッションを閉じるまで続くので、母がラジオや動画を流していると、返事を読んだあとも小さいまま戻らない。`AVSpeechSynthesizerDelegate` の `didFinish` で、続きが無ければ `setActive(false, options: .notifyOthersOnDeactivation)` を呼べば戻る。確かさは中くらい(Apple の AVAudioSession の仕様からの推測で、実機では見ていない)。

### 5. 軽い。返事を送れなかったとき、家族に何も出ない見込み

[`ios/App/Views/CaseCardView.swift`](ios/App/Views/CaseCardView.swift) の `RelayComposer`、[`ios/App/Views/RootView.swift`](ios/App/Views/RootView.swift) 18行目。

失敗の知らせは `RootView` の `.alert` で出すが、そのとき `RelayComposer` のシートが上に出ている。SwiftUI はシートを出している画面の下からはアラートを出せないことが多く、家族からは「送る」が押せる状態に戻るだけに見える。推測で、確かめていない。確かめるなら、スタブの `relay` を 500 にしてシミュレータで「送る」を押す。直すなら、シートの中に `.alert` を付けるか、送れなかったときの短い1語(「送れません」)をシートに出す。

### 6. 軽い。30分の見張りと引き受けが入れ違うと、母に通知が逆の順で届く

[`server/src/cases.ts`](server/src/cases.ts) 384行目から405行目。

見張りが `renotified_at` を立ててから APNs に送るまでのあいだに妹が引き受けると、母には「妹が見ています」のあとに「家族から返事がまだ。急ぐなら電話して」が届きうる。画面は `accepted` を正しく出すので、ずれは通知の列だけで、窓も APNs の往復1回ぶんと短い。直さなくてもよいが、気になるなら母への通知の直前に状態を読み直す。確かさは高い(順序から導いたもので、起こる頻度は低い)。

### 7. 軽い。計画の「D1 の表」に `ai_reply` が無い

[`docs/plan.md`](docs/plan.md) 108行目、[`server/migrations/0002_case_ai_reply.sql`](server/migrations/0002_case_ai_reply.sql)。

つなぎ目の約束の表と実際の表がずれている。タスク12が `deliverAiReply` を呼ぶときの手がかりになるので、表に足しておくとよい。本番の D1 への `0002` の適用は作者の確認が要る。

## 問題なしと確かめたこと

- 引き受けの1人勝ち。`UPDATE ... WHERE id = ? AND family_id = ? AND state = 'notified' RETURNING id` の1文で決まり、負けた人には 409 と `assignee`(名前つき)が返る。テストは `Promise.all` で2人同時に呼び、条件を外すと `[200, 200]` になって落ちる形になっている。別の家族の人は 404 で、状態が `notified` のままかも確かめているので、`family_id` の条件を外しても落ちる
- AI の案内を止める印。状態そのものを印にし、`deliverAiReply` は `UPDATE cases SET ai_reply = ? WHERE id = ? AND state = 'notified'` の1文で確かめと記録を兼ねる。引き受けのあとに届いた答えは記録されず、`delivered: false` と受け持ちの名前が返る。条件を外すとテストが落ちる。呼び手(タスク12)はまだ無いので、母へ実際に届かないかは、タスク12が `delivered` を見て送るかどうかに懸かっている
- 30分の見張り。`renotified_at IS NULL` で1回だけにし、母には `NO_REPLY_YET`、家族(`role = 'family'` だけ)にはもう一度送る。状態は `notified` のまま変えない。予算が家族全員に足りなければ枠を取らずに次の回へ回し、黙って捨てない。後の回で再送しないこと、29分の相談と引き受け済みの相談に触れないこと、予算2では送らず40で3件送ることをテストが確かめている
- Cron の順。`runScheduled` を JOBS の順に1つずつ流すように変え、見張りを先頭に置いた。見張りが3件使ったあとに掃除が37件使うテストがあり、順を入れ替えると落ちる
- `sendPush` の予算。届く端末の数だけまとめて取り、足りなければ誰にも送らず `no_budget` を返す。トークンの無い人は枠を使わない。テストあり
- 受け持ち以外の締め出し。`relay` は確かめと挿入が1文で、受け持ち以外は 403、引き受け前と解決後は 409。`resolveCase` も受け持ちだけ。別の家族の端末は `requireMember` の `family_id` で絞られ、`GET /cases` に別の家族の相談が出ないことをテストしている
- 「解決」「対応中」を出さないこと。母の画面の `ProtectedNotice` は `notified` のあいだ「家族に伝えました」か「家族から返事がまだ。急ぐなら電話して」だけを出し、`resolved` でも状態の文字を出さない。時刻を変えて7通り試すテストがある。端末の時計でも30分で切り替わるので、見張りの通知が届かなくても画面は変わる
- 母の番号。`ProtectedPhoneStore` は家族の端末の `UserDefaults` に置くだけで、`APIClient` にも `Session` にも渡る道が無い
- ログと D1。ログに出るのはエラーの名前と仕事の名前だけで、本文や名前は出ない。`relays` と `ai_reply` は `cases` と一緒に、30日の掃除と「すべて消す」で消える(`retention.ts`、`families.ts` の既存の削除で覆われている)
- 画面の文言。家族のカードは段階、要約、理由、AI の答え、返事、「(名前)が対応中」、1語のボタン、`n/200` の名札だけで、説明はすべて `accessibilityLabel` と `accessibilityHint` にある。母の画面も状態、伝えたこと、返事、マイクだけ
- 読み上げは1回だけ。`ReplyAnnouncer` が読んだ返事の ID を `UserDefaults` に残し、`AppModel` は `@MainActor` なので、1分ごとの読み込みと通知の受け取りが重なっても二重に読まない。テストで、同じ返事を2回目に渡すと空になること、作り直しても読まないことを確かめている
- 指示の混入。通知先は `members` の `family_id` と `role` だけで決まり、Claude の答えや届いた文面では変わらない。危なさの段階を下げる道も無い
- ルール。`ios/Core` は Foundation だけを import している。秘密、実在の家族の情報、外から写したコードは見当たらない。スタブとテストの名前は「母」「妹」「作者」だけ。dev-log の追記にも個人の情報は無い
