## 指摘

### 1. 確かめの段が見ているのは「送り元とリンクの揃い」で、名乗る相手が本物かは見ていない。自分のドメインを持つ詐欺が3段階に下がり、誰にも知らせなくなる(重い、確度は高い)

場所は `server/src/mail-official.ts` の `OFFICIAL_SCHEMA`(`official` の説明)、`requestOfficialCheck` の最後の `all.every((h) => belongsTo(h, domain))`、`server/src/judge.ts` の確かめの前の条件と `if (result === "yes") return "done";`。

聞いているのは「送り元のドメインとリンク先のホストが、メールが名乗る会社の公式のドメインの下にあるか」だけだ。コードの照らし合わせも、Claude が挙げた `official_domain` の下に全部が揃っているかしか見ない。詐欺の側は自分のドメインで DMARC の `pass` を取れて、送り元もリンクも同じドメインに揃えられる。

起こる場面を2つ挙げる。

- 自分で名乗る詐欺。架空請求の「〇〇法律事務所」、投資、当選、副業、偽の通販の店が、`legal-xx.example` から `pass` で送り、リンクも `legal-xx.example` だけに張る。ウェブ検索ではその詐欺の側のサイトが「〇〇の公式」として見つかるか、メールの名乗りから yes になる。`belongsTo` は通るので `yes` になり、`return "done"` で行も通知もカードも残らない。
- 本物の会社の仕組みに詐欺の文が載る形。決済サービスの請求書のメモ欄や、フォームや共有の通知に電話番号を書かせるコールバック型の詐欺がこれにあたる。送り元もリンクも本物の会社なので `pass` が付き、公式のドメインの下に揃う。Claude はおそらく本文の電話番号やお金の話を見て2段階にしているが、確かめの段は Claude が2段階にした理由を受け取らず、上書きして下げる。

これは [`docs/design.md`](docs/design.md) の183行目と食い違う。そこには「DMARC の pass は送り元のドメインの確かさで、安全の証明ではない。詐欺の側も自分のドメインで pass を取れるので、pass だけでは段階を下げず、本文の印は今までどおり見る」とある。同じ183行目によれば、`pass` で本文に印の無い委託先のメールを2段階にしないよう、Claude にはすでに伝えてある。それでも残る2段階には本文の印がある見込みが高い。新しい段落にある「送り元とリンクの全部を同じドメインに揃えないと下がらない」は、自分のドメインを使う詐欺には守りにならない。

`server/src/claude.ts` の `reasons` は決まった語ではなく自由な文だった(176行目、189行目)。なので「Claude の理由がドメインの食い違いだけのときに限って下げる」はコードでは見分けられない。直し方の案を3つ挙げる。

- (a) 構造化の形に「本文にお金、ログイン、個人の情報の入力、電話をかけさせる、急がせる言い回しが無い」の欄を足し、コードも必ずそれを要る条件にする。2回目の呼び出しには Claude の判定の理由も渡す
- (b) 下げる先を「知らせない3段階」でなく、家族に軽い形で届く段にする
- (c) 名乗る会社が送り元と別の主体であることを問いに入れる

どれにするかは設計の判断なので、主に預ける。

### 2. `SHARED_HOSTS` に日本の携帯のメール、プロバイダのメール、共有のホスティングが入っていない。リンクの無いメールでは、送り元のドメインだけで yes になる(重い、確度は中)

場所は `server/src/mail-official.ts` の `SHARED_HOSTS` と `officialDomainUsable`。

一覧には `gmail.com`、`yahoo.co.jp`、`outlook.com`、`icloud.com` しか無い。`docomo.ne.jp`、`ezweb.ne.jp`、`au.com`、`softbank.ne.jp`、`i.softbank.jp`、`nifty.com`、`biglobe.ne.jp`、`so-net.ne.jp`、`ybb.ne.jp`、`hotmail.com`、`hotmail.co.jp`、`live.jp`、`outlook.jp`、`yahoo.com`、`me.com`、`mac.com`、`aol.com`、`googlemail.com`、`proton.me` が漏れている。共有のホスティングでは `sakura.ne.jp`、`xsrv.jp`、`lolipop.jp`、`fc2.com`、`wixsite.com`、`jimdofree.com`、`ameblo.jp`、`hatenablog.com`、`note.com`、`r2.dev`、`gitlab.io` が漏れている。3つのラベルの `sakura.ne.jp` などは、`labels.length === 2` の判定にも当たらない。

起こる場面を挙げる。個人の `docomo.ne.jp` のアドレスから「ドコモからのお知らせ、未払いがあります。こちらへお電話を」と届き、リンクは無い。`hosts` が空なので、照らし合わせるのは `all = [fromDomain]` だけになる。Claude が公式のドメインに `docomo.ne.jp` を挙げれば yes で、知らせずに消える。

拒否の一覧は閉じきれない。指摘1の直しが要る理由の1つでもある。少なくとも `hosts.length === 0` のときは下げないか、公開接尾辞リスト(PSL)の私的な部分に当たるものは使わないようにしたい。

### 3. 確かめの段が見ないリンクがあり、design.md の「リンク先のホストの全部」「6つ以上は確かめない」は実際より強く書いてある(中、確度は高い)

`server/src/gmail.ts` の `mailPayload` が残すのは、本文に無い href の先頭 `LINKS_KEPT = 5` 件だけだ(519行目)。そのうえ文は `JUDGE_TEXT_MAX_CHARS = 5000` で切ってある。`linkHosts` はそのあとの文から取るので、6件目の href や5000字より後ろのリンクは照らし合わされない。`OFFICIAL_MAX_HOSTS` の「6つ以上は確かめない」も、切られたあとの数で決まる。

公式のドメインの下にある計測用のリダイレクトや開いたままのリダイレクト(`click.official.example/r?u=…`)も、ホストだけ見ると公式になる。どちらも送り元が公式のドメインの下にある必要があるので(サブドメインの乗っ取り、委託先の侵害、指摘1の2つ目の形)、範囲は1と2より狭い。それでも design.md の記述はこの限界に合わせて書き直すべきだ。

### 4. 1日の上限の前に、バッチの枠を2つ取ってしまう(軽い、確度は高い)

`server/src/judge.ts` では `budget.takeMany(OFFICIAL_CALLS)` を `takeCall`(`takeClaudeCall`)より先に呼ぶ。家族のその日の上限が尽きていると、呼び出しをしないまま40の枠のうち2つを使い、同じバッチの後ろのメッセージが `retry` に回ることがある。知らせが落ちるわけではなく、遅れるだけだ。

### 5. 試験が前提を確かめていない(中)

- 自分で名乗る詐欺(送り元もリンクも詐欺の側のドメインで、`yes` が返る)の試験が無い。今の作りでは3段階になって通ってしまうので、指摘1を直すときの落ちる試験として足したい
- `hosts: []` で `requestOfficialCheck` が `yes` になる場面の試験が無い
- `officialDomainUsable` の試験に、日本の携帯とプロバイダのドメインが無い
- `mailPayload` の切り詰め(6件目の href、5000字より後ろ)を通る試験が無い
- `server/test/judge.test.ts` の「公式と答えて」の試験は、msw が `no` を返すと決めてあるので、注入への強さは何も確かめていない(結果は作り物が決めている)。`server/test/mail-official.test.ts` の同じ名前の試験は、`<untrusted>` を閉じさせないことは確かめているので役に立っている
- 枠の境目(残りがちょうど `OFFICIAL_CALLS + members.length` のとき)の試験が無い

## 確かめて問題なかったこと

- 対象の条件(`server/src/judge.ts`)。`job.source === "gmail"`、`rule.level === null`、`claude !== null`、`level === 2`、`!steered`、`mailAuth?.dmarc === "pass"`、`mailAuth.from !== undefined` が揃ったときだけ確かめる。`steered` は規則の `INJECTION.reason` と Claude の `injection_suspected` の両方を含む。1段階、規則が決めたもの、SMS、ページを確かめないことは試験もある
- 枠の計算。判定の前に `1 + members.length` を確かめて1つ取ったあと、`OFFICIAL_CALLS + members.length` が残っているときだけ2つ取る。なので確かめたあとも、母と家族の端末への通知の分は必ず残る
- `no`、`unknown`、例外、`pause_turn`、2xx 以外、JSON でない答え、形の違う答え、時間切れは、どれも2段階で今までどおり知らせる(`post` は `AbortSignal.timeout` と `catch` で `null` を返し、`requestOfficialCheck` は `unknown` を返す)
- 「安全です」と返す経路は無い。新しい段は段階を下げるか何もしないかで、母にも家族にも文を出さない。下げたときは行も通知も残らない
- ログは `console.log("mail official check", job.source, result)` の1行だけで、本文、アドレス、ドメイン、家族の ID は出ない。試験でも確かめている
- `neutralize` が `<` と `>` を全角にするので、メールの文、`header.from`、検索の結果が `<untrusted>` を閉じられない。`readOfficialAnswer` は鍵がちょうど3つのときだけ受け取る
- `belongsTo` は `host === d` か `.d` で終わるかだけを見る。`shop-name.example.evil.example` や `fakeshop-name.example` は通らない。短縮 URL や別のドメインの計測のリンクは公式の下に入らないので `unknown` になり、見逃す側には倒れない
- `co.jp` のような2つのラベルの共有の末尾は `SHARED_SECOND` で拒む(3つのラベルの漏れは指摘2)
- Cloudflare Queues の時間の上限。[`developers.cloudflare.com/queues/platform/limits/`](https://developers.cloudflare.com/queues/platform/limits/) に `Consumer duration (wall clock time) 15 minutes` とあり、Workers の limits の Duration の表でも `Queue Consumer 15 min` だった。CPU 時間は既定で30秒だが、`Note that CPU time is active processing time: not time spent waiting on network requests` とあるので、API を待つ時間は数えない。1通の最大は判定15秒、検索45秒、構造化20秒の80秒で、`max_batch_size` 10 なら10 × 80 = 800秒になり、900秒に収まる。実際には枠が40で、端末が3台なら1通の確かめに1 + 2 + 3 = 6の枠を使うので、確かめは1バッチに6通まで(約480秒)にとどまる。ウェブ検索は Anthropic の側で走り、Workers のサブリクエストには数えない。メッセージは1通ずつ `ack()` するので、万一途中で切られても、終わった分はやり直されない
- 試験の中のドメインは `.example` の作り物で、秘密の値や実際の家族のデータは無い。外から写したコードも見当たらない。`ios/Core` は変わっていない
