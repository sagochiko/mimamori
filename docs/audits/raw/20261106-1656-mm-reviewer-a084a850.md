## 指摘

直すべき重さのものは無い。軽いものが3つある。

### 1. dev-log の「dev でも本物が1段階になった件は0だった」は、dev に該当する本物が1件も無いので裏付けにならない(確度は高い、影響は小さい)

[`docs/dev-log.md`](docs/dev-log.md) で足した項目の、最後から2つ目の段落にある一文。dev の本物(`is_scam: false`、consult を除く23件)を今の規則に通すと、1段階は0件だった。ただ、「家族」と「言わない/伝えない/教えない/話さない」を含む本物も0件だった(スクラッチパッドの `probe3.ts` で数えた。出力は `{ genuine: 23, level1: 0, secrecyLike: 0 }`)。

文としては正しい。それでも、読んだ人は「本物の口止めの文が dev で困っていない」と受け取りやすい。実際には、測る例が dev に無いだけだ。直すなら「dev には本物のこの形の文が無く、1段階になった本物も0件だった」のように書き足す。

### 2. `kakunin@gmail.com` は実在しうるアドレス(確度は中、影響は小さい)

[`server/test/rules.test.ts`](server/test/rules.test.ts) の新しい表で2回使っている。`server/test/` は `scan-private.sh` の `test_data` にあたり、止まらないのは決まりどおりだ。ただ、ほかの試験は `x@gmail.com` を使っている。この2件は SMS の本文の中のアドレスで、段階は口止めの文だけで決まるので(後で書く消した版でも `null`)、`x@gmail.com` に替えても試験の意味は変わらない。公開前に替えておくと安心できる。

### 3. 差分の外の話で、main の From の表示名で送り元を名乗れる穴が Issue になっていない(確度は高い、影響は中から低)

dev-log は「公式の送り元も、From の表示名にアドレスを書けば名乗れた」と PR #167 の話として書いている。けれども、取り出しは main の [`server/src/gmail.ts`](server/src/gmail.ts) 444行目 `/<([^<>\s]+@[^<>\s]+)>/.exec(from)` で、最初の `<...>` を送り元にしている。だから main でも効く。

確かめた例では、本文が `【三井住友銀行】口座が凍結されました。こちらから確認してください https://smbc-kakunin.top/login` のとき、送り元 `x@evil.com` なら `1, confident true`、`info@smbc.co.jp` なら `1, confident false` になった。confident が落ちると、[`server/src/claude.ts`](server/src/claude.ts) 189行で規則の段階が下限にならず、Claude が軽くできる。メールの見出しにある文字が段階を下げる向きに使える経路だ。

`gh issue list` の題と本文を「表示名」「From の」「gmail.ts」で探したが、追っている Issue は見つからなかった。この PR を止める理由にはならない。別の Issue にしておくことを勧める。

## 確かめて問題なかったこと

- `npx vitest run test/rules.test.ts` は200件すべて通った。足した表は31行ある(スクラッチパッドの `probe.ts` で、試験の書かれた文字列をそのまま読んで数えた)。
- 31件それぞれで、今の `judgeByRules` の答えが期待値(段階と confident)と一致した。口止めの文(「言わない」「伝えない」「話さない」「内緒」を含む文)を消して流し直すと、31件すべてで段階が下がった。`null` が多く、2件は2段階だった。つまりどの例も、段階を口止めの型に頼っている。口止めの型が弱まれば落ちるので、意味の無い例は混ざっていない。認証コードの5件は、消すと `null` と `認証コードの知らせに見える` になる。`worthAsking` も false になり、Claude に回らない。PR #167 の2回目で問題になった形をそのまま押さえている。
- 試験の説明(「Each is at the level the rules give it today」「keeps main's level」)は、実際の振る舞いと合う。比べ方は完全な一致なので、強くなる向きに変わったときも落ちる。説明の範囲を超えて緩い、ということは無い。
- dev-log の `worthAsking` と189行の記述は正しい。`worthAsking` は [`server/src/inbound.ts`](server/src/inbound.ts) 28〜30行で、`null` かつ `CODE_ONLY_REASON` のときだけ false を返す。本物の形の `認証コード 1234。このコードはご家族にも言わないでください。`(SMS)と、`info@smbc.co.jp` からの `暗証番号はご家族にも伝えないようにしてください。` は、どちらも `1, confident false`、`worthAsking` は true だった。[`server/src/claude.ts`](server/src/claude.ts) の189行は `if (rule.level !== null && (rule.confident || claude.injection_suspected)) level = heavier(level, rule.level);` で、確かでない1段階なら Claude が軽くできる。Claude が `injection_suspected` を立てたときは下限が残る。この点は dev-log の最後の「プロンプトの側で見る」とつながっていて、食い違わない。
- 「困るのは Claude が答えないときだけ」も正しい。189行の上にある `decide` は、`claude === null` のときに規則の1段階をそのまま使う。
- PR #167 のレビューのコメントに書かれた例(理由を挟む口止めの5件、From の表示名の話、`plain` の試験が落ちようがないという指摘)は、この PR の表と dev-log の記述に合っている。
- 差分は `docs/dev-log.md` と `server/test/rules.test.ts` だけで、`server/src` は変わっていない。秘密の値、家族の実データ、外から写したもの、`ios/Core` の変更、時刻の記載は無い。電話番号の形をした例(`〇三-一二三四-五六七八`、`3-1234-5678`)は作り例で、`server/test/` の例外にあたる。holdout は読んでいない。
