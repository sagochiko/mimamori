## 指摘(重い順)

### 1. 中。jq が無いとき、行頭の `gh` を `need_jq` が見落とす(この PR が閉じたと主張する穴が複数行のコマンドで残る)

場所は `~/develop/mimamori/.claude/hooks/lib.sh` の118行目。

```sh
if [[ "$2" =~ (^|[^[:alnum:]_.-])(gh|wrangler|push)([^[:alnum:]_.-]|$) || ...
```

`$2` はフックに渡る生の JSON で、改行は `\n`、タブは `\t` に符号化されている。2行目の先頭に `gh` が来ると直前の文字が `n` か `t`(英数字)になり、語の境界に当たらない。jq を落とした状態で guard-prod.sh に本物の改行を含む入力を流した結果(`jq -Rs` で JSON 化、PATH の先頭に exit 127 する jq を置いた)。

```text
exit=0 : cd server|gh api -X DELETE repos/x/y          (通ってしまう)
exit=0 : cd server|<tab>gh api -X DELETE repos/x/y     (通ってしまう)
exit=2 : cd server|git push --force origin main        (push は前に空白があるので止まる)
```

このリポジトリでは heredoc のあとに gh を2行目に書く形がふつうにあるので、jq が無い環境では `gh api` の書き込みが黙って通る。`gh` の語は PR 以前から同じ正規表現だったので guard-merge.sh と guard-private.sh にも元からある穴だが、この PR は guard-prod.sh について「jq が無ければ gh、wrangler、push を止める」と本文と `docs/harness.md` の表に書き、足したテスト(`scripts/test-hooks.sh` 458〜462行目)はすべて1行のコマンドなので、この形を捕まえるテストが無い。`\\n` と `\\t` を境界として足す(あるいは照合の前に復号する)のと、改行のあとに `gh` を置く nojq のテストを足すのが直し方。確からしさは高い(再現した)。

### 2. 中。Gmail のごみ箱の deny は別の道具で迂回できる

場所は `~/develop/mimamori/.claude/settings.json` の106〜107行目(`mcp__claude_ai_Gmail__trash_*`、`mcp__claude_ai_Gmail__delete_*`)。

deny 自体は効いている。このセッションの道具一覧から `trash_message`、`trash_thread`、`delete_*`、`Google_Calendar__delete_event`、`Claude_Docs__delete` が消え、`untrash_message` と `untrash_thread` は残っていた(glob が前方だけに効いている証拠)。ただし ToolSearch で `+trash` を引くと `mcp__claude_ai_Gmail__apply_sensitive_message_label` と `apply_sensitive_thread_label` が残っていて、定義文は「Prefer `trash_message` or `mark_message_spam` instead. Adds a sensitive label (Trash or Spam)」、引数は `labelOption: TRASH | SPAM`。つまり trash と同じことをする道具が deny の外にある。`mark_message_spam`、`mark_thread_spam` も残っている(迷惑メール送り)。`update_message_labels` の `addLabelIds` に `TRASH` を入れる道も定義上はありうるが、コネクタ側が拒むかは確かめていない(撃つものが守る対象なので試していない)。

permissions の文書では `mcp__` の規則に括弧(引数の条件)を付けると読み飛ばされるので、閉じるなら道具の名前で deny に足す。`mcp__claude_ai_Gmail__apply_sensitive_*` と `mcp__claude_ai_Gmail__mark_*_spam` を足せば、PR 本文と `docs/harness.md` の「ごみ箱と削除は deny」が実態と合う。確からしさは高い(道具の定義で見た)。

### 3. 中の下。`gh auth status --show-token` でトークンが画面に出る道が、allow の規則の下で開いたまま

場所は `~/develop/mimamori/.claude/hooks/guard-secrets.sh` の9行目の `pat` と、`.claude/settings.json` の54行目 `"Bash(gh auth status*)"`。

この PR の4は gh のトークンの置き場(`~/.config/gh/`)を閉じたが、gh には `gh auth status --show-token`(短い形 `-t`)があり、`gh auth status --help` に「-t, --show-token  Display the auth token」とある。フックに流した結果はどれも通る。

```text
exit=0 : gh auth status --show-token
exit=0 : gh auth status -t
exit=0 : gh auth status
```

しかも `Bash(gh auth status*)` が allow なので、聞かれもせずにトークンが Claude の文脈と記録に入る。PR 以前からの穴だが、同じ PR で足したテスト(`scripts/test-hooks.sh` 26行目「gh auth status passes」)はこの形も通ることを固定している。`pat` に `gh[[:space:]]+auth[[:space:]]+status[^;&|]*(--show-token|[[:space:]]-t([[:space:]]|$))` のような項を足し、止めるテストを1つ置くのが直し方。確からしさは高い(再現した)。
