## 指摘

重い指摘は無い。軽いメモが2つある。どちらもこの直しで悪くなったわけではない。

1. メモ(この直しの前から同じ)。同じ本文が別々の受け手の呼び出しに同時に届くと、Claude は2回呼ばれうる。場所は `server/src/judge.ts` の 301〜377行。両方が `SELECT` で行を見つけられないまま `askClaude` まで進み、`INSERT ... ON CONFLICT (id) DO NOTHING` で負けたほうが 379行で `done` になる。行は1つで、母と家族への通知も1回(勝ったほうだけが `finishNotices` を通る)。余るのは Claude の呼び出し1回と枠1枚だけ。順に流れる同じバッチの中の2回では起きないことをテストで確かめた。前はメッセージの ID で重複を外していたが、それでも同じことが起きていた。確からしさは高い(コードを読んでの結論で、テストは無い)。

2. メモ(これから作る呼び手への注意)。`enqueueJudge` を呼ぶたびに新しい ID が作られる。なので呼び手が同じ受信を2回積むと、別々の知らせになる。iOS の拡張がやり直した場合、Gmail の同じメールを読み直した場合、`send` の結果が分からず積み直した場合がこれに当たる。今の `server/src` には `enqueueJudge` の呼び手が1つも無く(grep の結果は下に貼った)、タスク5、7、8がこれから作る。送り主かドメインがあれば1時間のまとめで2回目の通知は止まる。どちらも無い経路では、母と家族に2回届きうる。キューのメッセージ ID を使っていた前の作りでも、2回 `send` すれば2通になっていたので、悪くはなっていない。呼び手の側の約束として、タスク5か7の Issue に1行書いておくとよい。確からしさは高い。

## 確かめて問題なかったこと

- 別のメッセージ ID で同じ本文が2回届いたとき。2回目は 301〜318行で行を見つけ、Claude を呼ばない。`notified !== 1` なら `done` で、まだ届いていない側だけを `finishNotices` に回す。テスト「writes one alert and tells everyone once ... under different message ids」で、`alerts` が1行で ID が本文の `alertId`、`claudeCalls` が1、`opened` が1件、母への通知が1件、家族への通知が2件(端末2台)になることを確かめている。やり直しの5件のテストも、すべて新しいメッセージ ID の `redelivered` で届く形に変わっている
- 同じバッチに同じ本文が2回入ったとき。メッセージは順に流れるので、2つ目は1つ目が書いた行を見る。テストで ack が2件、`alerts` が1行、Claude の呼び出しが1回、母1件、家族2件になる
- ID の無い本文と壊れた ID は、`parseJob` が null を返す。そのあと 295〜297行で `console.error("judge job dropped", "bad_shape")` を出して ack する。ログに出るのは決まった文字だけで、家族の印も本文も出ない。キューに積むのは `enqueueJudge` だけ(`server/src` に他の `JUDGE_QUEUE.send` は無い)で、積む前に同じ `parseJob` を通す。なので正しく積んだ仕事は受け手で捨てられない。古い形の本文は、デプロイ前なのでキューに無い。取りこぼしは起きない
- `enqueueJudge` は `{ ...job, alertId: crypto.randomUUID() }` の順で広げる。呼び手が `alertId` を入れても上書きされる(テスト「does not let the caller choose the alert id」)。返り値は `void` のままで、計画のつなぎ目 `enqueueJudge(env, job: { familyId, source, payload })` と食い違わない
- UUID の検査。正規表現は小文字の 8-4-4-4-12 で、`^` と `$` が付いている。大文字、前後の空白、ハイフン抜き、後ろに文字を足したもの、SQL を足したもの、数値、null、空文字を、テストで並べて落としている。値は bind でしか使わない
- `docs/plan.md` タスク6の書き直し(293〜294行)は実際と合う。「受け手はメッセージの ID を知らせの ID にしている」の文は消えている。計画、設計、`server/src`、マイグレーションに、メッセージ ID を知らせの ID とする記述は残っていない
- `docs/dev-log.md` の「直す前のコードでは13件落ちた」は、自分で流して13件落ちることを見た(下に貼った)
- Cloudflare の文書を `search_cloudflare_documentation` で引いた。Queues の JavaScript APIs は `id` を「A unique, system-generated ID for the message.」、Pull Consumers は「a unique, read-only ephemeral identifier for the message.」と書いている。やり直しで ID が変わらないという記述は、どちらの検索でも出てこなかった。Workers の Storage Options は「offers at-least once delivery」、Workers Best Practices は「Queues provide at-least-once delivery with configurable retries per message.」。コードのコメントと dev-log の引用は文書の文と一致する
- `summarize`(161〜165行)は差分の外で、#55 の作業とは重ならない。差分が触っているのは 6〜17行、36〜48行、83〜131行、272〜300行だけ
- 計画の約束にも外れはない。段階の決め方、「安全」と言わないこと、家族への知らせを `openCase` だけから送ること、3段階と1時間のまとめで知らせないこと、`CaseNoticeDeferred` でのやり直しは、どれもこの差分で変わっていない。秘密、本物の家族のデータ、外から写したコードは無い。`ios/Core` には触れていない
