### 1. 直すべき。家族の全員に APNs が届かない状態が続くと、相談がいつまでも作られない

- 鍵や Team ID の設定違い(`InvalidProviderToken`)
- トピックの違い
- 2分を超える APNs の障害。キューのやり直しは30秒おきに3回まで

### 5. 軽い(実機で要確認)。読み上げのあとにセッションを閉じる処理が、黙って失敗しうる

場所は [`ios/App/ReplySpeaker.swift`](ios/App/ReplySpeaker.swift) の `release()` と `stop()`。

`setActive(false)` を `try?` で呼んでいる。合成器の音がまだ止まりきっていないと `isBusy` で失敗することがある、と聞いている(推測で、実機では見ていない)。とくに危ないのは「もう一度」の道で、`stopSpeaking(at: .immediate)` の直後に `release()` を呼ぶ。失敗しても何も残らず、`pending` はもう空なので、あとの `didCancel` でも閉じ直さない。直したかった「ほかのアプリの音が小さいまま」が、そのまま残る。

`ObjectIdentifier` の使い回しも気になる。古い発話が解放されたあと、同じ番地で新しい発話が作られ、古い `didCancel` がそれを消すことがありうる。これも推測。

シミュレータでは確かめられないので、`docs/human-queue.md` に「ラジオを流したまま返事を読ませ、読み終えたら音量が戻るか、『もう一度』のあとも戻るか」を積むのがよい。今は積まれていない。直すなら、失敗をログに出し、少し待ってもう一度閉じる。

### 6. 軽い。受け持ちが抜けると、その人が送った返事が母の画面から消える

## 直っていると確かめたこと

- 1件目(最初の知らせ)は、予算が足りなければ行を作らずに投げ、次の呼び出しで開いて知らせる。誰にも届かなければ消して投げる。1人にでも届けば残す。家族に端末が無ければ投げずに残すので、やり直しが止まらなくなることはない。`410` と `BadDeviceToken` ではトークンが消えるので、次の試行で届く端末が0になり、行が残る。2回目の呼び出しでは、枠を取る前に既存の相談を返すので、知らせも枠の消費も重ならない。同時の2回の呼び出しは、1文の `INSERT ... WHERE NOT EXISTS` で1件になる(負けた側は取った枠を使わずに捨てるが、害は無い)。家族に2回知らせが届くのは、APNs が受け付けたのに応答が失われて `failed` になった場合だけで、届かないよりはよい
- 2件目(抜けたとき)は、`UPDATE` と `DELETE` が `batch` の1つの取引で動き、`accepted` だけを `notified` に戻す。解決済みの相談と、ほかの人の相談には触れない。`renotified_at` を空にするので、最初の知らせから30分たっていれば次の回で母と残りの家族に1回知らせ、たっていなければ30分まで待つ。どれもテストで確かめている
- 3件目(文字数)は、裏側を `Intl.Segmenter` の書記素で数えるようにした。「👍」100個、「👨‍👩‍👧」10個、「あ」90文字の200字が通り、もう1字足すと 400 になるテストがある。前の `length` に戻すとこのテストは落ちる
- 4件目(音声セッション)は、全部読み終えたときと止めたときに閉じる作りになった。`SpeechSession` は `ios/Core` にあって Foundation しか使わず、遅れて届く取り消しが新しい行を消さないことをテストしている。実機での効き目は指摘5のとおり
- 5件目(送れなかったとき)は、シートの中の `.alert` で理由を出し、文を残し、送れたときだけ閉じる。出す文字は既存の `Problem` の見出しと「OK」だけで、画面の文言の決まりに沿う。デバッグ用のスタブの引数は Debug ビルドのファイルの中にだけある
- 6件目(計画の表)は、`cases` の行に `ai_reply` が足されている
