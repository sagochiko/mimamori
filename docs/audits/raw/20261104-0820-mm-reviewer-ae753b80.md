## 指摘

### 1. 直すべき(計画の文、数語)。やり直しの決まりに「家族に知らせる知らせだったか」の条件が無く、3段階やまとめた知らせでも相談が開いて家族に通知が飛ぶ

場所は [`docs/plan.md`](docs/plan.md) 295行目。

文は「やり直しで届いた同じメッセージは、知らせの行があり、相談が無いか家族に届いていないときは `openCase(env, alertId, budget)` だけを呼び」となっている。3段階の知らせと、1時間に1回にまとめて通知しなかった知らせは、もともと相談を作らない。だから、この2つが同じメッセージでもう一度届くと「知らせの行があり、相談が無い」に当たり、文のとおりに作ると `openCase` を呼ぶ。`openCase` は知らせの段階を見ないので([`server/src/cases.ts`](server/src/cases.ts) 297行目)、相談が開き、家族に「3段階」の通知が届く。

もう一度届く道は実際にある。Queues は少なくとも1回届ける作りで、#7 の受け手は1件ずつ `ack` するので、まとめて受けたうちの途中で Worker が落ちると、`ack` していない残りがまた届く。#7 の `alerts` には `notified` の列があり(`judge.ts` の INSERT)、2回目のレビューで出した案も「知らせの行が有り、`notified = 1` で」だった。書き直した文でこの条件が落ちている。

直し方は、文に「`notified = 1` の」を足すこと。守りを重ねるなら、`openCase` が3段階の知らせでは相談を開かないようにしてもよい。設計の「3段階は家族に通知を送らない」と「1時間に1回にまとめる」に直接かかわるので、#7 の人が文をそのまま実装する前に、この PR で直しておきたい。それ以外の部分(家族への知らせは `openCase` だけ、枠に家族の端末の数を足す、`CaseNoticeDeferred` でやり直す、知らせ済みなら何も送らない)は、#7 の `judgeOne` の形にそのまま当てはめられる書き方になっている。確かさは高い(計画の文と #7 のコードを突き合わせた)。

### 2. 軽い。列を立てたあとで D1 の呼び出しが例外になると、誰にも届かないまま「知らせ済み」になり、もう送り直さない

場所は [`server/src/cases.ts`](server/src/cases.ts) 229行目(列を立てる)、239行目(`membersOf`)、243行目と266行目(空に戻す)。

列を立ててから空に戻すまでのあいだで、`membersOf` か空に戻す UPDATE が例外になると(D1 の一時的な失敗、問い合わせの上限、CPU の上限で Worker が止まる)、`family_notified_at` が立ったまま残る。投げられるのは `CaseNoticeDeferred` ではない。次の呼び出しも Cron も「知らせ済み」と見て送らない。`sendPush` の中の失敗は捕まえているので、APNs 側の失敗ではこうならない。

残る救いは30分の見張りで、`renotified_at` が空なら30分で母と家族に1回ずつ知らせる。だから多くの場合、家族は30分遅れで知る。見張りでも知らないまま終わるのは、APNs が30分以上落ちていて見張りがすでに `renotified_at` を立てたあと(見張りは送れなくても立てる)、さらに Cron の送り直しの途中で例外が出たときだけで、重なりは狭い。2回目の指摘4(DELETE の失敗で元の穴に戻る)と同じ大きさなので軽いとした。直すなら、列を「立てた時刻」として扱い、数分たっても届いた印の無いものは Cron が取り直せるようにする(届いた時刻と取った時刻を分ける)。流れはコードで確かめた。起こる頻度は推測。

### 3. 軽い(上限の数字に食い違いあり)。届かない相談が多いと、Cron の1回で D1 の問い合わせが50を超えうる

場所は [`server/src/cases.ts`](server/src/cases.ts) 314行目から326行目。

送り直しは相談1件につき、列を立てる、家族を読む、`sendPush` の中でトークンを読む、空に戻す、の4回ほど D1 を呼ぶ。1回20件までなので、全家族で届かない相談が12件を超えると、最初の SELECT と合わせて50回を超える。D1 のドキュメント(developers.cloudflare.com/d1/platform/limits/)は Free の「Queries per Worker invocation」を50としている。一方で Workers の limits のページは Free の「Subrequests to internal services」を1,000としていて、どちらが今の D1 に効くのかはドキュメントだけでは決められない。50が効く場合、上限に当たった所で例外になり、指摘2の「立ったまま残る」が起き、同じ回の30分の見張りも問い合わせが通らず止まる。

APNs の設定違い(`InvalidProviderToken`)が続いて全家族の相談が溜まったときだけの話で、期間中の家族の数なら届かない相談が12件を超える見込みは低い。直すなら、1回の件数を減らすか、`budget.ts` の考え方で D1 の回数も数える。確かさは中くらい(上限の数字が食い違っている)。

## 2回目の3件が直っているか

- 1件目(行を消す作りで相談が消える)は直っている。行は最初に入れて消さず、届かなければ `family_notified_at` を空に戻して `CaseNoticeDeferred` を投げる。キューがあきらめても、5分ごとの Cron が1日のあいだ送り直す。家族の端末が無いときは「知らせ済み」にして投げないので、やり直しが止まらなくなることはない。2回目の指摘3(窓のあいだの `ai_reply` が消える、ID が変わる)と指摘4(DELETE の失敗)も、行を消さなくなったので一緒になくなった。AI の答えが残ることはテストがある
- 2件目(計画の文)は、#7 の受け手の形に合わせて書き直されている。家族への知らせを `openCase` だけにし、枠に家族の端末の数を足し、やり直しでは Claude と母への通知を飛ばすと書いた。足りないのは指摘1の条件だけ
- 3件目(音声セッションを閉じる処理が黙って失敗する)は直っている。失敗を `Logger` に出し、300ミリ秒と1秒あとに閉じ直す。待つあいだに次の読み上げが始まれば `speak` が取り消し、`stillWanted` でも止まる。「もう一度」で `stop()` と `speak()` が続けて呼ばれると、閉じる処理が走る前に取り消されるので、前の作りのように一度閉じて開き直すこともなくなった。`Retry` は `ios/Core` にあり、何も import していない

## 頼まれた場面ごとに確かめたこと

- 列を立ててから送るまでに Worker が落ちたとき。指摘2のとおり「知らせ済み」のまま残り、30分の見張りだけが拾う
- Cron とキューのやり直しが重なったとき。列を立てる UPDATE が `IS NULL` を条件にしているので、送るのは片方だけ。キューが先に取って届かなければ空に戻して `CaseNoticeDeferred` を投げ、次の Cron が拾う。Cron が先に取ったときは、キューの側は「知らせ済み」と見て相談を返し、#7 は `ack` する。そのあと Cron の送信が失敗しても空に戻るので、次の回の Cron が拾う。どちらの順でも行き着く
- 最初の知らせと30分の見張りが同じ回に送るとき。開いてから30分から35分のあいだに初めて家族に届いた回だけ、家族に「N段階」と「まだ誰も引き受けていません」が数秒差で2通届き、母には「家族から返事がまだ」が届く。APNs が30分より長く落ちていた場合は、見張りが30分の時点で(送れないまま)`renotified_at` を立てているので、あとで最初の知らせが届いても2通にはならない。重なりは狭く、害も小さいので指摘にはしなかった
- 24時間を過ぎたあと。Cron は送り直さず、相談は `notified` のまま一覧に残る。見張りはそれより前に1回走っている。30日の削除は `notified_at` で消すので、この列とは関係なく消える
- 移行の文は、前からある行の `family_notified_at` を `notified_at` で埋めるので、前からある相談に Cron が知らせを送ることはない。`cases` に行を入れるのはアプリのコードでは `openCase` だけで、ほかはテストの準備だけ
- 個人の情報、秘密、外から写したコードは差分に無い。電話番号やメールアドレスの形の文字も無い
