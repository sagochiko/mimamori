## 指摘

1. ページの2回目で規則が1段階や2段階と決めても、家族に知らせが行かない(確度は高い、コードで追った)

   場所は [`server/src/page.ts`](server/src/page.ts) の128〜136行(`const queued = me.role === "protected" && !alreadyQueued && pageWorthAsking(...)`)と、[`ios/SafariExtension/Resources/content.js`](ios/SafariExtension/Resources/content.js) の `alreadyQueued: queued`。

   キューの受け手 `judgeOne`([`server/src/judge.ts`](server/src/judge.ts) の371〜397行)は、積まれた `payload`、つまり1回目の本文で規則と Claude を走らせ直す。1回目の本文にまだ偽警告が無ければ、段階は3になり、行も知らせも残らない(397行の `QUIET_WHEN_UNDECIDED`)。2回目は規則で答えるだけで積まれないので、偽警告の入った本文で家族に知らせる道が無くなる。

   具体的にはこうなる。母があるページを開く。1回目の本文には、パスワードの欄(`hasSecretField`)か、段階を決めない規則の理由(`rule.reasons` が空でない)があり、`pageWorthAsking` が真になって積まれる。Claude はその本文を3と読む。数秒後に「ウイルスに感染しました、サポートに電話」の偽警告がページに足される。2回目の問い合わせで規則は1段階と答え、母の画面には覆いが出る。それでも `alerts` の行も家族のカードもできない。main ではこの2回目が積まれて1段階になり、家族に知らせていた。設計の「1と2の段階は家族に知らせる」に反するし、主役の筋「母が気づけないときに家族が代わりに気づく」にも外れる。

   ページの側でこの形を作るのも難しくない。最初の表示にパスワードの欄を置き、偽警告を5秒の待ちのあいだに遅れて出せばよい。ページの文で `alreadyQueued` そのものは立てられない。それでも、どの本文を Claude と家族の判定に回すかを、ページの中身と表示の時機で選べてしまう(注入の5番に当たる、段階を下げる向き)。ただ、もともと2回目より後に出す偽警告は今も逃れていて、そこはこの PR で変わらない。

   直し方の案を挙げる。2回目で `rule.level` が1か2のときは `alreadyQueued` があっても積む。ページは URL から必ず `domain_key` ができるので、1回目がすでに母に届いて知らせていれば、1時間のまとめ(`judge.ts` の403〜411行、`level <= ?`)が2回目の知らせを止める。余るのは Claude の呼び出し1回だけになる。止めるのは、2回目の規則が何も決めず、`pageWorthAsking` が立っただけのときに絞る。このケースの試験も無い。`alreadyQueued: true` で、本文に規則が1と決める文が足されたときに積まれることを固定するとよい。

2. 1回目が `queued: true` と答えたのに実際は積まれなかった場合、2回目でも積み直さない(確度は中、影響は小さい)

   [`server/src/page.ts`](server/src/page.ts) の130〜137行。`enqueueJudge` は `ctx.waitUntil` の中で走り、失敗しても `catch` でログに出すだけで終わる。それでも答えには `queued: true` が付く。キューへの送信が落ちると、1回目も2回目も Claude に届かない。main では2回目が拾い直していた。直すなら1か所で済み、`queued` を返すのは enqueue を待って成功したときに限る。待っても `JUDGE_QUEUE.send` の1回分なので、答えはほとんど遅れない。

3. 2回目の時計を1回目の答えから数えるので、2回目の覆いは遅れうる(確度は高い、影響は小さい)

   [`ios/SafariExtension/Resources/content.js`](ios/SafariExtension/Resources/content.js) の `first.sent.then(() => setTimeout(...))`。1回目の覆いは答えが来た時点で出るので、変わらない。遅れるのは2回目の覆いだけで、1回目の答えにかかった時間の分になる。ネイティブ側の打ち切り(`PageCheck.timeout` の8秒)まで待つと、最悪は読み込みから約13秒に、そこから2回目の往復が足される。`sent` は `.catch(() => {})` まで含んだ鎖なので、拒否で止まりはしない。待つのは、1回目が積まれたかを知るための意図した変更だと読める。それでも、指摘1を直して規則が決めたときは積むことにすれば、待つ理由は薄くなる。

## 確かめて問題なかったこと

- 注入で `alreadyQueued` を直に立てられるか。裏側は本文の `alreadyQueued` 欄だけを真偽で読み、ページの文は見ない。真偽でない値は400 `page_invalid` になる。`content.js` の `queued` は拡張の答え(`reply.queued === true`)からしか立たない。`background.js` は `message.recheck === true && message.alreadyQueued === true` のときだけ送る。ページの JS は content script の変数と `runtime` に届かない。試験 `queues even when the page's text says it was already checked` は、本文に `alreadyQueued: true` と書いても積まれることを確かめていて、壊せば落ちる形になっている。
- `queued` の読み取り([`ios/Core/Sources/MimamoriCore/PageCheck.swift`](ios/Core/Sources/MimamoriCore/PageCheck.swift))。JSON の true 以外は積まれていない扱いで、変な値でも警告は落ちない(試験 `queuedReply`)。答えの JavaScript には段階と `queued` しか渡らず、ページの文も裏側の文も載らない。「安全」と読める欄も無い。
- `gmail.ts` の `saveProgress` の競合の守り。`WHERE` は、始めに読んだ `last_history_id` と `partial_record_id IS ?`、`partial_message_ids IS ?` で比べる。SQLite の `IS` は NULL どうしも等しいと見るので、空のままの行でも合う。ほかの実行が先に動かした行は上書きしない。2つの実行が同時に同じメールを積むのは main からある性質で、この PR で悪くはならない。`stop` のクロージャは呼ばれた時点の `done` を読む。途中の記録の `handled` は保存してある ID から始まる。保存した記録を読み終えると `partial` は空に戻る。history の呼び出しが落ちたときと、予算で何も読めなかったときは、`done === grant.last_history_id` で書かずに持ち越す。404 で読み直すときは `partial` も消す。許可を取り直すとき(`callbackRoute`)も消す。
- Gmail の試験3件。記録の途中で送信が落ちる場合、上限で止まる場合、間の実行で history が 503 になる場合のどれも、`calls.messages` で読んだメールの並びまで固定している。手元で `npx vitest run test/page.test.ts test/gmail.test.ts` を流し、`Tests 126 passed (126)`。
- 0006 と古い版が混ざる場合。古い Worker は列を名指しで SELECT し、UPDATE も `last_history_id` だけなので、新しい列があっても動く。古い版が `partial` を残したまま `last_history_id` を進めても、残った記録の ID は同じ記録がまた来ない限り合わず、害は無い。ロールバックしても動く。逆の順(先に Worker)だと SELECT が落ちるが、PR の「デプロイの順」と、[`.claude/skills/mm-deploy/SKILL.md`](.claude/skills/mm-deploy/SKILL.md) の35行(未適用のマイグレーションがあれば先に流す)で手当てされている。
- 古い拡張と新しい裏側の組み合わせは、`alreadyQueued` が無いので false になり、今までどおり。新しい拡張と古い裏側の組み合わせは、`queued` が返らないので `alreadyQueued` が立たず、古い裏側は知らない欄を無視するので今までどおり。
- `docs/plan.md` の D1 の表と `POST /page` の行は、コードの形と合っている。秘密、実在の家族の情報、外から写したもの、`ios/Core` が iOS 専用の枠組みを読み込むことは、差分に無い。
