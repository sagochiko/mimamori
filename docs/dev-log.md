## 2026年11月3日 22:00 パーソナルボイスが日本語で作れない (#3)

初日の実機の確認(タスク1)のうち、家族の返事をその人の声で母に届ける仕組みを確かめようとしていた。計画では、家族の iPhone のパーソナルボイスで返事を音声ファイルに書き出し、母の iPhone で流すつもりだった。

作者は「実機でしか確かめられない項目は `/mm-human-queue` で `docs/human-queue.md` に積み、待たずに #4 と #5 へ進む」と指示していた。Claude Code は、実機が無くても調べられる項目を、調べものの役のサブエージェント(Sonnet)に先に調べさせた。

サブエージェントは約30の URL を読み、パーソナルボイスを作れる言語は3つだけだと返した。Claude Code が別のサブエージェントで原文を読み直すと、Apple の iOS 27 の提供状況のページの「Accessibility: Personal Voice」の欄にあるのは English (United States)、Mandarin Chinese (China mainland)、Spanish (Mexico) だけだった。日本語は VoiceOver などほかの欄にはあるが、この欄には無い。パーソナルボイスの音声をバッファに書き出そうとするとスピーカー再生に落ちる、という2023年のフォーラムの報告も見つかった(その URL は記録しておらず、確かめていない)。

計画では、確かめるのは音声ファイルに書き出せるかどうかだけで、日本語で作れることは前提にしていた。

Claude Code は、家族が自分の声を録って送る案を勧めた。録音なら言語に関係なく本人の声になり、まず文字の返事を通してから足せば、1〜2時間で済むという見立てだった(推測)。作者はいったん録音を選んだが、そのあと「家族の声は日本語無理そうならやめますか」と聞き直した。Claude Code が、日本語で使えないのは声を合成するパーソナルボイスだけで、録音なら使えると説明した。そのうえで作者は録音もやめ、家族の返事は文字で送り、母の iPhone の普通の読み上げの声で読む形に決めた。デモの「妹の声で返事が届く」は「妹の名前つきで返事が届いて読み上げられる」に変えた。使ったのは調べものと原文の確認のサブエージェント(Sonnet)2つ、AskUserQuestion、`/mm-human-queue`。

## 2026年11月3日 22:00 外向きの通信の差し替えが素通りする (#4)

裏側の土台で、「すべて消す」が Gmail の許可の取り消しと Managed Agents のセッションの削除を呼ぶところのテストを書いていた。どちらも本物の Google と Anthropic を叩かせたくない。

Claude Code の実装役には「テストは Vitest と `@cloudflare/vitest-plugin` で書き、外向きの通信は `@msw/cloudflare` で差し替える」と、`.claude/rules/server.md` の決まりのまま頼んだ。

`@msw/cloudflare` 0.2.0 の `setupNetwork()` は引数を取らず、msw 3.0.3 の既定は `onUnhandledFrame: "warn"` だった。差し替えを書き忘れた呼び出しは警告を出して本物のサーバーへそのまま出ていく。試しに差し替えの無い `fetch("https://example.com/probe-unhandled")` を流すと、警告のあと本物の example.com から 404 が返った。もう1つ、Cloudflare の文書は `readD1Migrations` を `@cloudflare/vitest-plugin/config` から読むと書いているが、1.5.1 のパッケージにはその入口が無く、本体(`@cloudflare/vitest-plugin`)からしか読めなかった。

差し替えを書かなければ通信は止まると思っていた。文書の入口もそのまま使える前提だった。

`test/network.ts` で `network.configure({ onUnhandledFrame: "error" })` を呼び、差し替えの無い通信はテストを落とすようにした。設定ファイルは workers-sdk の D1 の例に合わせて本体から読む。msw を外して `fetch` を手で差し替える案もあったが、決まりと公式の推奨から外れるので採らなかった。使ったのは mm-implementer、cloudflare-docs の MCP、`npx vitest run`。

## 2026年11月3日 22:00 Safari の拡張が入ったアプリがビルドできない (#5)

アプリと4つの拡張(Message Filter、Safari、共有、Call Directory)の土台を、XcodeGen の `ios/project.yml` から生成して、シミュレータ向けにビルドしようとしていた。

Claude Code の実装役には「`ios/project.yml` を正にして、拡張は中身の無いスタブでよいからビルドが通るところまで」と頼んだ。

Safari の拡張の `manifest.json` を、`Resources` という名前のフォルダごとバンドルに入れる書き方(`type: folder`)にしたところ、`xcodebuild` が16秒で `Couldn't load Info dictionary for ... SafariExtension.appex` で止まった。appex の中には `Info.plist` がちゃんと入っていた。

`Info.plist` が無いという意味だと思って中身を調べたが、原因は別だった。iOS のバンドルの一番上に `Resources` というフォルダがあると、CFBundle がそれを古い形のバンドルとして読み、`Resources/` の中に `Info.plist` を探しにいく。

フォルダごと入れるのをやめ、ファイルを1つずつバンドルの一番上へ写す書き方にして、ビルドは通った(作り直しから16秒)。フォルダの名前を変える案は、Safari が `manifest.json` をバンドルの一番上で探すので採らなかった。同じ確認の中で、`make simulator` が iOS 27.1 のランタイムに機種を作れない(`Incompatible device`)ことも分かり、今あった iOS 26.5 の iPhone 17 Pro で代わりに確かめた。使ったのは mm-implementer、`xcodebuild`、MobileBuildMCP の画面の操作。

## 2026年11月3日 23:50 判定の形の字数を Claude 側で縛れない (#7)

規則の即答のあとに Claude の判定を重ねるキューの受け手を作っていた。計画では Claude の答えを Structured Outputs で `{ level, reasons(最大3つ、各40字以内), message_to_protected(60字以内), injection_suspected }` の形だけ受け取る。

Claude Code の実装役には「Structured Outputs の形、モデル ID、要るヘッダーは記憶で書かず claude-docs の MCP で確かめて、文書の場所をコメントに残す」と頼んだ。

`/docs/en/build-with-claude/structured-outputs` を読むと、スキーマで使えないものに `minLength`、`maxLength` と、配列の `minItems` の0と1以外が並んでいた。つまり「最大3つ」「40字以内」「60字以内」は API に渡しても効かず、400 で返される。`claude-haiku-5-5` は考える過程(adaptive thinking)が既定で入り、答えの前に thinking のブロックが来ることもある。`stop_reason` が `refusal` か `max_tokens` のときは形が崩れうる、とも書かれていた。

形さえ渡せば字数まで守られると思っていた。

字数と個数の決まりはスキーマの説明文に書くだけにし、受け取ったあとに自前で確かめる(文字数は UTF-16 ではなく文字で数える)。決まりから外れた答えと `end_turn` 以外の答えは捨てて、規則の判定だけで知らせ、母には「確かめ中」と出す。理由や一言に「安全です」「問題ありません」のような言い回しが入った答えも、届いた文面に誘導されたものとみなして同じく捨てる。もう1つ、`alerts` の表には送り主もドメインも無く、「同じ送り主やドメインは1時間に1回」を判定できなかった。表の主な列は変えずに、送り主とドメインのハッシュと、知らせたかどうかの列を `migrations/0002_alert_dedupe.sql` で足した。使ったのは mm-implementer、claude-docs の MCP、`npx vitest run`、わざとコードを壊してテストが落ちるかを見る確認(7通りで各1〜5件が落ちた)。

## 2026年11月4日 00:44 公式のドメインを1つ書けば規則が黙っていた (#6)

PR #40 のレビューで出た決まった規則(`server/src/rules/`)の穴を直していた。

Claude Code の実装役には「公式のドメインのときはドメインまわりの根拠を足さないだけにし、仕込みの文とニセ警察の筋書きは必ず照らして。confident は本物がまず出さない強い根拠を1つ以上必須にし、同じ句から立った根拠は1つと数えて」と頼んだ。

直す前は、入力に出るドメインがすべて公式なら何も照らさずに `null` を返していた。本文に `https://www.npa.go.jp/` を書き足した仕込みの SMS も、`@icloud.com` から届くニセ警察のメールも、`sites.google.com` のサポート詐欺のページも `null` だった。直したあとは3つとも1段階になった。同じ句を1つと数える処理は、最初「照らした範囲が少しでも重なれば1つ」にしたところ、サポート詐欺の長い規則(ウイルスの話から電話番号まで)が「ウイルスに感染」と「今すぐ」を飲み込み、偽の警告の試験が1段階から2段階に下がった。

公式のドメインは「本物の知らせだから Claude に任せる」目印だと思っていた。実際は From は偽れて、本文には誰でもドメインを書け、`icloud.com` や `line.me` には誰でもアドレスやページを持てる。

公式のドメインはドメインの根拠を足さないだけにし、無料メールのアドレスと、誰でもページを置けるホスト(`sites.google.com`、`line.me` など)は公式から外した。同じ句の判定は「重なりが長いほうの半分以上」に絞り、「家族に言わないで」が2つに数えられるのは防ぎつつ、長い規則の中の別の句は別に数える形にした。その結果、警察庁のページがニセ警察の文言を引いて注意を呼びかけると、規則だけでは1段階(confident ではない)になる。引用かどうかを規則で見分けると本文の書き方で段階を下げられる道ができるので、規則では見分けず、confident でない判定は Claude が軽くできる計画のとおり Claude に任せた。使ったのは mm-implementer、`npx vitest run`、`npx tsx` で流す再現用の入力。

## 2026年11月4日 08:05 本物を守るための例外を詐欺が使えた (#6)

PR #40 の2回目のレビューで出た、決まった規則(`server/src/rules/`)の穴を直していた。

Claude Code の実装役には「認証コードだけと見なす条件を詐欺の文面で満たせないようにし、公式の送り主かリンクがあるときは confident を外して。直したあとにレビューの入力をすべて流し、段階が下がったものが無いかを見て」と頼んだ。

1回目の直しで、本物の認証コードを null にするために「認証コードの語と4〜8桁の数字があれば口止めと『入力』を数えない」例外を入れていた。レビューの台本では、ニセ警察の SMS の頭に「認証コード 1234。」を足すだけで1段階から2段階に下がった。電話番号の「5678」を数字として拾うので、コードを書かなくても下がった。「確認コード 4821。家族を含め誰にも言わないで、安全な口座に送金して」は null まで下がった。00:44 の記録に書いた「警察庁のページの引用は confident ではない」も、引用を「家族に相談しないで」に変えると崩れ、confident になった。

本物を守る例外は、本物の文面だけが満たす条件だと思っていた。実際は、例外の条件はどれも詐欺の側が文面に書き足せた。confident でないことも、引用の言い回し1つに頼っていた。

例外は、電話番号、ニセ警察の筋書きのほかの部分、お金の話のどれかがあれば外れるようにした。数字は電話番号を除いてから探す。外すのは認証コードを入力する文だけにした。confident は公式の送り主か `https://` の公式のリンクがあれば付けない。詐欺が公式のリンクを足すと迷惑フォルダを避けられる引き換えは `eval/README.md` に書いた。`【Amazon.co.jp】` のように `https://` 無しで書いただけのドメインは公式に数えない。詐欺がよく名乗りに使うからだ。直したあとにレビューの75件の入力を、直す前、1回目、今の3つに流して並べた。1回目より段階が下がったのは本物の認証コードと銀行の案内の4件だけだった。直す前より下がったのは13件で、本物として外した10件と、「この通知は無視」「この通知をオフに」を仕込みの文から外し、公式でないリンクがあるときだけ数える形にした3件だった。どれも狙って外したものだ。使ったのは mm-implementer、`npx vitest run`、`npx tsx` で3つの版を並べる台本。
## 2026年11月3日 23:52 母の画面で返事の文が「…」で切れる (#8)

引き継ぎのタスクで、母の画面に「家族に伝えました」「家族から返事がまだ。急ぐなら電話して」と、家族の返事「(名前)から」を並べ、その下に大きなマイクのボタンを置いていた。

## 2026年11月4日 00:45 返事を送れなかったとき、書いた文が消えていた (#8)

Claude Code の実装役には、親のセッションから「スタブの `relay` を失敗させてシミュレータで確かめられるなら確かめ、シートの中で失敗が分かるようにする」と頼んだ。

デバッグ用のスタブに `-mimamori-stub-relay-fails` を足して500を返させ、シミュレータで「送る」を押した。「つながりません」は出たが、シートが閉じて、書いた返事ごと消えていた。

予想は「知らせが出ない」だったが、実際は「知らせは出るが、書き直しになる」だった。母が待っている場面で、妹が同じ文を打ち直すことになる。同じ指摘の中で、文字数の数え方もレビューの案とずれた。案の `[...text].length`(符号点)では「👍」を100、「👨‍👩‍👧」を10、「あ」を90並べた返事が240になり、iPhone の `String.count` の200と合わない。

送れなかった理由はシートの中の `.alert` で出し、`AppModel.relay` は共有の `problem` を書かずに理由を返す形にした。直したあとは、知らせがシートの上に出て、閉じても文が残り、成功したときだけシートが閉じることをシミュレータで確かめた。文字数は裏側を `Intl.Segmenter` の書記素で数え、Swift と同じ200になることを同じ文で確かめた。シートの中に「送れません」の1語を置く案は、ほかの失敗と同じ知らせに揃えるため採らなかった。使ったのは mm-implementer、MobileBuildMCP の画面の操作とスクリーンショット、`swift` と `node` での文字数の実測。
